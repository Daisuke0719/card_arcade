# Claude Code の使い方 — 丸投げではなく「速く正確な同僚」として

Claude Code は魔法の箱ではありません。
**とても速く、とても正確で、しかし放っておくと自分の担当範囲と目的を勝手に広げてしまう同僚**です。

同僚に仕事を頼むときと同じことをすれば、それでうまくいきます。

1. **何をするかを先に握る**
2. **上がってきたものを自分で確かめる**
3. **責任は頼んだ側が持つ**

この文書は、その3つを180分の研修の中で回すための手順書です。
リポジトリの決まりは `CLAUDE.md`、止められたときの仕組みは `docs/harness.md`、
エラーの直し方は `docs/troubleshooting.md` を見てください。

## ターミナルは2本 — 人間の担当を「ルール」ではなく「場所」にする

**このページで最初に読むのはここです。** 今日の研修は、ターミナルを2本開いた状態で進みます。

| | ターミナルA（Claude Code） | ターミナルB（自分の手だけ） |
|---|---|---|
| 中身 | Claude Code のセッション | ふつうの PowerShell |
| 常駐 | — | **`npm run dev`（研修中つけっぱなし）** |
| やること | 調査 / 計画 / 実装 / 差分読み / 下書き | **実機で遊ぶ** / `npm test` の自分確認 / `gh pr ready` / Approve / `gh pr checkout` / テストを疑う儀式 |
| 打つもの | プロンプト（日本語） | コマンド（PowerShell） |

### なぜ2本に分けるのか

今日はプロンプトで進めます。**プロンプトで進めるほど、丸投げしやすくなります。**
これは研修の目的（AI に丸投げしない）と、はっきり逆を向いています。

だから、**丸投げできる範囲を広げたぶん、丸投げできない場所を物理的に切り出しました。** それがターミナルB です。

「人間が確認しましょう」という**ルール**は、忙しくなると守られません。
でも「そのコマンドはターミナルB でしか打てない」という**場所**は、忙しくても動きません。
**ターミナルB でしかできないことは、あなたにしかできないことです。**

### ターミナルB の起動（研修が始まったら最初にやる）

```powershell
cd $HOME/dev/card_arcade
npm run dev
```

ブラウザで http://localhost:5173/ を開いたら、**そのまま180分つけっぱなし**にします。
コードを変えても再起動は要りません。**ブラウザを F5 で再読み込みするだけ**で最新のコードになります。

`Ctrl + C` で止めるのは、研修が終わったときだけです。

### ターミナルA では `npm run dev` が「実行できない」

これは我慢や心がけの話ではありません。**ハーネスが物理的に拒否します。**

```text
npm run dev は Claude Code からは実行できません。
起動したままになるので、このセッションが返ってこなくなります。
```

Claude Code に「開発サーバーを起動して」と頼んでも、何度頼んでも同じメッセージが返ります。
**回り込む方法を探させないでください。** 探す時間が、そのまま遊ぶ時間から引かれます。

## Claude Code に打てないコマンド一覧

ターミナルA で打っても**実行されず、拒否メッセージが返る**ものです。
「頼んだのに動かない」の答えは、たいていこの表にあります。

| コマンド | なぜ実行できないか | 代わりにどうするか |
|---|---|---|
| `npm run dev` / `npm run preview` | 起動したままになりセッションが返らない。参加者の 5173 番とポートが衝突する | **ターミナルB** で起動する。すでに動いていればブラウザを F5 |
| `npm run test:watch` / `npm test -- --watch` / `npx vitest`（`run` なし） | 監視モードは終わらないので、セッションが返らない | `npm test`（= `vitest run`）を使う。保存のたびに流したいなら**ターミナルB** で |
| `gh pr review` / `gh pr comment` / `gh issue comment` | 他人の Pull Request と Issue に文字を投稿する = **他の人に波及する側**。書いてよいのは「自分が実機で確認したこと」だけで、確認したかどうかを知っているのは人間だけ | 下書きは `/review` と `/fix-review` に作らせ、**GitHub の画面から自分で投稿する** |
| `gh api` | 上の判定を全部迂回できる**裏口**（作業ブランチのときだけ止まる） | やりたいことを言葉で言う。必要なら講師に相談する |
| `node scripts/setup-github.mjs` / `node scripts/build-issue-bodies.mjs` | **講師専用。** 9人分の Issue をまとめて壊せる（作業ブランチのときだけ止まる） | 参加者は使わない |
| `npm run scaffold -- --all` / `--force` | **講師専用。** 9人分の雛形をまとめて上書きする（作業ブランチのときだけ止まる） | `npm run scaffold -- --game <自分のゲームID>` を使う |
| `gh issue edit` | Issue 本文は全員が同じ条件で進むための基準なので、講師が管理する（作業ブランチのときだけ止まる） | チェックボックスは GitHub の Issue 画面で自分でクリックする |
| `npm install` / `yarn add` などの依存追加 | `package-lock.json` が変わると9人全員の Pull Request が競合する | `@core` と `@ui` で作る。足りなければ講師に相談する |
| `git push --force` / `git commit --no-verify` / `main` への push | 履歴とチェックを壊す。他の人の作業に波及する | 直しを新しいコミットで重ねる |

### 承認を求められるもの（`ask`）

実行はできますが、**人間に「よいですか？」と確認が出ます。**

```text
git push / gh pr create / gh pr merge / gh pr ready / gh pr edit / gh issue create
```

**この6つは、承認を押すのではなくターミナルB で自分の手で打つ決まりです。**
どれも「他の人に見える」か「元に戻すのに手間がかかる」操作だからです。
とくに `gh pr ready` を打った瞬間から、相手のレビュアーがあなたのコードを触り始めます。

### 確認なしで通るもの（`allow`）

```text
npm test / npm run verify / npm run build / npm run scaffold -- --game <ゲームID>
git switch / git add / git commit / git status / git diff / git pull
gh pr checkout / gh pr view / gh pr checks / gh pr diff
node -v / gh auth status
```

**なぜ全部に確認を出さないのか**は `docs/harness.md` の「なぜ無害なコマンドは確認なしで通るのか」にあります。
ひとことで言うと、**確認の回数が増えると、本当に大事な確認が形骸化するから**です。

## 3原則

### 原則1: 計画を先に出させる

いきなり「作って」と言わないでください。最初は必ず `/kickoff <Issue番号>` です。

```text
/kickoff <Issue番号>
```

`/kickoff` は **コードを1行も変更できないようになっています**。
コマンドの定義（`.claude/commands/kickoff.md`）に `disallowed-tools: Edit, Write, NotebookEdit` と書いてあり、
このコマンドの間だけ編集ツールそのものが取り上げられます。
だから安心して「まず考えさせる」ことができます。

`/kickoff` が出すのは次の7点です。

- 採用するルール（Issue に書かれたものだけ）
- 状態の設計（State / Action / フェーズの遷移）
- 純粋関数の一覧
- テストの一覧
- 画面の構成
- 実装の順番（Step1 → Step2 → Step3）
- 分からないこと・確認したいこと

**ここで人間が合意するまで `/implement` に進まないでください。**
計画が5分ずれていると、実装は30分ずれます。研修でいちばん時間を失うのは、
合意していない計画で30分実装してから作り直すパターンです。

合意する前に、計画を1か所だけ削らせるプロンプトを打っておくと精度が上がります。

```text
この計画のうち、Issue に書かれていない機能を1つ以上挙げてください。
挙げたものは計画から外してください。まだ実装はしないでください。
```

### 原則2: 実装結果は人間が実機で確認する

AI は「実装しました」とは言えますが、「遊んで楽しかった」とは言えません。
`/implement` が終わったら、**必ず自分の手で1回遊んでください。**

**ターミナルB の開発サーバーはつけっぱなしなので、ブラウザを F5 で再読み込みするだけです。**

```powershell
# ターミナルB（止まっていたときだけ）
npm run dev
```

- 最初から最後まで通しで1回プレイする
- リセットして2回目が正しく始まるか見る
- やってはいけない操作をわざとやる（判定中の連打、出せないカードのクリック、0枚のときに引く）

`npm run verify` が緑でも、遊べないゲームは緑になります。テストは「書いたことしか確かめない」からです。
**遊ぶのは人間の仕事です。** そして、遊ぶ道具（開発サーバー）はターミナルB にしかありません。

遊ぶ前に、**壊し方を3つ、自分の手で書き出してください。** Claude に考えさせないでください。

```text
（これは Claude に打つプロンプトではありません。自分のメモ帳に書きます）

このゲームで、私が壊せそうだと思う操作を3つ:
1.
2.
3.
```

自分で書いた3つを試すのと、AI が挙げた3つを試すのは、まったく別の作業です。
**前者はあなたがルールを理解している証拠になり、後者は何の証拠にもなりません。**

### 原則3: テストの中身は人間が読む

テストが100件あっても、全部が正常系なら仕様は守られていません。
`logic.test.ts` を開いて、**`it("...")` の日本語だけを上から読んでください。**

お手本（`src/games/example-game/logic.test.ts`）のテスト名はこうなっています。

```
it("同じランクは引き分け")
it("判定中にもう一度予想しても状態が変わらない（連打で先に進めない）")
it("山札が空なら予想した時点で終了する")
it("判定待ちでないときの tick は無視される")
it("同じ seed なら同じ展開になる（テストが安定する）")
```

テスト名を読むだけで「このゲームは何を守っているか」が分かります。
自分のゲームのテスト名を読んで**そうなっていなければ、テストが足りていません。**

そしてもう1つ、**必ず1回はやってください。**

> `logic.test.ts` のアサーション（`expect(...)` の行）を1つだけわざと逆にして `npm test` を実行し、
> **赤くなることを確認してから元に戻す。**

赤くならないテストは、何も守っていないテストです。これは30秒で終わります。

**この儀式は、ターミナルB とエディタだけで行います。ターミナルA には1文字も打ちません。**
「このテストは正しいですか」と Claude に聞くのは、この儀式の代わりになりません。
**聞いた時点で、確かめたのはあなたではなくなります。**

儀式が終わったら、ターミナルA で**1回だけ**これを打ちます。

```text
今 logic.test.ts を1行だけ書き換えて、元に戻しました。
git diff で本当に元に戻っているか確認してください。
差分が残っていたら、どの行かだけを教えてください。直さないでください。
```

**このプロンプトは、儀式をやった人にしか打てません。** やっていない人には、打つ理由がありません。
（`Ctrl + Z` を押しすぎて**戻しすぎている**こともあります。このプロンプトはそれも見つけます。）

## スラッシュコマンド8本

`.claude/commands/` に入っています。チャット欄に `/` を打てば一覧が出ます。

| コマンド | いつ使う | 何をする（そして何をしない） |
|---|---|---|
| `/kickoff <Issue番号>` | 実装を始める前に1回 | Issue と正典（`docs/games/<ゲームID>.md`）を読み、ルール・状態設計・関数一覧・テスト一覧・実装順を出して**そこで止まる**。**コードは変更できない**（編集ツールが無効） |
| `/implement [Step番号]` | 計画に合意したあと | 合意した計画に沿って実装する。**テストを先に書いて赤を確認してから** `logic.ts` を書き、最後に画面を作る。計画に無いことは足さず、思いついた改善は提案として最後に書くだけ。**`npm run dev` は実行しない**（画面の確認は人間に依頼する） |
| `/verify [Issue番号]` | 提出前 | `npm run verify` を実行し、Issue の必須要件と実装・テストの対応表を作る。`rule-checker` サブエージェント（別の目）にも規約を点検させる |
| `/pr` | Pull Request を出す直前 | `git diff origin/main...HEAD` を読んで本文を `.pr-body.md` に書く。**`git push` も `gh pr create` も実行しない**（人間がターミナルB で打つ）。「レビューしてほしい点」は空欄のまま残す（人間が書く欄） |
| `/review <相手のPR番号>` | 相手の PR をレビューするとき | **人間がターミナルB で `gh pr checkout` して遊び終わったあとに**打つ。何を実機で見たかを先に聞いてから差分を読み、3点セットの指摘案を作る。**コメント投稿はしない**（ハーネスが止める。編集ツールも無効） |
| `/fix-review <自分のPR番号>` | 自分の PR に指摘が付いたとき | コメントを取得し「直す / 相談 / 直さない」の3分類で対応方針の表を作る。**合意してから**直し、指摘ごとの返信文案まで作る（投稿は人間が GitHub の画面から） |
| `/handoff` | 中断するとき・講師に状況を渡すとき・**Step9 と Step12 の直前**（必須） | 今どこ / 直前にやったこと / できている・できていない / 次の一手 を10行でまとめる。**次に打つコマンドを1つだけ**示す。**出てきた10行から、事実と違う行を1つ人間が探す**のがこのコマンドの本体 |
| `/stuck <困っていること>` | 詰まったとき | `scope` `lint` `typecheck` `test` を回して事実を集め、**最初のエラーだけ**を引用し、次の一手を1つだけ出す。**コードは変更しない**（詰まったときに作り直しを始めさせないため） |

**編集ツールを取り上げてあるのは `/kickoff` `/review` `/stuck` の3本です。**
「考えるだけ」「読むだけ」「整理するだけ」のときに、勝手に手が動かないようにしてあります。

### `/handoff` は「読むためのメモ」ではなく「あなたを試すための10行」

`/handoff` は Step9（中間チェックポイント）と Step12（`/pr` の直前）の**直前に必須**です。
出てきた10行を読んで満足しないでください。**課題はこれです。**

> ### 出てきた10行のうち、**事実と違う行を1つ**探してください

`/handoff` は「今どこ / 直前にやったこと / できていること / できていないこと / 次の一手 / 注意」を10行で出します。
**その中には、たいてい1行、実態とずれた行があります。**
「できている」に書かれているが実は途中のもの。「次の一手」が、もう終わっていること。

**これは、あなたが自分の状態を知っていなければ判定できません。**
だから、`/handoff` を打つ前にターミナルB でこの4つを打ち、出力を画面に残しておきます。

```powershell
git branch --show-current
npm run scope
npm test
git status --short
```

1行も判定できなかったとしたら、それは AI に丸投げしていて状態を把握していない、ということです。
**責められることではなく、今日いちばん役に立つ発見です。** そのときは講師に見せてください。

見つけたら、その行を引用して直させます。

```text
引き継ぎメモの「<その行をそのまま貼る>」は事実と違います。
実際は <正しい状態> です。

どこを見てそう書いたのかを説明してから、その行だけを直してください。
他の行は変えないでください。コードも変更しないでください。
```

## 良いプロンプトと悪いプロンプトの対比

### 対比1: 実装を頼むとき

| | プロンプト |
|---|---|
| 悪い | 「<ゲーム名>を作って」 |
| 良い | 「Issue #<Issue番号> の Step1 だけ、`logic.ts` と `logic.test.ts` を実装して。画面（`.tsx`）はまだ触らないで」 |

**なぜ悪いのか**: 範囲が無いので、AI は自分で範囲を決めます。
ルールも自分で決め、画面も作り、CPU も作り、10分後に600行が出てきます。
そうなると人間は読めず、確認できず、直せません。**確認できない成果物は、無いのと同じです。**

良いプロンプトの型はこれです。

```text
<正典の場所> の <どの部分> だけを、<どのファイル> に実装して。
<やらないこと> はまだやらないで。
```

範囲は「ファイル」と「Step」で切ると失敗しません。

### 対比2: エラーで困ったとき

| | プロンプト |
|---|---|
| 悪い | 「テストが落ちる、直して」 |
| 良い | 「このテストの**最初のエラーだけ**を見て、原因の候補を挙げて。まだ直さないで」 |

**なぜ悪いのか**: 「直して」と言うと、AI は**落ちているテストを通すこと**を目的にします。
いちばん速く通す方法は、テストのほうを書き換えることです。
気づかないうちに `expect` が緩められ、仕様が消えます。

エラーが10件出ていても、原因はたいてい1つです。
2件目以降は1件目の影響なので、**最初の1件だけ**を見せてください。`/stuck` はこれを自動でやってくれます。

```text
/stuck テストが3件落ちていて、原因が分からない
```

### 対比3: 仕上げのとき

| | プロンプト |
|---|---|
| 悪い | 「もっと良くして」 |
| 良い | 「必須要件はすべて終わったので、`README.md` の実装メモを書いて。採用したルールと、採用しなかったルールを書き分けて」 |

**なぜ悪いのか**: 「良く」の基準が無いので、AI は**自分の基準**で良くします。
アニメーションが増え、ローカルルールが増え、リファクタリングが始まり、
さっきまで緑だった `npm run verify` が赤くなります。研修の残り時間は戻ってきません。

**仕上げでやることは決まっています。** 迷ったらこの3つだけ頼んでください。

- `README.md` の「遊び方 / 採用したルール / 実装メモ」を埋める
- `index.ts` の `status` を `"ready"` にする（`npm run verify` が緑のときだけ）
- `/pr` で Pull Request の本文を作る

### 対比4: 範囲を切る（**今日いちばん効くのはこれです**）

| | プロンプト |
|---|---|
| 悪い | 「直しておいて」 |
| 良い | 「`logic.ts` だけ直して。画面（`.tsx`）は触らないで」 |

| | プロンプト |
|---|---|
| 悪い | 「テストを足して」 |
| 良い | 「`logic.test.ts` に `it("判定中にもう一度クリックしても手数が増えない")` を1件だけ足して。`logic.ts` は変えないで。まず赤くなることを見せて」 |

| | プロンプト |
|---|---|
| 悪い | 「レビューして、コメントも入れておいて」 |
| 良い | 「差分を読んで指摘案を出して。**投稿はしないで。** 私が GitHub の画面から自分で投稿します」 |

| | プロンプト |
|---|---|
| 悪い | 「PR を出しておいて」 |
| 良い | 「`.pr-body.md` に本文の下書きだけ書いて。**push も `gh pr create` もしないで。**「レビューしてほしい点」は空欄のまま残して」 |

**なぜ悪いのか**: 「直しておいて」には**どこまで**が入っていません。
AI は親切なので、ついでに画面も直し、ついでに関数名も変え、ついでにテストも書き換えます。
そして**差分が200行になった時点で、あなたはもうそれを読みません。**

範囲を切る言葉は、この4つを覚えれば足ります。

| 切り方 | 言い方 |
|---|---|
| **ファイルで切る** | 「`logic.ts` と `logic.test.ts` だけ」 |
| **やらないことを言う** | 「画面は触らないで」「実装は変えないで」 |
| **止める場所を言う** | 「まだ直さないで」「計画だけ出して止まって」 |
| **投稿させない** | 「投稿はしないで」「push はしないで」 |

**範囲を切るのは、AI を疑っているからではありません。あなたが読める大きさに保つためです。**

### 対比5: Claude Code にできないことを頼まない

| | プロンプト |
|---|---|
| 悪い | 「`npm run dev` を起動して、画面を確認して」 |
| 良い | 「実装が終わったら、私がターミナルB のブラウザで確認します。**確認すべき操作を3〜5ステップで**書き出して」 |

| | プロンプト |
|---|---|
| 悪い | 「レビューコメントを投稿しておいて」 |
| 良い | 「投稿用の文章を作って。私が実機で確認できたのは次の3つです（…）。それ以外には『未確認』と明記して」 |

**なぜ悪いのか**: どちらもハーネスが拒否します。頼んだ時間がそのまま失われます。
そして、もっと大事なことがあります。
**この2つは、代わりにやってもらった時点で、確認したことにならない作業だからです。**

## 人間が確認する4フェーズ

AI に任せてよい作業と、人間がやらなければならない確認は別物です。
次の4回だけは、必ず自分の目で見てください。1回あたり2〜5分で終わります。
**印のある項目は、ターミナルB でしかできません。**

### フェーズ1: 計画（`/kickoff` の直後）

- [ ] Issue（`docs/games/<ゲームID>.md`）の**必須要件と計画が1対1で対応**しているか
- [ ] ルールの解釈が正典と食い違っていないか（「たぶんこうだろう」で足されたルールが無いか）
- [ ] テストの一覧が**正常系だけに偏っていないか**（境界値・やってはいけない操作があるか）
- [ ] 担当フォルダ `src/games/<自分のゲームID>/` の外を触る計画になっていないか
- [ ] `logic.ts` に `reduce` と `pendingDelayMs` が置かれているか（時間と乱数が画面側に漏れていないか）

**1つでも「いいえ」があれば、`/implement` に進まずに計画を直させてください。**

### フェーズ2: 実装後（`/implement` の直後）

- [ ] `npm run verify` が**緑**（AI の「できました」ではなく、自分の画面で緑を見る）
- [ ] **【B】** ブラウザを F5 で再読み込みして、**最初から最後まで1回プレイ**した
- [ ] **【B】** リセットして2回目が正しく始まった
- [ ] **【B】** 遊ぶ前に自分で書いた「壊し方3つ」を試した（連打 / 出せないカード / 0枚のとき）
- [ ] `logic.test.ts` の `it("...")` を上から読んで、仕様が言葉になっている
- [ ] **【B】** アサーションを1つ逆にして**赤くなることを確認**し、元に戻した（**A には打たない**）
- [ ] `git status` で、変更が担当フォルダの中だけに収まっている

### フェーズ3: Pull Request を出す前（`/pr` の前後）

- [ ] `/handoff` を打ち、10行から**事実と違う行を1つ**見つけた
- [ ] `npm run verify` が緑（`/pr` は緑でなければそこで止まります）
- [ ] `.pr-body.md` の「**レビューしてほしい点**」を**自分の言葉で**書いた
      （「勝敗判定を見てください」ではなく「同じ数字が出たときの処理が怪しいので、そこを重点的に」）
      **ここはレビュアーが具体性を検問する場所です。テンプレのままだと指摘されます**
- [ ] 「採用したルール」に、**採用しなかったもの**まで書いてある
- [ ] 「発展課題・未対応事項」に、できていないことを正直に書いた
- [ ] **【B】** スクリーンショットを撮った（`Win + Shift + S`。画像は**コミットせず** PR 本文にドラッグ&ドロップ）

**push と PR 操作は、ターミナルB で自分の手で打ちます。**

```powershell
# ターミナルB
git push -u origin HEAD
gh pr edit <自分のPR番号> --body-file .pr-body.md
gh pr checks
gh pr ready
```

（Step 6 でまだ Draft を作っていない場合だけ
`gh pr create --draft --title "<ゲーム名>を実装" --body-file .pr-body.md` を使います）

CI が緑になってから `gh pr ready` で Draft を外します。
**遊んでいないもの、`verify` が緑でないものを ready にしないでください。**

### フェーズ4: レビュー時（`/review` と `/fix-review`）

**レビューする側**

- [ ] **【B】** `gh pr checkout <相手のPR番号>` してブラウザを F5 で再読み込みし、**実際に遊んだ**（差分を眺めるだけは無効）
- [ ] `docs/games/<相手のゲームID>.md` の「レビュアー向けミッション」を**原文のまま引用させ、手で書き写した**
- [ ] 指摘のそれぞれについて「自分が実機で確認できたか / 未確認か」を区別した
- [ ] **相手の PR の「レビューしてほしい点」が具体的か確かめた。テンプレのままなら、それ自体を指摘した**
- [ ] **【B】** 投稿する文章を**自分で読み直してから**、GitHub の画面で投稿した（AI の下書きをそのまま貼らない）

**指摘を受けた側**

- [ ] `/fix-review` が出した「直す / 相談 / 直さない」の分類に、**自分が納得している**
- [ ] 直したあと `npm run verify` を回し直した
- [ ] **【B】** 指摘された操作を、ブラウザでもう一度やって直ったことを見た
- [ ] **【B】** 指摘1件ずつに返信した（直しただけで黙っているのが、レビュアーをいちばん困らせます）

詳しくは `docs/review-guide.md` を見てください。

## AI が間違えやすいところ（研修で実際に起きます）

### 1. 担当範囲外を「ついでに直す」

`src/core/` の型が気に入らない、`src/components/Card` にプロパティを足したい ——
AI は**親切心で**共通基盤に手を伸ばします。

- **どうなるか**: フック（`.claude/hooks/guard-scope.mjs`）がその場で止めます。
  すり抜けても `npm run scope` が赤くなり、pre-commit でコミットできず、CI でマージできません。
- **見つけ方**: `git status` を見る。担当フォルダ以外の行があれば、そこが事故です。
- **戻し方**: `npm run scope` が出す `git restore ...` をそのまま実行してください。

```powershell
npm run scope
git status
```

**レビュー中は、これがもう1段きつくなります。** `gh pr checkout` で相手のブランチにいる間、
`.claude/.state/owner.json` に記録された自分の担当と突き合わせるので、
**相手のコードを編集しようとすると止まります。** 気づいたことは直さず、コメントで伝えてください。

### 2. 「動きました」と言うが `npm run verify` を通していない

`npm test` だけ通して「完成しました」と報告してくることがあります。
`npm run verify` は **範囲チェック → lint → 型 → テスト → ビルド** の5つで、CI とまったく同じ内容です。

- **どうなるか**: PR を出してから CI が赤くなり、レビュアーを待たせます。
- **対処**: 報告を受けたら、必ず**自分で**打ってください。

```powershell
npm run verify
```

作業を終えようとしたときに `verify` を通していないと、Stop フックが1回だけ引き止めます。
ただし2回目は通るようになっているので、「止められないから大丈夫」ではありません。

### 3. テストが正常系だけになる

AI に「テストを書いて」と頼むと、**動く経路のテスト**を書きます。
ゲームが壊れるのは、動く経路ではなく境界です。

- **不足しがちなもの**: 同じ数字 / 最後の1枚 / 0枚 / 判定中の二重クリック / 出せないカードを出す
- **頼み方**: 「テストを足して」ではなく、**テスト名を指定して**頼みます。

```text
it("判定中にもう一度クリックしても手数が増えない") を logic.test.ts に足してください。
実装（logic.ts）は変えないでください。まず赤くなることを見せてください。
```

### 4. Issue に書かれていないローカルルールを勝手に足す

トランプゲームは家庭ごとにルールが違います。
AI は学習した「一般的なルール」を知っているので、頼まなくても**縛り**や**追加の役**を足しがちです。

- **正しい判断**: `docs/games/<ゲームID>.md` が**正典**です。**そこに無いことは実装しません。**
- **見つけ方**: `/verify` が作る「必須要件 → 実装 → テスト」の対応表に、**Issue に無い行**が出ていないか見る。
- **言い方**:

```text
正典に無いルールを実装していないか、docs/games/<ゲームID>.md と突き合わせて表にしてください。
正典に無いものが見つかったら、消す前に一覧で見せてください。
```

余計なルールは、レビュアーを混乱させ、CPU のバグを増やし、時間を奪います。
**足すのではなく、必須要件を先に終わらせてください。**

### 5. 実行できないコマンドを、言い方を変えて何度も試す

`npm run dev` を拒否されると、AI は `npx vite` を試し、次に `vite` を試し、
次に「バックグラウンドで起動しましょうか」と言い出します。**全部止まります。**

- **どうなるか**: 3分から5分が消えます。ゲームは1行も進みません。
- **対処**: 拒否メッセージが出たら、**その時点であなたが引き取ってください。**

```text
それは実行できない決まりになっています。別の方法を探さないでください。
画面の確認は私がターミナルB でやります。確認すべき操作を3〜5ステップで書き出してください。
```

---

## 止められたときは、回避策を探させない

ハーネスに止められると、AI は**善意で回り込もうとします。**
`sed -i` で書く、リダイレクト（`>`）で上書きする、`cp` で置き換える、
`git commit --no-verify` を使う、`.claude/settings.json` を書き換える ——
これらは全部ふさいであります（`.claude/hooks/guard-bash.mjs`）。

**止められたのは、あなたが悪いからではありません。**
「共通基盤に手を入れないと解けない」と感じた時点で、たいていは**設計の勘違い**か、
本当に運営が直すべきことのどちらかです。どちらも参加者が直すものではありません。

止められたら、AI にこう言ってください。

```text
回避策は探さないでください。
CLAUDE.md と docs/harness.md を読んで、なぜ止められたのかを説明してください。
そのうえで、src/games/<自分のゲームID>/ の中だけで実現する案があるかを教えてください。
別のコマンドで同じことをやり直すのはやめてください。
```

そのうえで、**手を止めて講師に相談**します。相談するときはこの形で伝えてください
（フックの拒否メッセージも、同じ形で報告するように AI に指示しています）。

```text
- やりたいこと:
- 足りないと思うもの:
- ゲーム側だけで実現する案（あれば）:
```

読むもの:

- `CLAUDE.md` … 絶対に守る5条
- `docs/harness.md` … 何が、どの層で、なぜ止まるのか
- `docs/troubleshooting.md` … よくあるエラーと対処

## まとめ — 誰がやるか

| やること | 担当 |
|---|---|
| Issue を読んで計画を立てる | Claude Code（`/kickoff`） |
| 計画が正しいか決める | **人間** |
| テストとロジックを書く | Claude Code（`/implement`） |
| **開発サーバーを起動する** | **人間**（ターミナルB。A では実行できません） |
| 実機で遊ぶ | **人間**（ターミナルB） |
| 遊ぶ前に「壊し方」を3つ書き出す | **人間**（自分の手で。Claude に考えさせない） |
| テスト名を読み、1つ逆にして赤を見る | **人間**（ターミナルB とエディタだけ。A には打たない） |
| `npm run verify` を回す | どちらでもよい（結果は**人間**が見る） |
| PR 本文の下書き | Claude Code（`/pr`） |
| 「レビューしてほしい点」を書く | **人間** |
| **PR とレビューを投稿する** | **人間**（GitHub の画面から。A では実行できません） |
| **Issue のチェックを付ける** | **人間**（GitHub の Issue 画面でクリック。`gh issue edit` は止まります） |
| 相手の「レビューしてほしい点」を検問する | **人間**（レビュアー） |
| 引き継ぎメモの10行から、事実と違う行を探す | **人間**（`/handoff` の本体） |
| 止められたときの判断 | **人間**（そして講師） |

右の列が **人間** の行は、ほとんどが**ターミナルB でしかできない作業**です。これは偶然ではありません。
**確認を「気をつけること」ではなく「別の場所でやること」にしてある**からです。

**AI が速いぶんだけ、人間は確かめる時間を持てる。**
これがこの研修でいちばん持ち帰ってほしいことです。
