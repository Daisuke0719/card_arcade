# Claude Code を使った作業の進め方

Claude Code は、指示に基づいて調査や実装を行う開発支援ツールです。
指示が曖昧な場合は、想定より広い範囲を変更することがあります。

この文書では、依頼する作業範囲、実装結果の確認方法、提出前の確認事項を説明します。
リポジトリの規則は `CLAUDE.md`、操作が拒否される条件は `docs/harness.md`、エラーへの対処方法は `docs/troubleshooting.md` を参照してください。

---

## 2つのターミナルを使い分ける

研修では、2つのターミナルを使い分けます。

|                      | ターミナルA（Claude Code）                 | ターミナルB（参加者が操作）                     |
| -------------------- | ------------------------------------------ | ----------------------------------------------- |
| 使用するもの         | Claude Code のセッション                   | PowerShell                                      |
| 継続して実行するもの | —                                          | `npm run dev`（研修中は起動したままにする）     |
| 操作                 | 調査、実装の依頼、差分の確認、文章の下書き | ブラウザでの動作確認、`npm test`、`gh pr ready` |
| 入力するもの         | プロンプト（日本語）                       | コマンド（PowerShell）                          |

### ターミナルを分ける理由

Claude Code へ依頼する作業と、参加者が結果を確認する作業を区別するためです。ターミナルBでは、ブラウザの表示や GitHub の状態を確認します。また、ターミナルAからの実行を禁止している操作も、ターミナルBで行います。

### ターミナルBで開発サーバーを起動する

```powershell
cd $HOME/dev/card_arcade
npm run dev
```

ブラウザで `http://localhost:5173/` を開きます。開発サーバーは、研修が終わるまで起動したままにします。
コードを変更した場合は、ブラウザを `F5` キーで再読み込みしてください。開発サーバーの再起動は不要です。

研修が終わったら、`Ctrl + C` で開発サーバーを停止します。

### ターミナルAでは `npm run dev` を実行できない

ターミナルAで `npm run dev` を実行すると、ハーネスによって拒否されます。

```text
npm run dev は Claude Code からは実行できません。
起動したままになるので、このセッションが返ってこなくなります。
```

別のコマンドで開発サーバーを起動しようとせず、ターミナルBで `npm run dev` を実行してください。

## Claude Code から実行できないコマンド

ターミナルAでは実行が拒否されるコマンドを次に示します。

| コマンド                                                                  | 拒否する理由                                                                         | 対処方法                                                                            |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| `npm run dev` / `npm run preview`                                         | 処理が終了せず、ターミナルBの開発サーバーと5173番ポートが競合する                    | ターミナルBで起動する。すでに起動している場合はブラウザを `F5` キーで再読み込みする |
| `npm run test:watch` / `npm test -- --watch` / `npx vitest`（`run` なし） | 監視モードが終了しない                                                               | `npm test`（`vitest run`）を使う。監視モードが必要な場合はターミナルBで実行する     |
| `gh pr review` / `gh pr comment` / `gh issue comment`                     | Pull Request や Issue へ投稿する操作である                                           | Claude Code には下書きの作成だけを依頼し、参加者が GitHub 上で投稿する              |
| `gh api`                                                                  | 操作内容を事前に判定できない（作業ブランチの場合のみ拒否する）                       | 実行したい操作を講師に説明し、対応を確認する                                        |
| `node scripts/setup-github.mjs` / `node scripts/build-issue-bodies.mjs`   | 9名分の Issue をまとめて変更する講師用の操作である（作業ブランチの場合のみ拒否する） | 参加者は実行しない                                                                  |
| `npm run scaffold -- --all` / `--force`                                   | 9名分の雛形をまとめて上書きする講師用の操作である（作業ブランチの場合のみ拒否する）  | `npm run scaffold -- --game <自分のゲームID>` を使う                                |
| `gh issue edit`                                                           | Issue 本文を変更する（作業ブランチの場合のみ拒否する）                               | チェックボックスは、参加者が GitHub の Issue 画面で操作する                         |
| `npm install` / `yarn add` などの依存追加                                 | `package-lock.json` の変更が、ほかの参加者の Pull Request と競合する                 | 既存の `@core` と `@ui` を使用する。不足がある場合は講師に相談する                  |
| `git push --force` / `git commit --no-verify` / `main` への push          | 履歴を書き換えたり、検証を省略したりする                                             | 修正は新しいコミットとして追加する                                                  |

### 承認を求められるもの（`ask`）

実行前に、参加者へ承認を求める画面が表示されます。

```text
git push / gh pr create / gh pr merge / gh pr ready / gh pr edit / gh issue create
```

これらのコマンドは承認画面から実行せず、参加者がターミナルBで実行します。リモートリポジトリの状態を変更する操作や、ほかの利用者に公開される操作が含まれるためです。
`gh pr ready` を実行すると、Pull Request は提出済みとして扱われます。

### 承認なしで実行できるコマンド（`allow`）

```text
npm test / npm run verify / npm run build / npm run scaffold -- --game <ゲームID>
git switch / git add / git commit / git status / git diff / git pull
gh pr checkout / gh pr view / gh pr checks / gh pr diff
node -v / gh auth status
```

承認なしで実行できる理由は、`docs/harness.md` の「承認なしで実行できるコマンド」で説明しています。リモートリポジトリや担当範囲外へ影響しない操作は、承認の対象から除外しています。

## 作業時に確認する3つの原則

### 原則1: 実装計画を先に確認する

実装を依頼する前に、変更内容の計画作成を依頼します。

```text
GitHub の Issue #<Issue番号> と docs/games/<ゲームID>.md を読んで、
src/games/<ゲームID>/ にこのゲームをどう実装するか計画を立ててください。

- Issue にも docs/games/<ゲームID>.md にも書かれていないルールは足さないでください。
- まだコードは書かないでください。ファイルも変更しないでください。
```

計画を確認する前に実装が始まらないよう、「まだコードは書かないでください」という指示を残します。

作成された計画を、Issue の必須要件と上から1件ずつ照合します。対応する項目が見つからない場合は、次のプロンプトを入力します。

```text
必須要件の「<Issue の要件の文言をそのまま貼る>」に対応する項目が計画にありません。
どの項目で実現するか分かるように、計画へ追記してください。まだ実装はしないでください。
```

```text
計画の「<計画の中の1行をそのまま貼る>」は、Issue にも docs/games/<ゲームID>.md にも書かれていないルールです。
実装対象ではないため、計画から外してください。まだ実装はしないでください。
```

計画と要件が一致していないと、実装後に修正が必要になります。計画を確認し、必要な修正を反映してから実装を依頼してください。

### 原則2: 実装結果は参加者がブラウザで確認する

実装後は、操作方法やゲームの進行をブラウザで確認します。ターミナルBの開発サーバーは起動したままにし、ブラウザを `F5` キーで再読み込みしてから1回遊んでください。

```powershell
# ターミナルB（止まっていたときだけ）
npm run dev
```

- 最初から最後まで1回遊ぶ
- リセット後に、2回目のゲームが正しい初期状態で始まるか確認する
- 無効になるべき操作を試す（判定中の連打、出せないカードのクリック、山札が0枚のときのドロー）

`npm run verify` が成功しても、操作や進行に問題が残ることがあります。テストで確認できるのは、定義した条件だけだからです。
ブラウザでの動作確認は参加者が行い、開発サーバーはターミナルBで起動します。テストが成功していても、画面を操作できない、ゲームが終了しないといった問題が残ることがあるため、実際の操作結果も確認してください。

### 原則3: 実装と同時にテストを作成する

`logic.ts` に関数を追加するときは、対応するテストも `logic.test.ts` に作成するよう依頼します。実装と同時に作成することで、提出時のテスト不足を防ぎます。

```text
logic.ts に関数を足したら、logic.test.ts にその関数のテストも書いてください。合計3件以上にしてください。
```

`status` を `"ready"` にするゲームには、`logic.test.ts` に `it(` が**3件以上**必要です。
3件未満の場合は契約テストが失敗し、CIも成功しません。必要な件数は `harness/config.json` の `minTestsPerReadyGame` で定義されており、`it.skip` は件数に含まれません。

テストの作成後に `logic.test.ts` を開き、`it("...")` のテスト名を上から確認します。サンプル（`src/games/example-game/logic.test.ts`）では、次のような名前を使用しています。

```
it("同じランクは引き分け")
it("判定中にもう一度予想しても状態が変わらない（連打で先に進めない）")
it("山札が空なら予想した時点で終了する")
it("判定待ちでないときの tick は無視される")
it("同じ seed なら同じ展開になる（テストが安定する）")
```

テスト名から検証内容を判断できない場合は、内容を確認して名前の修正を依頼します。

```text
テスト名の「<読んで分からなかった名前をそのまま貼る>」は、何を確認しているのかが名前から分かりません。
このテストが何を確認しているのかを説明したうえで、名前を分かる形に直してください。実装は変えないでください。
```

## よく使うプロンプトの型

場面ごとの依頼内容と、プロンプトに残す必要がある指示を次の表に示します。コピーして使えるプロンプトは `docs/handson-steps.md` を参照してください。

| 場面               | 依頼する内容                                                    | 残す必要がある文言                                                   |
| ------------------ | --------------------------------------------------------------- | -------------------------------------------------------------------- |
| 実装を始める前     | Issue とルール文書を読み、実装計画を作成する                    | 「まだコードは書かないでください」                                   |
| 実装               | まず最後まで遊べる状態まで実装する                              | 「`src/games/<ゲームID>/` の中だけ」「`npm run dev` は実行しないで」 |
| 遊んで直す         | プランモード（`/plan`）で原因と改善策を整理し、確認後に実行する | 「まだファイルは変更しないでください」                               |
| 提出前             | `npm run verify` を実行し、必須要件との対応表を作成する         | 「満たせていない要件は未達と書いて」                                 |
| Pull Request       | `.pr-body.md` に本文の作成を依頼する                            | 「`gh pr create` も `git push` も実行しないで」                      |
| 状況の共有         | 現在の状況を10行以内にまとめる                                  | 「推測で書かないでください」                                         |
| 問題が発生したとき | 事実を確認し、次に試すことを1つ挙げてもらう                     | 「コードは変更しないでください」                                     |

### 現在の状況を10行以内で整理する

作業を中断するときや講師に相談するときは、現在の状態を次の形式で整理します。

```text
現在の状況を10行以内でまとめてください。次の5点を含めます。

- いま何をしているか
- 直前に終わったこと
- まだ終わっていないこと
- 次に行うこと
- 気をつけること

先に git branch --show-current / git status --short / npm run scope を実行し、
その結果にもとづいて書いてください。推測で書かないでください。コードは変更しないでください。
```

未確認の内容が含まれないよう、「推測で書かないでください」という指示を残します。作成された内容は、`git status --short` と `npm test` の結果に照らして確認してください。

> `.claude/commands/` にある以前の版のスラッシュコマンドは、当日の手順では使用しません。この文書に記載したプロンプトを使用してください。

## プロンプトの比較

### 対比1: 実装を依頼するとき

|        | プロンプト                                                                                         |
| ------ | -------------------------------------------------------------------------------------------------- |
| 曖昧   | 「<ゲーム名>を作って」                                                                             |
| 具体的 | 「合意した方針どおりに、`src/games/<ゲームID>/` の中だけを実装して。ほかのファイルは変更しないで」 |

対象範囲を指定しないと、依頼していないルールや CPU の処理まで実装されることがあります。差分が広がるほど、内容の確認や修正に時間がかかります。

対象範囲を明示する場合は、次の形式を使用します。

```text
<ルール文書の場所> の <どの部分> だけを、<どのファイル> に実装して。
<やらないこと> はまだやらないで。
```

対象のフォルダとファイルを指定し、変更範囲を限定します。

### 対比2: エラーで困ったとき

|        | プロンプト                                                                 |
| ------ | -------------------------------------------------------------------------- |
| 曖昧   | 「テストが失敗するので、直して」                                           |
| 具体的 | 「このテストの最初のエラーだけを見て、原因の候補を挙げて。まだ直さないで」 |

修正対象を指定しないと、実装ではなくテストの期待値が変更され、仕様を検証できなくなることがあります。

複数のエラーが同じ原因から発生している場合があります。まず最初のエラーを確認し、原因を切り分けます。

```text
テストが3件失敗していて、原因が分かりません。
npm test を実行して、最初のエラーだけを引用してください。
そのうえで docs/troubleshooting.md と照らし合わせ、次に試すことを1つだけ挙げてください。

コードは変更しないでください。
```

### 対比3: 仕上げのとき

|        | プロンプト                                                                                                       |
| ------ | ---------------------------------------------------------------------------------------------------------------- |
| 曖昧   | 「もっと良くして」                                                                                               |
| 具体的 | 「必須要件はすべて終わったので、`README.md` に遊び方と採用したルールを書いて。採用しなかったルールも書き分けて」 |

「良く」の基準がないため、アニメーション、独自ルール、リファクタリングなど、依頼していない変更が加わることがあります。仕上げとして必要な内容を具体的に指定してください。

仕上げでは、次の3点を確認します。

- `README.md` の「遊び方 / 採用したルール」を埋める
- `index.ts` の `status` を `"ready"` にする（`npm run verify` が成功したときだけ）
- `.pr-body.md` に Pull Request の本文を書く（`gh pr create` は実行しない）

### 対比4: 対象範囲を指定する

|        | プロンプト                                              |
| ------ | ------------------------------------------------------- |
| 曖昧   | 「直しておいて」                                        |
| 具体的 | 「`logic.ts` だけ直して。画面（`.tsx`）は変更しないで」 |

|        | プロンプト                                                                                                                                     |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 曖昧   | 「テストを足して」                                                                                                                             |
| 具体的 | 「`logic.test.ts` に `it("判定中にもう一度クリックしても手数が増えない")` を1件だけ足して。`logic.ts` は変えないで。まず失敗することを見せて」 |

|        | プロンプト                                                                                 |
| ------ | ------------------------------------------------------------------------------------------ |
| 曖昧   | 「PR を出しておいて」                                                                      |
| 具体的 | 「`.pr-body.md` に本文の下書きだけ書いて。`gh pr ready` はしないで。私が自分で入力します」 |

「直しておいて」だけでは対象範囲が分かりません。画面、関数名、テストなど、意図していない箇所まで変更される可能性があるため、変更するファイルと変更しないファイルを指定します。

変更範囲は、次の4つの観点で指定できます。

| 観点             | 指示の例                                       |
| ---------------- | ---------------------------------------------- |
| 対象ファイル     | 「`logic.ts` と `logic.test.ts` だけ」         |
| 対象外の作業     | 「画面は変更しないで」「実装は変えないで」     |
| 作業を止める時点 | 「まだ直さないで」「計画だけ作成して止まって」 |
| 外部への操作     | 「投稿はしないで」「push はしないで」          |

対象範囲を指定するのは、変更内容を確認できる大きさに保つためです。

### 対比5: 実行できない操作を依頼しない

|        | プロンプト                                                                                            |
| ------ | ----------------------------------------------------------------------------------------------------- |
| 曖昧   | 「`npm run dev` を起動して、画面を確認して」                                                          |
| 具体的 | 「実装が終わったら、私がターミナルBのブラウザで確認します。確認すべき操作を3〜5ステップで書き出して」 |

`npm run dev` はハーネスによって拒否されます。また、画面の表示と操作結果は参加者がブラウザで確認します。

## 参加者が確認する3つの場面

Claude Code へ依頼する作業と、参加者が行う確認を分けます。次の3つの時点で、実際の状態を確認してください。【B】と記載した項目は、ターミナルBで行います。

### 1. 実装の計画を読んだとき

- [ ] Issue と `docs/games/<ゲームID>.md` の必須要件に、計画の項目が対応しているか
- [ ] ルールの解釈がルール文書と食い違っていないか（推測で足されたルールが無いか）
- [ ] 担当フォルダ `src/games/<自分のゲームID>/` の外を変更する計画になっていないか
- [ ] ルールを `logic.ts` に置き、時間と乱数を画面側に漏らさない形になっているか

対応していない項目がある場合は、実装を依頼する前に計画を修正します。

### 2. 実装が終わったと報告されたとき

- [ ] `npm run verify` の実行結果が成功している
- [ ] 【B】ブラウザを `F5` で再読み込みし、最初から最後まで1回遊んだ
- [ ] 【B】リセット後に2回目のゲームが正しい初期状態で始まった
- [ ] 【B】無効になるべき操作を試した（連打、出せないカード、山札が0枚のときのドロー）
- [ ] `logic.test.ts` の `it("...")` を上から読んで、何を確かめているか分かる
- [ ] `logic.test.ts` に `it(` が3件以上ある
- [ ] `git status` で、変更が担当フォルダの中だけに収まっている

### 3. Pull Request を提出する前

- [ ] `npm run verify` が成功する
- [ ] `README.md` で、採用したルールと採用しなかったルールが区別されている
- [ ] 「発展課題・未対応事項」に、できていないことを正直に書いた

push と Pull Request の操作は、参加者がターミナルBで実行します。

```powershell
# ターミナルB
git push -u origin HEAD
gh pr edit <自分のPR番号> --body-file .pr-body.md
gh pr checks
gh pr ready
```

Draftをまだ作成していない場合に限り、`gh pr create --draft --title "<ゲーム名>を実装" --body-file .pr-body.md` を使用します。

CI が成功してから、`gh pr ready` で Draft 状態を解除します。ブラウザでの動作確認と `verify` が終わっていない場合は、Draft のままにしてください。

## 作業中に起こりやすい問題

### 1. 担当範囲外のファイルが変更される

指示の対象範囲が曖昧だと、`src/core/` の型や `src/components/Card` など、共通基盤まで変更されることがあります。

- **検出時の動作**: `.claude/hooks/guard-scope.mjs` が変更を拒否します。フックで検出されなかった場合も、`npm run scope`、pre-commit、CI の各段階で失敗します。
- **確認方法**: `git status` を実行します。担当フォルダ以外のファイルが表示された場合は、範囲外の変更です。
- **戻し方**: `npm run scope` の出力に示された `git restore ...` を実行します。

```powershell
npm run scope
git status
```

ほかの参加者のブランチへ切り替わっていた場合も、`.claude/.state/owner.json` に記録された担当情報との照合により、担当外のコードは変更できません。

### 2. `npm run verify` が実行されていない

`npm test` だけでは、範囲チェック、lint、型チェック、ビルドを確認できません。`npm run verify` では、これらをテストとあわせて実行します。検証内容は CI と同じです。

- **影響**: Pull Request の作成後に CI が失敗し、追加の修正が必要になります。
- **対処**: 提出前に、参加者がターミナルBで実行します。

```powershell
npm run verify
```

`verify` を実行せずに作業を終了しようとすると、Stopフックが初回の終了を拒否します。2回目の終了は拒否しないため、フックの有無にかかわらず、提出前に実行結果を確認してください。

### 3. テストが正常系だけになる

テスト条件を指定せずに依頼すると、正常系のテストだけが作成されることがあります。
同値、最後の1枚、0枚、判定中の再操作など、境界条件も明示して依頼してください。

- **確認する境界条件**: 同じ数字、最後の1枚、0枚、判定中の二重クリック、出せないカードの選択
- **依頼方法**: 「テストを追加して」だけでなく、確認する条件をテスト名として指定します。

```text
it("判定中にもう一度クリックしても手数が増えない") を logic.test.ts に足してください。
実装（logic.ts）は変えないでください。まず失敗することを見せてください。
```

### 4. Issue に書かれていない独自ルールを追加する

トランプゲームは家庭ごとにルールが違います。
依頼内容によっては、文書にない一般的なルールや追加の役が実装されることがあります。

- **判断基準**: `docs/games/<ゲームID>.md` に記載されていないルールは実装しません。
- **確認方法**: 提出前に「必須要件 → 実装 → テスト」の対応表を作成し、Issueにない項目が含まれていないか確認する。
- **依頼方法**:

```text
ルール文書にないルールを実装していないか、docs/games/<ゲームID>.md と照合して表にしてください。
ルール文書にないものが見つかったら、削除する前に一覧で表示してください。
```

文書にないルールを追加すると、CPU の処理やテストにも変更が必要になります。まず必須要件を実装し、追加機能は発展課題として扱ってください。

### 5. 拒否された操作を別のコマンドで再実行する

`npm run dev` が拒否されたあとに、`npx vite` や `vite` など、同じ目的のコマンドが提案されることがあります。
これらのコマンドも拒否されるため、実行しないでください。

- **影響**: 拒否されるコマンドを繰り返し実行することになります。
- **対処**: 拒否メッセージを確認し、必要な操作をターミナルBで実行します。

```text
それは実行できない決まりになっています。別の方法を探さないでください。
画面は私がターミナルBで確認します。確認すべき操作を3〜5ステップで書き出してください。
```

## 操作が拒否された場合の対応

ハーネスに拒否された操作を、別のコマンドで実行しないでください。`sed -i`、リダイレクト（`>`）、`cp`、`git commit --no-verify`、`.claude/settings.json` の変更も、`.claude/hooks/guard-bash.mjs` で拒否されます。

操作が拒否された場合は、設計の前提に誤りがあるか、運営による共通基盤の変更が必要な可能性があります。どちらの場合も、参加者だけで変更を進めず、講師に相談してください。

操作が拒否された場合は、Claude Code に次のように伝えてください。

```text
回避策は探さないでください。
CLAUDE.md と docs/harness.md を読んで、操作が拒否された理由を説明してください。
そのうえで、src/games/<自分のゲームID>/ の中だけで実現する案があるかを教えてください。
別のコマンドで同じことをやり直すのはやめてください。
```

解決できない場合は変更を中断し、次の形式で講師に相談します。フックの拒否メッセージも、この形式で報告するように設定されています。

```text
- やりたいこと:
- 足りないと思うもの:
- ゲーム側だけで実現する案（あれば）:
```

関連文書:

- `CLAUDE.md`: 必須ルール5項目
- `docs/harness.md`: 各処理で操作を拒否する条件
- `docs/troubleshooting.md`: よくあるエラーと対処方法

## 作業ごとの担当

| 作業                                                   | 担当                                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------------------ |
| Issue を読んで実装の計画を立てる                       | Claude Code                                                              |
| 計画が要件に合っているか判断する                       | 参加者                                                                   |
| ロジックと画面とテストを書く                           | Claude Code                                                              |
| 開発サーバーを起動する                                 | 参加者（ターミナルB。Aでは実行できません）                               |
| ブラウザでプレイする                                   | 参加者（ターミナルB）                                                    |
| テスト名を読み、検証内容を判断する                     | 参加者                                                                   |
| プレイ中に見つけた不具合を、再現手順つきで伝える       | 参加者（ターミナルBで操作してから）                                      |
| `npm run verify` を実行する                            | どちらでもよい（結果は参加者が確認する）                                 |
| PR 本文の下書き                                        | Claude Code（`.pr-body.md` への作成を依頼する）                          |
| PR を Ready for review にする                          | 参加者（ターミナルBで `gh pr ready`。Aでは承認を求められます）           |
| マージする                                             | 講師                                                                     |
| Issue のチェックを付ける                               | 参加者（GitHub の Issue 画面で操作する。`gh issue edit` は拒否されます） |
| 10行に整理した内容が、実際の状態と合っているか確認する | 参加者                                                                   |
| 操作が拒否された場合の判断                             | 参加者（必要に応じて講師に相談）                                         |

右の列が参加者となっている操作は、主にターミナルBで行います。
操作する場所を分けることで、確認や承認を省略しにくくしています。

Claude Code に作業を依頼した場合も、結果の確認と提出の判断は参加者が行います。
