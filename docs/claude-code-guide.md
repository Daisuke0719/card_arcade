# Claude Code の使い方 — 丸投げではなく「速く正確な同僚」として

Claude Code は魔法の箱ではありません。
**とても速く、とても正確で、しかし放っておくと自分の担当範囲と目的を勝手に広げてしまう同僚**です。

同僚に仕事を頼むときと同じことをすれば、それでうまくいきます。

1. **何をするかを先に握る**
2. **上がってきたものを自分で確かめる**
3. **責任は頼んだ側が持つ**

この文書は、その3つを180分の研修の中で回すための手順書です。
リポジトリの決まりは `CLAUDE.md`、止められたときの仕組みは `docs/harness.md`、
エラーの直し方は `docs/troubleshooting.md` を見てください。

---

## 3原則

### 原則1: 計画を先に出させる

いきなり「作って」と言わないでください。最初は必ず `/kickoff <Issue番号>` です。

```
/kickoff 1
```

`/kickoff` は **コードを1行も変更できないようになっています**。
コマンドの定義（`.claude/commands/kickoff.md`）に `disallowed-tools: Edit, Write, NotebookEdit` と書いてあり、
このコマンドの間だけ編集ツールそのものが取り上げられます。
だから安心して「まず考えさせる」ことができます。

`/kickoff` が出すのは次の7点です。

- 採用するルール（Issue に書かれたものだけ）
- 状態の設計（State / Action / フェーズの遷移）
- 純粋関数の一覧
- テストの一覧
- 画面の構成
- 実装の順番（Step1 → Step2 → Step3）
- 分からないこと・確認したいこと

**ここで人間が合意するまで `/implement` に進まないでください。**
計画が5分ずれていると、実装は30分ずれます。研修でいちばん時間を失うのは、
合意していない計画で30分実装してから作り直すパターンです。

### 原則2: 実装結果は人間が実機で確認する

AI は「実装しました」とは言えますが、「遊んで楽しかった」とは言えません。
`/implement` が終わったら、**必ず自分の手で1回遊んでください。**

```
npm run dev
```

- 最初から最後まで通しで1回プレイする
- リセットして2回目が正しく始まるか見る
- やってはいけない操作をわざとやる（判定中の連打、出せないカードのクリック、0枚のときに引く）

`npm run verify` が緑でも、遊べないゲームは緑になります。テストは「書いたことしか確かめない」からです。
**遊ぶのは人間の仕事です。**

### 原則3: テストの中身は人間が読む

テストが100件あっても、全部が正常系なら仕様は守られていません。
`logic.test.ts` を開いて、**`it("...")` の日本語だけを上から読んでください。**

お手本（`src/games/example-game/logic.test.ts`）のテスト名はこうなっています。

```
it("同じランクは引き分け")
it("判定中にもう一度予想しても状態が変わらない（連打で先に進めない）")
it("山札が空なら予想した時点で終了する")
it("判定待ちでないときの tick は無視される")
it("同じ seed なら同じ展開になる（テストが安定する）")
```

テスト名を読むだけで「このゲームは何を守っているか」が分かります。
自分のゲームのテスト名を読んで**そうなっていなければ、テストが足りていません。**

そしてもう1つ、**必ず1回はやってください。**

> `logic.test.ts` のアサーション（`expect(...)` の行）を1つだけわざと逆にして `npm test` を実行し、
> **赤くなることを確認してから元に戻す。**

赤くならないテストは、何も守っていないテストです。これは30秒で終わります。

## スラッシュコマンド8本

`.claude/commands/` に入っています。チャット欄に `/` を打てば一覧が出ます。

| コマンド | いつ使う | 何をする（そして何をしない） |
|---|---|---|
| `/kickoff <Issue番号>` | 実装を始める前に1回 | Issue と正典（`docs/games/<ゲームID>.md`）を読み、ルール・状態設計・関数一覧・テスト一覧・実装順を出して**そこで止まる**。**コードは変更できない**（編集ツールが無効） |
| `/implement [Step番号]` | 計画に合意したあと | 合意した計画に沿って実装する。**テストを先に書いて赤を確認してから** `logic.ts` を書き、最後に画面を作る。計画に無いことは足さず、思いついた改善は提案として最後に書くだけ |
| `/verify [Issue番号]` | 提出前 | `npm run verify` を実行し、Issue の必須要件と実装・テストの対応表を作る。`rule-checker` サブエージェント（別の目）にも規約を点検させる |
| `/pr` | Pull Request を出す直前 | `git diff origin/main...HEAD` を読んで本文を `.pr-body.md` に書く。**`gh pr create` は実行しない**。「レビューしてほしい点」は空欄のまま残す（人間が書く欄） |
| `/review <PR番号>` | 他チームの PR をレビューするとき | `gh pr checkout` して `npm run dev` で**実際に遊んでから**差分を読み、3点セットの指摘案を作る。**コメント投稿はしない**（編集ツールも無効） |
| `/fix-review <PR番号>` | 自分の PR に指摘が付いたとき | コメントを取得し「直す / 相談 / 直さない」の3分類で対応方針の表を作る。**合意してから**直し、指摘ごとの返信文案まで作る（投稿は人間） |
| `/handoff` | 作業を中断するとき・講師に状況を渡すとき | 今どこ / 直前にやったこと / できている・できていない / 次の一手 を10行でまとめる。**次に打つコマンドを1つだけ**示す。1人開発なので、再開する自分への引き継ぎにもなる |
| `/stuck <困っていること>` | 詰まったとき | `scope` `lint` `typecheck` `test` を回して事実を集め、**最初のエラーだけ**を引用し、次の一手を1つだけ出す。**コードは変更しない**（詰まったときに作り直しを始めさせないため） |

**編集ツールを取り上げてあるのは `/kickoff` `/review` `/stuck` の3本です。**
「考えるだけ」「読むだけ」「整理するだけ」のときに、勝手に手が動かないようにしてあります。

## 良いプロンプトと悪いプロンプトの対比

### 対比1: 実装を頼むとき

| | プロンプト |
|---|---|
| 悪い | 「ババ抜きを作って」 |
| 良い | 「Issue #1 の Step1 だけ、`logic.ts` と `logic.test.ts` を実装して。画面（`.tsx`）はまだ触らないで」 |

**なぜ悪いのか**: 範囲が無いので、AI は自分で範囲を決めます。
ルールも自分で決め、画面も作り、CPU も作り、10分後に600行が出てきます。
そうなると人間は読めず、確認できず、直せません。**確認できない成果物は、無いのと同じです。**

良いプロンプトの型はこれです。

```
<正典の場所> の <どの部分> だけを、<どのファイル> に実装して。
<やらないこと> はまだやらないで。
```

範囲は「ファイル」と「Step」で切ると失敗しません。

### 対比2: エラーで困ったとき

| | プロンプト |
|---|---|
| 悪い | 「テストが落ちる、直して」 |
| 良い | 「このテストの**最初のエラーだけ**を見て、原因の候補を挙げて。まだ直さないで」 |

**なぜ悪いのか**: 「直して」と言うと、AI は**落ちているテストを通すこと**を目的にします。
いちばん速く通す方法は、テストのほうを書き換えることです。
気づかないうちに `expect` が緩められ、仕様が消えます。

エラーが10件出ていても、原因はたいてい1つです。
2件目以降は1件目の影響なので、**最初の1件だけ**を見せてください。`/stuck` はこれを自動でやってくれます。

```
/stuck 神経衰弱のテストが3件落ちる
```

### 対比3: 仕上げのとき

| | プロンプト |
|---|---|
| 悪い | 「もっと良くして」 |
| 良い | 「必須要件はすべて終わったので、`README.md` の実装メモを書いて。採用したルールと、採用しなかったルールを書き分けて」 |

**なぜ悪いのか**: 「良く」の基準が無いので、AI は**自分の基準**で良くします。
アニメーションが増え、ローカルルールが増え、リファクタリングが始まり、
さっきまで緑だった `npm run verify` が赤くなります。研修の残り時間は戻ってきません。

**仕上げでやることは決まっています。** 迷ったらこの3つだけ頼んでください。

- `README.md` の「遊び方 / 採用したルール / 実装メモ」を埋める
- `index.ts` の `status` を `"ready"` にする（`npm run verify` が緑のときだけ）
- `/pr` で Pull Request の本文を作る

## 人間が確認する4フェーズ

AI に任せてよい作業と、人間がやらなければならない確認は別物です。
次の4回だけは、必ず自分の目で見てください。1回あたり2〜5分で終わります。

### フェーズ1: 計画（`/kickoff` の直後）

- [ ] Issue（`docs/games/<ゲームID>.md`）の**必須要件と計画が1対1で対応**しているか
- [ ] ルールの解釈が正典と食い違っていないか（「たぶんこうだろう」で足されたルールが無いか）
- [ ] テストの一覧が**正常系だけに偏っていないか**（境界値・やってはいけない操作があるか）
- [ ] 担当フォルダ `src/games/<自分のゲームID>/` の外を触る計画になっていないか
- [ ] `logic.ts` に `reduce` と `pendingDelayMs` が置かれているか（時間と乱数が画面側に漏れていないか）

**1つでも「いいえ」があれば、`/implement` に進まずに計画を直させてください。**

### フェーズ2: 実装後（`/implement` の直後）

- [ ] `npm run verify` が**緑**（AI の「できました」ではなく、自分の画面で緑を見る）
- [ ] `npm run dev` で**最初から最後まで1回プレイ**した
- [ ] リセットして2回目が正しく始まった
- [ ] やってはいけない操作を試した（連打 / 出せないカード / 0枚のとき）
- [ ] `logic.test.ts` の `it("...")` を上から読んで、仕様が言葉になっている
- [ ] アサーションを1つ逆にして**赤くなることを確認**し、元に戻した
- [ ] `git status` で、変更が担当フォルダの中だけに収まっている

### フェーズ3: Pull Request を出す前（`/pr` の前後）

- [ ] `npm run verify` が緑（`/pr` は緑でなければそこで止まります）
- [ ] `.pr-body.md` の「**レビューしてほしい点**」を**自分の言葉で**書いた
      （「勝敗判定を見てください」ではなく「同じ数字が出たときの処理が怪しいので、そこを重点的に」）
- [ ] 「採用したルール」に、**採用しなかったもの**まで書いてある
- [ ] 「発展課題・未対応事項」に、できていないことを正直に書いた
- [ ] スクリーンショットを撮った（`Win + Shift + S`。画像は**コミットせず** PR 本文にドラッグ&ドロップ）

```
git push -u origin HEAD
gh pr create --draft --title "<ゲーム名>を実装" --body-file .pr-body.md
```

CI が緑になったら `gh pr ready` で Draft を外します。

### フェーズ4: レビュー時（`/review` と `/fix-review`）

**レビューする側**

- [ ] `gh pr checkout <PR番号>` して `npm run dev` で**実際に遊んだ**（差分を眺めるだけは無効）
- [ ] 指摘のそれぞれについて「自分が実機で確認できたか / 未確認か」を区別した
- [ ] 投稿する文章を**自分で読み直した**（AI の下書きをそのまま貼らない）

**指摘を受けた側**

- [ ] `/fix-review` が出した「直す / 相談 / 直さない」の分類に、**自分が納得している**
- [ ] 直したあと `npm run verify` を回し直した
- [ ] 指摘1件ずつに返信した（直しただけで黙っているのが、レビュアーをいちばん困らせます）

詳しくは `docs/review-guide.md` を見てください。

## AI が間違えやすいところ（研修で実際に起きます）

### 1. 担当範囲外を「ついでに直す」

`src/core/` の型が気に入らない、`src/components/Card` にプロパティを足したい ——
AI は**親切心で**共通基盤に手を伸ばします。

- **どうなるか**: フック（`.claude/hooks/guard-scope.mjs`）がその場で止めます。
  すり抜けても `npm run scope` が赤くなり、pre-commit でコミットできず、CI でマージできません。
- **見つけ方**: `git status` を見る。担当フォルダ以外の行があれば、そこが事故です。
- **戻し方**: `npm run scope` が出す `git restore ...` をそのまま実行してください。

```
npm run scope
git status
```

### 2. 「動きました」と言うが `npm run verify` を通していない

`npm test` だけ通して「完成しました」と報告してくることがあります。
`npm run verify` は **範囲チェック → lint → 型 → テスト → ビルド** の5つで、CI とまったく同じ内容です。

- **どうなるか**: PR を出してから CI が赤くなり、レビュアーを待たせます。
- **対処**: 報告を受けたら、必ず**自分で**打ってください。

```
npm run verify
```

作業を終えようとしたときに `verify` を通していないと、Stop フックが1回だけ引き止めます。
ただし2回目は通るようになっているので、「止められないから大丈夫」ではありません。

### 3. テストが正常系だけになる

AI に「テストを書いて」と頼むと、**動く経路のテスト**を書きます。
ゲームが壊れるのは、動く経路ではなく境界です。

- **不足しがちなもの**: 同じ数字 / 最後の1枚 / 0枚 / 判定中の二重クリック / 出せないカードを出す
- **頼み方**: 「テストを足して」ではなく、**テスト名を指定して**頼みます。

```
it("判定中にもう一度クリックしても手数が増えない") を logic.test.ts に足して。
実装は変えないで、まず赤くなることを見せて。
```

### 4. Issue に書かれていないローカルルールを勝手に足す

トランプゲームは家庭ごとにルールが違います。
AI は学習した「一般的な大富豪」を知っているので、頼まなくても**縛り**や**スペードの3**を足しがちです。

- **正しい判断**: `docs/games/<ゲームID>.md` が**正典**です。**そこに無いことは実装しません。**
- **見つけ方**: `/verify` が作る「必須要件 → 実装 → テスト」の対応表に、**Issue に無い行**が出ていないか見る。
- **言い方**: 「正典に無いルールを実装していないか、`docs/games/<ゲームID>.md` と突き合わせて表にして」

余計なルールは、レビュアーを混乱させ、CPU のバグを増やし、時間を奪います。
**足すのではなく、必須要件を先に終わらせてください。**

## 止められたときは、回避策を探させない

ハーネスに止められると、AI は**善意で回り込もうとします。**
`sed -i` で書く、リダイレクト（`>`）で上書きする、`cp` で置き換える、
`git commit --no-verify` を使う、`.claude/settings.json` を書き換える ——
これらは全部ふさいであります（`.claude/hooks/guard-bash.mjs`）。

**止められたのは、あなたが悪いからではありません。**
「共通基盤に手を入れないと解けない」と感じた時点で、たいていは**設計の勘違い**か、
本当に運営が直すべきことのどちらかです。どちらも参加者が直すものではありません。

止められたら、AI にこう言ってください。

```
回避策は探さないで。CLAUDE.md と docs/harness.md を読んで、
なぜ止められたのかと、ゲーム側だけで実現する案があるかを説明して。
```

そのうえで、**手を止めて講師に相談**します。相談するときはこの形で伝えてください
（フックの拒否メッセージも、同じ形で報告するように AI に指示しています）。

```
- やりたいこと:
- 足りないと思うもの:
- ゲーム側だけで実現する案（あれば）:
```

読むもの:

- `CLAUDE.md` … 絶対に守る5条
- `docs/harness.md` … 何が、どの層で、なぜ止まるのか
- `docs/troubleshooting.md` … よくあるエラーと対処

## まとめ — 誰がやるか

| やること | 担当 |
|---|---|
| Issue を読んで計画を立てる | Claude Code（`/kickoff`） |
| 計画が正しいか決める | **人間** |
| テストとロジックを書く | Claude Code（`/implement`） |
| 実機で遊ぶ | **人間** |
| テスト名を読み、1つ逆にして赤を見る | **人間** |
| `npm run verify` を回す | どちらでもよい（結果は**人間**が見る） |
| PR 本文の下書き | Claude Code（`/pr`） |
| 「レビューしてほしい点」を書く | **人間** |
| 止められたときの判断 | **人間**（そして講師） |

**AI が速いぶんだけ、人間は確かめる時間を持てる。**
これがこの研修でいちばん持ち帰ってほしいことです。
