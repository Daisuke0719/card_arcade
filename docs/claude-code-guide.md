# Claude Code の使い方 — 役割を分けて安全に進める

Claude Codeは、指示に基づいて調査や実装を行う開発支援ツールです。
指示が曖昧な場合は、想定より広い範囲を変更することがあります。

この文書では、依頼する作業範囲、実装結果の確認方法、提出前の確認事項を説明します。
リポジトリの決まりは `CLAUDE.md`、止められたときの仕組みは `docs/harness.md`、
エラーの直し方は `docs/troubleshooting.md` を見てください。

---

## ターミナルは2本 — 操作する場所を分ける

研修では、2つのターミナルを使い分けます。

| | ターミナルA（Claude Code） | ターミナルB（参加者が操作） |
|---|---|---|
| 中身 | Claude Code のセッション | ふつうの PowerShell |
| 常駐 | — | **`npm run dev`（研修中は起動したままにする）** |
| やること | 調査 / 実装の依頼 / 差分の確認 / 文章の下書き | **ブラウザでプレイする** / `npm test` の結果確認 / `gh pr ready` |
| 入力するもの | プロンプト（日本語） | コマンド（PowerShell） |

### なぜ2本に分けるのか

研修ではプロンプトで作業を依頼します。依頼する作業と、参加者が確認する作業を分けて進めます。

そこで、Claude Code から実行できない操作をターミナルB に分けています。

確認を忘れないようにするには、ルールだけでなく操作する場所も分けると効果的です。
ターミナルB では、参加者が実際の画面や GitHub の状態を確認します。

### ターミナルB の起動（研修が始まったら最初にやる）

```powershell
cd $HOME/dev/card_arcade
npm run dev
```

ブラウザで http://localhost:5173/ を開いたら、**研修が終わるまで開発サーバーを起動したままにします。**
コードを変えても再起動は要りません。**ブラウザを F5 で再読み込みするだけ**で最新のコードになります。

`Ctrl + C` で止めるのは、研修が終わったときだけです。

### ターミナルA では `npm run dev` が「実行できない」

これは運用上の注意ではなく、**ハーネスによって実行が拒否されます。**

```text
npm run dev は Claude Code からは実行できません。
起動したままになるので、このセッションが返ってこなくなります。
```

Claude Code に「開発サーバーを起動して」と頼んでも、何度頼んでも同じメッセージが返ります。
**別のコマンドで回避しないでください。** その時間を実機の確認に使います。

## Claude Codeから実行できないコマンド

ターミナルAでは実行が拒否されるコマンドを次に示します。

| コマンド | なぜ実行できないか | 代わりにどうするか |
|---|---|---|
| `npm run dev` / `npm run preview` | 起動したままになりセッションが返らない。参加者の 5173 番とポートが衝突する | **ターミナルB** で起動する。すでに動いていればブラウザを F5 |
| `npm run test:watch` / `npm test -- --watch` / `npx vitest`（`run` なし） | 監視モードは終わらないので、セッションが返らない | `npm test`（= `vitest run`）を使う。保存のたびに流したいなら**ターミナルB** で |
| `gh pr review` / `gh pr comment` / `gh issue comment` | 他人の Pull Request と Issue に投稿する操作で、影響範囲が広い | 下書きは Claude Code に作成を依頼し、**GitHub の画面から参加者が投稿する** |
| `gh api` | 上の判定をすべて回避できる操作（作業ブランチのときだけ止まる） | やりたいことを説明し、必要なら講師に相談する |
| `node scripts/setup-github.mjs` / `node scripts/build-issue-bodies.mjs` | **講師専用。** 9人分のIssueをまとめて変更する（作業ブランチのときだけ止まる） | 参加者は使わない |
| `npm run scaffold -- --all` / `--force` | **講師専用。** 9人分の雛形をまとめて上書きする（作業ブランチのときだけ止まる） | `npm run scaffold -- --game <自分のゲームID>` を使う |
| `gh issue edit` | Issue 本文は全員が同じ条件で進むための基準なので、講師が管理する（作業ブランチのときだけ止まる） | チェックボックスは GitHub の Issue 画面で自分でクリックする |
| `npm install` / `yarn add` などの依存追加 | `package-lock.json` が変わると9人全員の Pull Request が競合する | `@core` と `@ui` で作る。足りなければ講師に相談する |
| `git push --force` / `git commit --no-verify` / `main` への push | 履歴とチェックを壊す。他の人の作業に波及する | 直しを新しいコミットで重ねる |

### 承認を求められるもの（`ask`）

実行前に、**参加者の承認を求める確認が表示されます。**

```text
git push / gh pr create / gh pr merge / gh pr ready / gh pr edit / gh issue create
```

**この6つは承認画面から実行せず、参加者がターミナルBで実行します。**
どれも「他の人に見える」か「元に戻すのに手間がかかる」操作だからです。
とくに `gh pr ready` を打った瞬間から、提出済みとして扱われます。

### 確認なしで通るもの（`allow`）

```text
npm test / npm run verify / npm run build / npm run scaffold -- --game <ゲームID>
git switch / git add / git commit / git status / git diff / git pull
gh pr checkout / gh pr view / gh pr checks / gh pr diff
node -v / gh auth status
```

確認なしで実行できる理由は、`docs/harness.md` の「なぜ無害なコマンドは確認なしで通るのか」で説明しています。確認の対象を影響の大きい操作に絞ることで、各確認の目的を明確にしています。

## 作業時の3つの原則

### 原則1: 実装計画を先に確認する

実装を依頼する前に、予定している変更内容の説明を求めます。

```text
GitHub の Issue #<Issue番号> と docs/games/<ゲームID>.md を読んで、
src/games/<ゲームID>/ にこのゲームをどう実装するか計画を立ててください。

- Issue にも docs/games/<ゲームID>.md にも書かれていないルールは足さないでください。
- まだコードは書かないでください。ファイルも変更しないでください。
```

**「まだコードは書かないでください」を消さないでください。** この1文があるので、
計画を読んでいる間にファイルが変わりません。

出てきた計画を、Issue の必須要件と上から1件ずつ突き合わせます。
**対応が見えない要件が1つでもあれば、その場で伝えてください。**

```text
必須要件の「<Issue の要件の文言をそのまま貼る>」に対応する項目が計画にありません。
どこで実現するつもりなのかを計画に足してください。まだ実装はしないでください。
```

```text
計画の「<計画の中の1行をそのまま貼る>」は、Issue にも docs/games/<ゲームID>.md にも書かれていないルールです。
Issue に無いものは実装しないので、計画から外してください。まだ実装はしないでください。
```

計画と要件にずれがあると、実装後の手戻りが大きくなります。特に時間がかかるのは、
内容を確認しないまま実装を進めて、後から作り直すことになるためです。**計画を確認してから実装を依頼してください。**

### 原則2: 実装結果は参加者がブラウザで確認する

Claude Codeによる実装後も、操作感やゲームの進行はブラウザで確認する必要があります。
実装が終わったと報告されたら、**実際の画面で1回プレイしてください。**

**ターミナルB の開発サーバーは起動したままなので、ブラウザを F5 で再読み込みします。**

```powershell
# ターミナルB（止まっていたときだけ）
npm run dev
```

- 最初から最後まで通しで1回プレイする
- リセットして2回目が正しく始まるか見る
- やってはいけない操作をわざとやる（判定中の連打、出せないカードのクリック、0枚のときに引く）

`npm run verify` が成功しても、操作や進行に問題が残ることがあります。テストで確認できるのは、定義した条件だけだからです。
**実機でのプレイは参加者が行います。** 開発サーバーはターミナルB で起動します。

**実装完了の報告だけで次へ進まず、実際に操作してください。** テストが成功していても、
画面を操作できない、ゲームが終了しない、といった問題が残ることがあります。

### 原則3: テストは実装と同時に作成し、名前を参加者が確認する

テストを後回しにすると、時間切れで不足したまま提出することがあります。
**`logic.ts` に関数を追加するときは、`logic.test.ts` のテストも同時に作成するよう依頼してください。**

```text
logic.ts に関数を足したら、logic.test.ts にその関数のテストも書いてください。合計3件以上にしてください。
```

`status` を `"ready"` にするゲームには、`logic.test.ts` に `it(` が**3件以上**必要です。
足りないと契約テストが失敗し、CI を通せません
（件数は `harness/config.json` の `minTestsPerReadyGame`。`it.skip` は数に入りません）。

書けたら `logic.test.ts` を開いて、**`it("...")` の日本語だけを上から読んでください。**
お手本（`src/games/example-game/logic.test.ts`）のテスト名はこうなっています。

```
it("同じランクは引き分け")
it("判定中にもう一度予想しても状態が変わらない（連打で先に進めない）")
it("山札が空なら予想した時点で終了する")
it("判定待ちでないときの tick は無視される")
it("同じ seed なら同じ展開になる（テストが安定する）")
```

テスト名を読むだけで「このゲームは何を守っているか」が分かります。
何を確かめているか分からない名前があれば、その場で修正を依頼してください。

```text
テスト名の「<読んで分からなかった名前をそのまま貼る>」は、何を確認しているのかが名前から分かりません。
このテストが何を確認しているのかを説明したうえで、名前を分かる形に直してください。実装は変えないでください。
```

## よく使うプロンプトの型

覚えるコマンドはありません。場面ごとに、次の形で頼みます。
そのままコピーできる文面は `docs/handson-steps.md` に載っています。

| 場面 | 依頼する内容 | 残す必要がある文言 |
|---|---|---|
| 実装を始める前 | Issue とルール文書を読み、実装計画を作成する | 「まだコードは書かないでください」 |
| 実装 | まず最後まで遊べる状態まで実装する | 「`src/games/<ゲームID>/` の中だけ」「`npm run dev` は実行しないで」 |
| 遊んで直す | プランモード（`/plan`）で原因と改善策を整理し、確認後に実行する | 「まだファイルは変更しないでください」 |
| 提出前 | `npm run verify` を実行し、必須要件との対応表を作成する | 「満たせていない要件は未達と書いて」 |
| Pull Request | `.pr-body.md` に本文の作成を依頼する | 「`gh pr create` も `git push` も実行しないで」 |
| 状況の共有 | 現在の状況を10行以内にまとめる | 「推測で書かないでください」 |
| 詰まったとき | 事実を集めて、次に試すことを1つだけ挙げさせる | 「コードは変更しないでください」 |

### 状況を10行でまとめさせる

作業を中断するときや講師に相談するときは、現在の状態をClaude Codeに整理してもらいます。

```text
現在の状況を10行以内でまとめてください。次の5点を含めます。

- いま何をしているか
- 直前に終わったこと
- まだ終わっていないこと
- 次にやること
- 気をつけること

先に git branch --show-current / git status --short / npm run scope を実行し、
その結果にもとづいて書いてください。推測で書かないでください。コードは変更しないでください。
```

**「推測で書かないでください」を消さないでください。** この1文が無いと、
確認していない内容がそれらしい文章で並びます。
作成された10行を、`git status --short` と `npm test` の結果に照らして確認してください。

> `.claude/commands/` には、以前の版で使っていたスラッシュコマンドの定義が残っています。
> 当日は使いません。上のプロンプトで進めてください。

## 良いプロンプトと悪いプロンプトの対比

### 対比1: 実装を依頼するとき

| | プロンプト |
|---|---|
| 悪い | 「<ゲーム名>を作って」 |
| 良い | 「合意した方針どおりに、`src/games/<ゲームID>/` の中だけを実装して。ほかのファイルは変更しないで」 |

**なぜ悪いのか**: 範囲を指定していないため、AI が対象を判断してしまいます。
ルールも自分で決め、画面も作り、CPU も作り、気づくと600行が出てきます。
そうなると、内容を確認したり修正したりするのが難しくなります。

良いプロンプトの型はこれです。

```text
<ルール文書の場所> の <どの部分> だけを、<どのファイル> に実装して。
<やらないこと> はまだやらないで。
```

範囲は「フォルダ」と「ファイル」で指定すると失敗しません。

### 対比2: エラーで困ったとき

| | プロンプト |
|---|---|
| 悪い | 「テストが失敗するので、直して」 |
| 良い | 「このテストの**最初のエラーだけ**を見て、原因の候補を挙げて。まだ直さないで」 |

**問題点**: 修正対象を指定しないと、実装ではなくテストの期待値を変更することがあります。それでは仕様を検証できません。

エラーが10件出ていても、原因はたいてい1つです。
2件目以降は1件目の影響なので、**最初の1件だけ**を見せてください。

```text
テストが3件失敗していて、原因が分かりません。
npm test を実行して、最初のエラーだけを引用してください。
そのうえで docs/troubleshooting.md と照らし合わせ、次に試すことを1つだけ挙げてください。

コードは変更しないでください。
```

### 対比3: 仕上げのとき

| | プロンプト |
|---|---|
| 悪い | 「もっと良くして」 |
| 良い | 「必須要件はすべて終わったので、`README.md` に遊び方と採用したルールを書いて。採用しなかったルールも書き分けて」 |

**問題点**: 「良く」の基準がないため、アニメーション、独自ルール、リファクタリングなど、依頼していない変更が加わることがあります。その結果、必須要件の実装が遅れ、`npm run verify` が失敗する場合もあります。

仕上げでは、次の3点を確認します。

- `README.md` の「遊び方 / 採用したルール」を埋める
- `index.ts` の `status` を `"ready"` にする（`npm run verify` が成功したときだけ）
- `.pr-body.md` に Pull Request の本文を書く（`gh pr create` は実行しない）

### 対比4: 対象範囲を指定する

| | プロンプト |
|---|---|
| 悪い | 「直しておいて」 |
| 良い | 「`logic.ts` だけ直して。画面（`.tsx`）は触らないで」 |

| | プロンプト |
|---|---|
| 悪い | 「テストを足して」 |
| 良い | 「`logic.test.ts` に `it("判定中にもう一度クリックしても手数が増えない")` を1件だけ足して。`logic.ts` は変えないで。まず失敗することを見せて」 |

| | プロンプト |
|---|---|
| 悪い | 「PR を出しておいて」 |
| 良い | 「`.pr-body.md` に本文の下書きだけ書いて。**`gh pr ready` はしないで。** 私が自分で入力します」 |

**なぜ悪いのか**: 「直しておいて」だけでは、対象範囲が分かりません。
指示の範囲が曖昧だと、画面や関数名、テストまで変更対象に含まれることがあります。
変更範囲が広がると、差分を確認しきれなくなります。

範囲を切る言葉は、この4つを覚えれば足ります。

| 切り方 | 言い方 |
|---|---|
| **ファイルで切る** | 「`logic.ts` と `logic.test.ts` だけ」 |
| **やらないことを言う** | 「画面は触らないで」「実装は変えないで」 |
| **止める場所を言う** | 「まだ直さないで」「計画だけ出して止まって」 |
| **投稿させない** | 「投稿はしないで」「push はしないで」 |

対象範囲を指定するのは、変更内容を確認できる大きさに保つためです。

### 対比5: Claude Code にできないことを頼まない

| | プロンプト |
|---|---|
| 悪い | 「`npm run dev` を起動して、画面を確認して」 |
| 良い | 「実装が終わったら、私がターミナルB のブラウザで確認します。**確認すべき操作を3〜5ステップで**書き出して」 |

**なぜ悪いのか**: ハーネスが拒否します。頼んだ時間がそのまま失われます。
また、画面の確認は、参加者が実際に操作して結果を判断する必要があります。

## 参加者が確認する3つの場面

Claude Code に依頼する作業と、参加者が行う確認を分けます。
次の3回は、実際の状態を確認してください。
**【B】の項目は、ターミナルB でしかできません。**

### 1. 実装の計画を読んだとき

- [ ] Issue（`docs/games/<ゲームID>.md`）の**必須要件と計画が1対1で対応**しているか
- [ ] ルールの解釈がルール文書と食い違っていないか（推測で足されたルールが無いか）
- [ ] 担当フォルダ `src/games/<自分のゲームID>/` の外を触る計画になっていないか
- [ ] ルールを `logic.ts` に置き、時間と乱数を画面側に漏らさない形になっているか

**1つでも「いいえ」があれば、実装を依頼せず計画を修正します。**

### 2. 実装が終わったと報告されたとき

- [ ] `npm run verify` が**成功する**（AI の「できました」ではなく、自分の画面で確認する）
- [ ] **【B】** ブラウザを F5 で再読み込みして、**最初から最後まで1回プレイ**した
- [ ] **【B】** リセットして2回目が正しく始まった
- [ ] **【B】** やってはいけない操作を試した（連打 / 出せないカード / 0枚のとき）
- [ ] `logic.test.ts` の `it("...")` を上から読んで、何を確かめているか分かる
- [ ] `logic.test.ts` に `it(` が3件以上ある
- [ ] `git status` で、変更が担当フォルダの中だけに収まっている

### 3. Pull Request を出す前

- [ ] `npm run verify` が成功する
- [ ] 「採用したルール」に、**採用しなかったもの**まで書いてある
- [ ] 「発展課題・未対応事項」に、できていないことを正直に書いた

**push と Pull Request の操作は、参加者がターミナルBで実行します。**

```powershell
# ターミナルB
git push -u origin HEAD
gh pr edit <自分のPR番号> --body-file .pr-body.md
gh pr checks
gh pr ready
```

（Draft をまだ作っていない場合だけ
`gh pr create --draft --title "<ゲーム名>を実装" --body-file .pr-body.md` を使います）

CI が成功してから `gh pr ready` で Draft 状態を解除します。
**遊んでいないもの、`verify` が成功していないものを ready にしないでください。**

## AI が間違えやすいところ（研修で実際に起きます）

### 1. 担当範囲外を「ついでに直す」

`src/core/` の型が気に入らない、`src/components/Card` にプロパティを足したい ——
指示が曖昧だと、共通基盤まで変更対象に含まれることがあります。

- **どうなるか**: フック（`.claude/hooks/guard-scope.mjs`）がその場で止めます。
  すり抜けても `npm run scope` が失敗し、pre-commit でコミットできず、CI でマージできません。
- **見つけ方**: `git status` を確認します。担当フォルダ以外の行があれば、範囲外の変更です。
- **戻し方**: `npm run scope` が出す `git restore ...` をそのまま実行してください。

```powershell
npm run scope
git status
```

何かの拍子に他の人のブランチへ移っていても、`.claude/.state/owner.json` に記録された
自分の担当と突き合わせるので、**他人のコードを編集しようとすると止まります。**

### 2. 「動きました」と言うが `npm run verify` を通していない

`npm test` だけ通して「完成しました」と報告してくることがあります。
`npm run verify` は **範囲チェック → lint → 型 → テスト → ビルド** の5つで、CI とまったく同じ内容です。

- **どうなるか**: PR を出してから CI が失敗し、マージが遅れます。
- **対処**: 報告を受けたら、参加者がターミナルBで実行してください。

```powershell
npm run verify
```

作業を終えようとしたときに `verify` を通していないと、Stop フックが1回だけ引き止めます。
ただし2回目は通るようになっているので、「止められないから大丈夫」ではありません。

### 3. テストが正常系だけになる

テスト条件を指定せずに依頼すると、正常系のテストだけが作成されることがあります。
同値、最後の1枚、0枚、判定中の再操作など、境界条件も明示して依頼してください。

- **不足しがちなもの**: 同じ数字 / 最後の1枚 / 0枚 / 判定中の二重クリック / 出せないカードを出す
- **頼み方**: 「テストを足して」ではなく、**テスト名を指定して**頼みます。

```text
it("判定中にもう一度クリックしても手数が増えない") を logic.test.ts に足してください。
実装（logic.ts）は変えないでください。まず失敗することを見せてください。
```

### 4. Issue に書かれていない独自ルールを追加する

トランプゲームは家庭ごとにルールが違います。
Claude Codeが、文書にない一般的なルールや追加の役を実装することがあります。

- **判断基準**: `docs/games/<ゲームID>.md` に記載されていないルールは実装しません。
- **見つけ方**: 提出前に作らせる「必須要件 → 実装 → テスト」の対応表に、**Issue に無い行**が出ていないか見る。
- **言い方**:

```text
ルール文書にないルールを実装していないか、docs/games/<ゲームID>.md と突き合わせて表にしてください。
ルール文書にないものが見つかったら、消す前に一覧で見せてください。
```

文書にないルールを加えると、CPUの処理やテストも増え、必須要件の実装が遅れます。
**足すのではなく、必須要件を先に終わらせてください。**

### 5. 実行できないコマンドを、言い方を変えて何度も試す

`npm run dev` が拒否されたあと、Claude Codeが `npx vite` や `vite` などの代替コマンドを提案することがあります。
これらのコマンドも拒否されるため、実行しないでください。

- **影響**: 同じ目的のコマンドを繰り返し試すことになり、実装が進みません。
- **対処**: 拒否メッセージが出たら、参加者がターミナルBで操作を引き継ぎます。

```text
それは実行できない決まりになっています。別の方法を探さないでください。
画面の確認は私がターミナルB でやります。確認すべき操作を3〜5ステップで書き出してください。
```

## 止められたときは、回避策を探させない

ハーネスに拒否されたあと、別のコマンドで同じ操作を試す場合があります。
`sed -i` で書く、リダイレクト（`>`）で上書きする、`cp` で置き換える、
`git commit --no-verify` を使う、`.claude/settings.json` を書き換える ——
これらの操作は `.claude/hooks/guard-bash.mjs` で拒否されます。

操作が拒否された場合は、設計の前提に誤りがあるか、運営による共通基盤の変更が必要な可能性があります。どちらの場合も、参加者だけで変更を進めず、講師に相談してください。

操作が拒否された場合は、Claude Codeに次のように伝えてください。

```text
回避策は探さないでください。
CLAUDE.md と docs/harness.md を読んで、なぜ止められたのかを説明してください。
そのうえで、src/games/<自分のゲームID>/ の中だけで実現する案があるかを教えてください。
別のコマンドで同じことをやり直すのはやめてください。
```

そのうえで、**手を止めて講師に相談**します。相談するときはこの形で伝えてください
（フックの拒否メッセージも、同じ形で報告するように AI に指示しています）。

```text
- やりたいこと:
- 足りないと思うもの:
- ゲーム側だけで実現する案（あれば）:
```

読むもの:

- `CLAUDE.md` … 必須ルール5項目
- `docs/harness.md` … 何が、どの層で、なぜ止まるのか
- `docs/troubleshooting.md` … よくあるエラーと対処

## まとめ — 誰がやるか

| やること | 担当 |
|---|---|
| Issue を読んで実装の計画を立てる | Claude Code |
| 計画が正しいか判断する | **参加者** |
| ロジックと画面とテストを書く | Claude Code |
| **開発サーバーを起動する** | **参加者**（ターミナルB。Aでは実行できません） |
| ブラウザでプレイする | **参加者**（ターミナルB） |
| テスト名を読み、何を確かめているか判断する | **参加者** |
| プレイ中に見つけた不具合を、再現手順つきで伝える | **参加者**（ターミナルBで操作してから） |
| `npm run verify` を実行する | どちらでもよい（結果は**参加者**が確認する） |
| PR 本文の下書き | Claude Code（`.pr-body.md` への作成を依頼する） |
| **PR を Ready にする** | **参加者**（ターミナルBで `gh pr ready`。Aでは承認を求められます） |
| **マージする** | **講師** |
| **Issue のチェックを付ける** | **参加者**（GitHubのIssue画面でクリック。`gh issue edit` は拒否されます） |
| まとめた10行が、実際の状態と合っているか確かめる | **参加者** |
| 操作を拒否されたときの判断 | **参加者**（必要に応じて講師に相談） |

右の列が参加者となっている操作は、主にターミナルBで行います。
操作する場所を分けることで、確認や承認を省略しにくくしています。

Claude Codeに作業を依頼した場合も、結果の確認と提出の判断は参加者が行います。
