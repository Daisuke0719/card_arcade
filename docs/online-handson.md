# オンライン対戦ハンズオン

前回作ったCPU対戦を残したまま、同じゲームをオンライン対戦に対応させます。参加者は1人1ゲームを担当し、Claude Codeへのプロンプト入力、ブラウザでの試遊、Pull Requestの提出までを自分で行います。

共通のルーム管理、WebSocket、再接続、再戦、Cloudflare、D1、認証、デプロイは運営が管理します。参加者はCloudflareへログインしたり、Secretを入力したりしません。

## 完成条件

- ゲームの入口からCPU対戦とオンライン対戦を選べる
- CPU版とオンライン版が同じ画面部品・盤面レイアウトを使う
- 担当Issueに書かれた人数でルームを作成・参加して最後まで遊べる
- 手番外、不正操作、試合終了後の操作を拒否できる
- 相手の非公開手札や山札の順序を表示しない
- 再読み込み後に同じプレイヤーとして復帰できる
- 同じルームで再戦できる
- CPU対戦が壊れていない
- `npm run verify` とオンライン固有テストが成功している

オンライン対戦のルール、人数、公開してよい情報は、担当のオンラインIssueに書かれています。以下のプロンプトの `<オンラインIssue番号>` には、この表の番号を入力します。

| `poker` | ポーカー | 2人 | #39 |

ページワン（`pageone`）はオンライン対戦に対応済みで、他のゲームの手本になっています。

CPU版の仕様書（`docs/games/<ゲームID>.md`）の人数はCPU対戦の人数です。オンライン対戦ではオンラインIssueの人数とルールを優先します。

## 参加者と運営の境界

### 参加者が実装するもの

- ゲーム固有のAction
- 手番、合法性、勝敗の検証
- 状態更新
- プレイヤーごとの公開状態
- CPU版とオンライン版で共有する画面部品
- オンライン固有のテスト

### 運営が用意するもの

- ルーム作成・参加・待機・退出・再接続
- WebSocket、revision、actionIdの処理
- 同じルームでの再戦
- 共通オンラインクライアントと接続状態表示
- `ServerGameAdapter` / `defineOnlineGame` / `defineOnlineView` / `OnlineGameViewProps` の契約
- `manifest.online` を登録したゲームに表示するCPU対戦／オンライン対戦の入口
- 再読み込み後に同じプレイヤーとしてルームへ戻る処理
- Worker、Durable Objects、D1
- ゲームごとのオンラインIssue
- CloudflareのSecret、デプロイ、Pagesとの接続

共通基盤に不足がある場合は、参加者が共通ファイルを変更せず、講師へ不足内容と利用例を報告します。

## 2つのターミナル

| 場所 | 用途 |
| --- | --- |
| ターミナルA（Claude Code） | 以下のプロンプトを入力し、調査・実装・テスト・PR本文を依頼する |
| ターミナルB（PowerShell） | `npm run dev`、`npm test`、ブラウザ確認、`gh pr ready`を実行する |

ターミナルAで`npm run dev`や監視モードのテストを実行しません。ターミナルBは研修中起動したままにします。

## Step 0｜起動とCPU版の比較基準

ターミナルBでフロントエンドを起動します。

```powershell
npm ci
npm run dev
```

オンライン対戦用のWorkerはローカルでは起動しません。マージ前の確認はオンライン固有テストとCPU版の動作で行い、2画面での試遊はマージ後に公開環境で行います。

担当ゲームのCPU対戦を1回最後まで遊び、盤面のスクリーンショットを保存します。オンライン版の比較では同じ画面幅を使います。CPU対戦が未完成ならオンライン化を始めず講師へ報告します。

## Step 1｜現状を調査する

ターミナルAに次を入力します。

```text
私は <ゲームID> の担当です。
前回作ったCPU対戦を残して、オンライン対戦を追加します。

まず、このリポジトリのCLAUDE.md、担当ゲームのREADME、
docs/online-handson.md、Issue #<オンラインIssue番号> を読んでください。

次を調査して報告してください。
1. 現在のブランチと未コミットの変更
2. 担当ゲームのCPU対戦が実装されているか
3. ルール、CPUの判断、画面描画がどのファイルにあるか
4. オンライン対応に使える共通機能と、担当ゲームで追加する機能
5. 作業開始を妨げる不足事項

まだファイルを変更しないでください。
既存ファイルの上書きや雛形の再生成はしないでください。
開発サーバーは私が別ターミナルで起動します。
```

## Step 2｜オンライン化の計画を立てる

```text
Issue #<オンラインIssue番号> に従って、
<ゲームID> をオンライン対戦対応にする計画を立ててください。

条件：
- 編集範囲は src/games/<ゲームID>/ の中だけです。
- 既存のCPU対戦を維持してください。
- CPU版とオンライン版は、外枠・盤面・カード・スコア表示まで同じ画面を使ってください。
- CPU版はローカル状態、オンライン版はサーバー公開状態を同じ画面へ渡してください。
- ルールと勝敗はサーバー側で決めてください。
- 相手の非公開手札と山札の順序をクライアントへ送らないでください。
- 接続、ルーム、再接続、再戦は運営の共通機能を使ってください。
- Issueにないルールは追加しないでください。

変更ファイル、共有する画面、送信するAction、公開状態、必要なテストを示してください。
共通基盤に不足がある場合は、担当範囲を広げず、不足する契約と利用例だけを報告してください。
まだ実装しないでください。
```

計画をIssueの必須要件と照合し、オンライン専用の別盤面を作る計画になっていないことを確認します。

## Step 3｜画面をCPU版と共通化する

```text
計画に沿って作業を始めてください。

最初に作業ツリーを確認してください。未コミットの変更があれば削除・上書きせず報告してください。
変更がなければ最新mainを取得し、担当ブランチ feature/<ゲームID> を用意してください。
同名ブランチや既存PRがあれば状態を確認し、強制リセットや重複PR作成はしないでください。

まずCPU対戦の外枠、盤面背景、ヘッダー、スコア、カード配置、結果表示を、
オンラインでも再利用できる画面コンポーネントへ整理してください。
CPU版のルールと操作感は維持し、オンライン処理はまだ実装しないでください。
変更は src/games/<ゲームID>/ の中だけに限定してください。

関連テストと型チェックを実行し、結果を報告してください。
```

ブラウザを再読み込みし、CPU版がStep 0のスクリーンショットと同じ見た目・操作になっていることを確認します。

## Step 4｜オンラインアダプターを実装する

```text
次に、計画したオンライン用アダプターとテストを実装してください。

src/games/pageone/onlineAdapter.ts を手本にして @core の defineOnlineGame を使い、
src/games/<ゲームID>/onlineAdapter.ts から onlineAdapter を公開してください。
minPlayers、maxPlayers、parseAction、getResult も実装してください。

要件：
- seedと参加者から初期状態を作る
- Actionの形式、本人、手番、合法性を検証する
- 状態更新と勝敗判定はサーバー側で行う
- 試合終了後の操作を拒否する
- 公開状態には見せてよい情報だけを含める
- CPU用タイマーやブラウザ専用処理をサーバーへ持ち込まない
- 既存のゲームロジックを可能な範囲で再利用する

合法操作、不正操作、終了判定、非公開情報のテストを追加してください。
revision、actionId、再接続処理は作り直さないでください。
担当フォルダ以外を変更せず、テスト結果を報告してください。
```

## Step 5｜共通画面へ接続する

```text
オンライン用アダプターを、共通ロビーへ接続してください。

src/games/pageone/PageOneOnlineView.tsx と src/games/pageone/index.ts を手本にして、
次の2つを実装してください。
1. @core の OnlineGameViewProps を受け取るオンライン対戦画面を src/games/<ゲームID>/ に作る
2. index.ts の manifest に online: defineOnlineView(onlineAdapter, オンライン対戦画面) を追加する

CPU版とオンライン版は同じ GameShell と同じ盤面コンポーネントを使い、
オンライン専用の別パネルで包み直さないでください。

要件：
- props の view（サーバーの公開状態）だけを盤面へ渡す
- 操作は props の sendAction で送信する
- サーバーから届く前に手札や勝敗を確定しない
- canAct が false の間は操作を無効にする
- GameShell の onReset と ResultModal の onRetry には props の onRematch を渡す
- 再戦後に前の試合結果を残さない

ゲームの入口、ルーム作成・参加・待機画面、接続状態と拒否理由の表示、
再読み込み後の復帰は共通ロビーが行うため、担当フォルダでは作らないでください。

実装と関連テストを実行してください。
未確認事項は「確認済み」とせず分けて報告してください。
変更範囲は src/games/<ゲームID>/ の中だけです。
```

## Step 6｜CPU版が壊れていないことを確認する

ブラウザを再読み込みし、次の3点を確認します。

- CPU版を最後まで遊び、リセットできる
- 盤面がStep 0のスクリーンショットと同じ見た目になっている
- ターミナルBの`npm test`が成功する

不具合があれば次を入力します。公開後の確認で見つかった不具合にも同じプロンプトを使います。

```text
<ゲームID> を試したところ、不具合がありました。

モード：<CPU／オンライン>
操作した画面：<ルーム作成者／参加者>
再現手順：<操作を順番に記載>
期待する結果：<期待した動作>
実際の結果：<起きたこと>
画面のエラー：<表示された文言>

まず原因を特定し、その根拠を説明してください。
原因に対応した修正と、再発を確認できるテストを追加してください。
変更は担当ゲームフォルダ内に限定してください。
範囲外の修正が必要なら、講師へ渡す調査結果をまとめてください。
```

## Step 7｜検証してPRを提出する

```text
<ゲームID> のオンライン対応を提出します。

1. mainとの差分を確認し、変更が担当フォルダ内だけか確認する
2. npm run verify を実行する
3. node scripts/scope-guard.mjs --base origin/main --branch feature/<ゲームID> を実行する
4. 成功したら担当フォルダの変更だけをコミットしてpushする
5. 既存PRがあれば更新し、なければDraft PRを作成する
6. PRテンプレートに、実装内容・テスト結果・CPU版の確認結果・未確認事項を書く
7. GitHubからPR URLと最新コミットを取得して報告する

検証が失敗した場合はコミット・提出へ進まず、原因を報告してください。
範囲チェックを無効にしたり、CI設定を変更したりしないでください。
オンライン版の2画面試遊はマージ後に行うため、未確認事項として書いてください。
PRのDraft解除とmainへのマージは行わないでください。
```

ターミナルBで次を実行し、CI成功後に講師へPR番号を共有します。

```powershell
gh pr ready <自分のPR番号>
gh pr checks <自分のPR番号> --watch
```

## 公開後の確認

マージは講師が行います。マージ後、Pagesとstaging Workerのデプロイ成功を講師が確認します。

講師からデプロイ完了の連絡を受けたら、公開URLを通常ウィンドウとシークレットウィンドウなど別セッションの2画面で開き、次を確認します。

| 確認 | 合格条件 |
| --- | --- |
| 作成・参加 | 片方が作ったルームへもう片方が参加できる |
| 開始・進行 | 必要人数がそろい、両画面の盤面と手番が一致する |
| UI比較 | CPU版と背景・外枠・カード配置がそろう |
| 不正操作 | 手番外、連打、不正カードで状態が壊れない |
| 情報保護 | 相手の非公開手札と山札順序が表示されない |
| 再接続 | 再読み込み後に同じプレイヤーとして復帰する |
| 終了・再戦 | 同じルームで次の試合を開始できる |

不具合が見つかった場合は、Step 6の不具合報告プロンプトで原因を調査し、修正を追加のPull Requestで提出します。

基盤側の問題を報告するときは、ゲームID、ルームコード、発生時刻、操作、画面のエラーを伝えます。認証トークンやSecretは共有しません。
