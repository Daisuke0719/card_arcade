## 1. 研修の設計意図

### 1-1. 主目的はゲーム制作ではない

180分でトランプゲームを1本仕上げるのは、正直に言えばおまけです。
**この研修が測っているのは「他人がいる共有リポジトリで、自分の担当範囲を守って完成まで持っていけるか」だけ**です。

参加者が持ち帰る経験は次の5つです。

1. 自分の担当範囲がコードで機械的に定義されている状態で作業した
2. `npm run verify` が緑になるまで「できました」と言わなかった
3. 他人に読まれる前提で Pull Request を書いた
4. **他人のコードを実際に動かして**レビューした（差分を眺めるだけではない）
5. 指摘を受けて直し、マージされ、公開された

ゲームの出来は6番目です。**時間が足りないときに削るのは常にゲームの中身**で、この5つではありません。
5章の「切り捨て順」はこの優先順位をそのまま数字にしたものです。

### 1-2. なぜ「間違いを機械が止める」ようにしてあるのか

9名が1つの `main` を共有します。この規模で口頭ルールは必ず破られます。
破られたときに困るのは破った人ではなく、**他の8名**です。

そこで、この研修では規約を文章ではなく**動くコード**にしてあります。

- 「他人のフォルダを触らないでください」→ `scripts/scope-guard.mjs` が差分を見て落とす
- 「依存を追加しないでください」→ `.claude/settings.json` の deny と `.claude/hooks/guard-bash.mjs` が止める
- 「`logic.ts` に `Math.random()` を書かないでください」→ ESLint が error にする
- 「ESLint を無効化して回り込まないでください」→ `tests/contract/boundaries.contract.test.ts` が落とす

**講師が注意する回数を減らすことが目的ではありません。**
「なぜダメか」を人間が説明するのは1回で済み、2回目以降は機械が同じ言葉で説明してくれる、という状態を作るのが目的です。
講師の時間は、機械が判定できないこと（ルール解釈・要件の削り方・レビューの質）に使ってください。

**個人開発ではこの効果がチーム開発のときより大きくなります。**
チームなら「それ触っちゃダメじゃない？」と隣の人が言ってくれますが、1人だと誰も言いません。
**機械が唯一の隣の人**になります。

### 1-3. ハーネスは5層。Layer 4 だけがバイパス不能

| 層 | 実体 | 役割 | 抜けられるか |
|---|---|---|---|
| Layer 1 予防 | `scripts/scaffold-game.mjs` / `templates/game/` | そもそも間違った形を作らせない | 手で書けば抜けられる |
| Layer 2 伝える | `CLAUDE.md` / `src/games/CLAUDE.md` | 何が禁止かを AI と人間の両方に伝える | 読まなければ抜けられる |
| Layer 3 その場で止める | `.claude/settings.json` の deny / `.claude/hooks/` | 範囲外の編集・依存追加・迂回コマンドを止める | `CARD_ARCADE_HARNESS=off` で抜けられる |
| **Layer 4 コミットさせない** | **ESLint / `tests/contract/` / `.githooks/pre-commit`** | **境界違反をコミット不能・マージ不能にする** | **pre-commit は `--no-verify` で抜けられるが、ESLint と契約テストは CI で必ず走る** |
| Layer 5 マージさせない | `.github/workflows/ci.yml` / `CODEOWNERS` / ブランチ保護 | 赤い Pull Request をマージできなくする | 管理者権限が要る |

**「Layer 4 だけがバイパス不能」の意味**を正確に押さえてください。

- Layer 1〜3 は参加者の手元にあります。手元にあるものは必ず抜けられます。フックを承認しない、
  環境変数を立てる、Claude Code を使わずエディタで直接書く — どれも可能です。
- Layer 4 の実体は **ソースコードそのものの性質** です。`logic.ts` に `Math.random()` が書いてあるという事実は、
  誰がどんな手順でコミットしても消えません。`npm run lint` と `npm test` はそれを必ず見つけます。
- そして CI（Layer 5）は必ず Layer 4 を実行します。つまり **Layer 4 の判定からは逃げられない**。
- Layer 5 は講師（管理者）が外せます。だから Layer 5 は「最後の砦」ではなく「**運用の砦**」です。

この役割分担は当日 Step 4 のデモでそのまま説明できます。
「手元の3つは君の味方（早く気づかせるためのもの）で、CI の1つは全員の味方（壊れたものを入れないためのもの）」
という言い方が通りやすいです。

### 1-4. 単一の真実源

参加者・ゲーム・保護対象パスは **`harness/config.json` の1箇所だけ**に書いてあります。
`scope-guard` / `scaffold` / 契約テスト / `.claude` のフック / `doctor` / `status` / `score` /
`build-issue-bodies` / `setup-github.mjs` が **すべてこのファイルを読みます。**
**当日、担当を入れ替える必要が出たらここだけを直してください。**

配列の名前は `participants` です（チーム制の名残りの `teams` はもうありません）。1要素が1人です。

```json
{
  "participant": "participant-1",
  "displayName": "担当1",
  "gameId": "babanuki",
  "name": "ババ抜き",
  "difficulty": "easy",
  "issue": 1,
  "reviews": "participant-2"
}
```

- `participant` … 参加者の ID。**当日ここを GitHub のアカウント名に書き換えます**（2-3）
- `displayName` … 画面と Issue とセッション開始メッセージに出る表示名
- `reviews` … **この人がレビューする相手**の `participant`

コード側では `GameManifest` の `owner` フィールドがこの `participant` を指します
（型は `src/core/types.ts` の `OwnerId`。中身は文字列です）。
アーケードの並び順は `src/app/registry/gameOrder.ts` が `harness/config.json` の並び順から作ります。
**参加者が自分のタイルを先頭に持ってくることはできません。**

#### リングの並びには意図があります

**上級を担当している人がレビューするのは、初級のゲームにしてあります。**

- 担当2（大富豪・上級）→ レビューするのは担当3（神経衰弱・初級）
- 担当4（ポーカー・上級）→ レビューするのは担当5（ぶたのしっぽ・初級）

上級の2人は127分の時点でまだ実装が押している可能性が高いので、**レビューの負担を最初から軽くしてあります。**

**逆に、上級の Pull Request をレビューするのは、早く終わる初級の担当**にしてあります。

- 担当2（大富豪）の PR をレビューするのは担当1（ババ抜き・初級）
- 担当4（ポーカー）の PR をレビューするのは担当3（神経衰弱・初級）

差分がいちばん大きい2本に、**いちばん時間の余っている2人**が当たる形です。
**この設計を当日の最初（10〜18分の担当確認）で参加者に説明してください。**
「なぜ自分がこの人を見るのか」が分かっていると、127分からのレビューの入りが速くなります。

#### リングが切れると2人が止まる

輪になっているので、**どこか1人が Pull Request を出さないと、その人をレビューする担当がやることを失います。**
チーム制なら「他のメンバーが代わりに出す」がありましたが、**個人開発にはそれがありません。**
1人が止まると、確実に2人分の時間が死にます。
4章の「127分に Draft PR が出ていない」を介入ラインに入れているのはこのためです。

### 1-6. 個人開発にしたことで、運営はここが難しくなる

**この章がこの文書でいちばん重要です。** チーム制のときと同じ運営をすると必ず取りこぼします。

#### (1) 詰まりが表面化しない

チーム開発では、詰まっている人の周りで会話が起きます。
「これどうなってるんだっけ」「Issue にはこう書いてある」——**その声が講師に聞こえます。**

**個人開発では、詰まった人は黙ります。** 画面に向かったまま、20分でも30分でも止まります。
本人に自覚がないこともあります（AI と往復しているうちに時間だけが過ぎる形が典型です）。
**「静かな部屋 = 順調」ではありません。静かな部屋のほうが危険です。**

埋め方は3つあります。

1. **`npm run status` を70分・95分・118分の3回投影し、遅れている人を名指しで拾う**（3-4）
2. **机間巡視で「手が止まっていないか」「`verify` を通さずに進んでいないか」だけを見る**（3-5）
3. **`/stuck` を「詰まったら打つもの」ではなく「15分進まなければ打つもの」として最初に宣言する**

#### (2) `/stuck` の重要度が上がる

チームなら相談相手が2〜4人います。**個人開発では相談相手が講師しかいません。**
`/stuck` はコードを変更せずに、ブランチ・`scope`・`lint`・`typecheck`・`test` の事実を並べて出すコマンドです。
**講師はその出力を見るだけで判断できます。** 状況説明を口頭で聞き出す時間が要りません。

当日の最初に、次のとおり宣言してください。

> 「**15分やって1ミリも進まなかったら、`/stuck` を打って私を呼んでください。**
> 相談は遅れではありません。手順です。
> 今日は1人で作っているので、**黙っていると誰にも気づかれません。**」

`/stuck` にはもう1つ効果があります。**詰まった人が焦って大きな作り直しを始める事故を防ぎます。**
このコマンドは `Edit` / `Write` が禁止されているので、**絶対にコードを壊しません。**

#### (3) Issue のチェックリストが唯一の進捗指標になる

チーム制では「今どこ？」と聞ける相手が同じ島にいました。個人開発ではいません。
**外から進捗が見えるのは、Issue の必須要件のチェックボックスだけです。**

Issue 本文は `docs/games/<ゲームID>.md` から機械生成していて、必須要件がそのままチェックリストになっています。
当日の最初に次を徹底してください。

> 「**1つ終わるたびに Issue のチェックを入れてください。**
> 私が見るのはそこだけです。チェックが増えていない人には私から声をかけます」

チェックが動いていない人は、**進んでいないか、進捗を出す習慣が抜けているかのどちらか**です。
どちらも介入の対象です。

#### (4) レビューは1対1で、逃げ場がない

チームなら、1人が見落としても他のメンバーが気づきます。
**個人開発では、あなたのコードを見る他人はレビュアー1人だけです。** 見落としたらそのまま `main` に入ります。

だから、レビューの手順を守らせる仕組みがチーム制のときより重要になります。
**`gh pr checkout` して実際に遊ぶ**、という手順を飛ばさせないでください（3-5 の (4) と 4章 145分）。
`docs/review-guide.md` のミッションカードは、**そのゲームの壊れやすい所を先に指定してあります。**
「どこを見ればいいか分からない」で止まらないようにするためのものです。

#### (5) 代わりに、無くなった手間もある

正直に書いておくと、個人開発のほうが楽になった部分もあります。

- 役割分担（Driver / Navigator / …）の説明が丸ごと要らなくなり、**開始18〜24分が軽くなりました**
- 「1人が全部操作していないか」を見る必要がなくなりました（全員が1人で全部操作します）
- チーム内の合意形成で止まることがなくなり、**削る判断が本人と講師の2者で完結します**

**空いた講師の時間は、そのまま (1) の見回りに使ってください。**

## 2. 事前準備チェックリスト（前日まで）

### 2-1. 誰にどのゲームを渡すか（**講師の判断ポイント**）

9本のゲームは **初級3 / 中級4 / 上級2** に分かれています。
**難易度はゲーム側に固定されていて、人に合わせて変えられません。**
だから「誰にどれを渡すか」が、当日の完走率をいちばん左右します。

| 難易度 | ゲーム | 渡す相手 |
|---|---|---|
| 初級（3本） | ババ抜き / 神経衰弱 / ぶたのしっぽ | **経験の浅い人。** React も Git も初めてに近い人はここ |
| 中級（4本） | スピード / 七並べ / ダウト / ページワン | 業務で1つはアプリを書いたことがある人 |
| 上級（2本） | 大富豪 / ポーカー | **慣れている人。** 自分でテストを書いた経験がある人 |

原則は1つだけです。

> **経験の浅い人に初級を、慣れている人に上級を渡す。**

「成長のために背伸びさせる」は180分ではやらないでください。
上級を経験の浅い人に渡すと、**70分で Step1 が終わらず、118分で削る決断をしても間に合いません。**
背伸びさせたいなら、初級を渡したうえで「発展課題まで行ってみて」と言うほうが確実です。

#### 上級2本の違い — **ポーカーのほうが見積もりが立てやすい**

上級は2本ありますが、**難しさの質が違います。** ここを取り違えると割り当てを間違えます。

| | 大富豪（担当2 / #6） | ポーカー（担当4 / #8） |
|---|---|---|
| 難しさの中身 | **ルールが多く、状態が絡み合う** | **役の判定1点に集中している** |
| 状態遷移 | 場・パス・場流れ・8切り・革命・順位。手番の進み方がルールごとに変わる | **一直線。** 配る → 一度だけ交換 → 勝負 |
| プレイ人数 | 4人（あなた + CPU3人） | 2人（あなた + CPU1人） |
| 時間の使いどころ | Step1 を3段（出せる判定 → 8切り → 革命）に割って積み上げる | **時間の8割を `evaluateHand` に使う。** 役9種類の判定を書き切れるか |
| 詰まったときの見え方 | 「どこで詰まっているか」が本人にも分かりにくい | 「役のテストが何件緑か」で**外から数えられる** |
| 削りやすさ | 革命 → CPU の複数枚出し → 8切り、と段階的に削れる | 同じ役どうしの比較 → 役を7種類に減らす、と削れる |

**ポーカーは上級ですが、状態遷移が単純なので見積もりが立ちます。**
`docs/games/poker.md` は「75分の時点で必須テスト8件のうち7件が緑」を目安に置いてあり、
**講師は緑のテスト件数を数えるだけで進み具合が分かります。**

**大富豪はそうはいきません。** ルールどうしが干渉するので、
「8切りは動くが革命を入れたら場流れが壊れた」のような戻りが起きます。
`docs/games/daifugo.md` は Step1 を3段（60分 / 68分 / 75分）に割っていますが、
**この3段のどこで止まっているかは、本人に聞かないと分かりません。**

割り当ての結論はこうです。

- **いちばん経験のある人 → 大富豪（担当2）。** 戻りが起きても自力で立て直せる人を置く
- **2番目に経験のある人 → ポーカー（担当4）。** 判定ロジックを黙々と書ける人が向く
- 上級を任せられる人が1人しかいないときは、**大富豪を経験の浅い人に渡さないでください。**
  そのときは大富豪の「革命」を最初から外して配る（`docs/games/daifugo.md` の削る順番の2番）と講師が宣言します

### 2-2. リポジトリ側（**この順番で実行する**）

順番に意味があります。特に 5 → 6 の順を逆にすると、必須チェックの名前が確定していない状態で
ブランチ保護がかかり、**全 Pull Request が永久に pending になって当日マージできなくなります。**

**すべて Node のスクリプトで行います。** PowerShell 版（`.ps1`）はもうありません。
理由は `scripts/setup-github.mjs` の先頭に書いてあります（企業端末の ExecutionPolicy、
PowerShell 5.1 が BOM なし UTF-8 の日本語スクリプトを壊すこと、Mac の参加者がいても同じものが動くこと）。

実行はリポジトリのルート（`C:\Users\daisu\project\card_arcade`）で行います。
**どのコマンドにも `--dry-run` を付けられます。** 何が起きるかだけ先に見たいときに使ってください。

#### 1. 参加者を collaborator に招待し、**全員に承諾させる**

**当日 403 が出る原因の第1位がこれです。** 招待メールを開いていない参加者は `git push` も `gh pr create` も落ちます。

```powershell
node scripts/setup-github.mjs collaborators <GitHubユーザー名1> <GitHubユーザー名2> ...
```

`permission=push` で招待されます。admin は渡しません。
実行すると、招待に続けて**現在の共同作業者**と**未承諾の招待**が両方出ます。

引数なしで実行すると、**確認だけ**を行います。前日と当日の朝に1回ずつ打ってください。

```powershell
node scripts/setup-github.mjs collaborators
```

「未承諾の招待」が **`なし（全員が承諾済みです）` になるまで**催促します。
未承諾のまま当日を迎えた人は、**その場で招待し直し、本人のブラウザで
https://github.com/Daisuke0719/card_arcade を開かせてください。** 画面上部に承諾ボタンが出ます。

**個人開発では、未承諾の人を他の人で肩代わりできません。**
チーム制なら「承諾済みの人が操作を代わる」で逃げられましたが、
**今回は1人1 Pull Request なので、本人が承諾するまでその人の成果は出せません。**
前日までに必ず空にしてください。

#### 2. ラベルを作る

```powershell
node scripts/setup-github.mjs labels
```

`--force` 付きで作るので、何度実行しても安全です。作られるのは18個です。

- `game` … 参加者が担当するゲームの実装
- `participant-1` 〜 `participant-9` … 誰の Issue かを表す9個
- `difficulty:easy` / `difficulty:normal` / `difficulty:hard`
- `stretch-goal` / `blocked` / `bug` / `core-change` / `harness:override`

最後の `harness:override` は**講師専用**です（6章 補足A）。**参加者には存在を教えないでください。**

#### 3. Issue の本文を組み立てる

```powershell
node scripts/build-issue-bodies.mjs
```

`docs/games/<ゲームID>.md`（ルールの正典）から、必須要件・実装の進め方・削る順番・発展課題を転記して、
`.github/issue-bodies/<participant>-<ゲームID>.md` を9本作ります。

**Issue 本文を手で書かないでください。** 手で書くと、正典と Issue でルールがずれます。
ずれた状態で当日を迎えると、**参加者は Issue を見て実装し、レビュアーは正典を見て指摘する**ことになり、
127分からのレビューが噛み合わなくなります。

#### 4. マイルストーンと Issue を作る

```powershell
node scripts/setup-github.mjs milestone
node scripts/setup-github.mjs issues
```

Issue は9本作られ、`game` / `participant-N` / `difficulty:*` のラベルと
マイルストーン `CARD ARCADE v1` が付きます。

**発行された Issue 番号は、スクリプトが `harness/config.json` に自動で書き戻します。**
手で書き写す必要はありません。書き戻しが終わると、次にやることが画面に出ます。

```powershell
node scripts/build-issue-bodies.mjs
npm run scaffold -- --all --force
npm run verify
```

**この3つを必ず実行してください。** Issue 番号が入ったことで本文中の `#<番号>` が確定し、
雛形とアーケードのタイルにも反映されます。
ここが `0` のままだと、Claude Code のセッション開始メッセージ（`.claude/hooks/session-brief.mjs`）に
「担当 Issue: #未設定」と出て、参加者が自分の Issue を探すところで数分を失います。

なお、`harness/config.json` の `issue` に**すでに番号が入っている行は作り直されません**（「済み #6」と出ます）。
番号がずれると全部の参照が壊れるので、**意図的にそうしてあります。**
作り直したいときは、その行の `issue` を `0` に戻してから実行してください。

現状を目で確かめるにはこれです。

```powershell
gh issue list --repo Daisuke0719/card_arcade --limit 20
```
