# 講師ガイド

「Claude Code × GitHub 共同開発ハンズオン — みんなでつくる CARD ARCADE」を運営する人のための文書です。
**当日はこの手順書を使って進行できます。** 事前準備・当日の流れ・介入の基準・緊急時の対応をまとめています。

**この研修は参加者9名が1人1ゲームを担当する形で行います。**
チームには分かれません。各参加者が、調査、実装、テスト、Pull Requestの提出までを担当します。
個人作業にしたことで運営上の注意点も増えます。注意点と対応は1-6で説明します。

今回の版では、参加者はClaude Codeにプロンプトを入力して作業を進めます。
そのまま利用できるプロンプトは `docs/handson-steps.md` に掲載しています。
運営時に確認する内容は1-7で説明します。

参加者向けの文書は次のとおりです。講師が読ませる順番もこの順です。

| 文書 | いつ読ませるか |
|---|---|
| `docs/handson-steps.md` | 当日の最初から最後まで（フェーズ1〜7） |
| `docs/claude-code-guide.md` | Claude Code の頼み方に迷ったとき（3原則とプロンプトの型） |
| `docs/games/<ゲームID>.md` | 担当ゲームのルール文書 |
| `docs/harness.md` | 止められたとき（拒否メッセージの読み方） |
| `docs/troubleshooting.md` | 詰まったとき（T-01〜） |

## 1. 研修の設計意図

### 1-1. 主目的はゲーム制作ではない

ゲームの完成だけが研修の目的ではありません。
共有リポジトリで担当範囲を守り、確認を重ねながら提出まで進める過程を重視します。

この研修では、参加者が次の5つを経験します。

1. 自分の担当範囲がコードで機械的に定義されている状態で作業した
2. `npm run verify` が成功するまで「できました」と言わなかった
3. 他人に読まれる前提で Pull Request を書いた
4. **自分で実際に遊んで**不具合を見つけ、直した（テストが通っただけで終わらせない）
5. マージされ、公開された

ゲームの完成度は、この5項目を満たしたうえで評価します。時間が足りない場合は、ゲーム内の実装項目を減らします。
5章の「省略順」は、この優先順位に沿って定めています。

### 1-2. なぜ「間違いを機械が止める」ようにしてあるのか

9名が1つの `main` を共有するため、口頭での説明だけではルールの見落としが起こり得ます。
破られたときに困るのは破った人ではなく、**他の8名**です。

そこで、この研修では規約を文章ではなく**動くコード**にしてあります。

- 「他人のフォルダを触らないでください」→ `scripts/scope-guard.mjs` が差分を検査し、違反があれば処理を失敗させる
- 「依存を追加しないでください」→ `.claude/settings.json` の deny と `.claude/hooks/guard-bash.mjs` が止める
- 「`logic.ts` に `Math.random()` を書かないでください」→ ESLint が error にする
- 「ESLint を無効化して回り込まないでください」→ `tests/contract/boundaries.contract.test.ts` が違反を検出する
- 「開発サーバーは自分のターミナルで動かしてください」→ `guard-bash.mjs` が `npm run dev` を拒否する

**講師が注意する回数を減らすことが目的ではありません。**
禁止する理由は講師が説明し、同じ違反が起きた場合はツールから同じ案内を返せるようにしています。
講師の時間は、機械が判定できないこと（ルール解釈・要件の削り方・実装の中身）に使ってください。

個人作業では、近くの参加者による指摘を期待できないため、ツールで問題を早期に検出します。

### 1-3. ハーネスは5層。Layer 4 だけがバイパス不能

| 層 | 実体 | 役割 | 抜けられるか |
|---|---|---|---|
| Layer 1 予防 | `scripts/scaffold-game.mjs` / `templates/game/` | 最初から誤った形を作らない | 手作業なら回避できる |
| Layer 2 伝える | `CLAUDE.md` / `src/games/CLAUDE.md` | 禁止事項をClaude Codeと参加者に伝える | 文書を確認しなければ見落とす可能性がある |
| Layer 3 その場で止める | `.claude/settings.json` の deny / `.claude/hooks/` | 範囲外の編集・依存追加・迂回コマンドを止める | `CARD_ARCADE_HARNESS=off` で抜けられる |
| **Layer 4 コミットさせない** | **ESLint / `tests/contract/` / `.githooks/pre-commit`** | **境界違反をコミット不能・マージ不能にする** | **pre-commit は `--no-verify` で抜けられるが、ESLint と契約テストは CI で必ず走る** |
| Layer 5 マージさせない | `.github/workflows/ci.yml` / `CODEOWNERS` / ブランチ保護 | 検証に失敗したPull Requestをマージできなくする | 管理者権限が必要 |

**「Layer 4 だけがバイパス不能」の意味**を正確に押さえてください。

- Layer 1〜3 は参加者の手元にあります。手元にあるものは必ず抜けられます。フックを承認しない、
  環境変数を立てる、Claude Code を使わずエディタで直接書く — どれも可能です。
- Layer 4 の実体は **ソースコードそのものの性質** です。`logic.ts` に `Math.random()` が書いてあるという事実は、
  誰がどんな手順でコミットしても消えません。`npm run lint` と `npm test` はそれを必ず見つけます。
- CI（Layer 5）でも Layer 4 を実行するため、同じ基準で変更内容を検査できます。
- Layer 5は講師が管理者権限で解除できるため、運用によって維持する制限です。

この役割分担は、当日のハーネスのデモ（3-2）で説明します。
手元の検証は問題の早期発見、CIは問題のある変更を `main` に入れないことが目的です。

### 1-4. 設定の参照元

参加者・ゲーム・保護対象パスは `harness/config.json` で管理します。
`scope-guard` / `scaffold` / 契約テスト / `.claude` のフック / `doctor` / `status` / `score` /
`build-issue-bodies` / `setup-github.mjs` が **すべてこのファイルを読みます。**
**当日、担当を入れ替える必要が出たらここだけを直してください。**

配列の名前は `participants` です（チーム制の名残りの `teams` はもうありません）。1要素が1人です。

```json
{
  "participant": "participant-1",
  "displayName": "担当1",
  "gameId": "babanuki",
  "name": "ババ抜き",
  "difficulty": "easy",
  "issue": 1,
  "reviews": "participant-2"
}
```

- `participant` … 参加者の ID。**当日ここを GitHub のアカウント名に書き換えます**（2-3）
- `displayName` … 画面と Issue とセッション開始メッセージに出る表示名

コード側では `GameManifest` の `owner` フィールドがこの `participant` を指します
（型は `src/core/types.ts` の `OwnerId`。中身は文字列です）。
アーケードの並び順は `src/app/registry/gameOrder.ts` が `harness/config.json` の並び順から作ります。
**参加者が自分のタイルを先頭に持ってくることはできません。**

**参加者向けの手順書に、担当名やゲーム名を直接書いていないのも同じ理由です。**
プロンプトはすべて `<ゲームID>` `<Issue番号>` `<相手のPR番号>` というプレースホルダで書いてあるので、
当日 `participant` を GitHub のアカウント名へ差し替えても、手順書を1文字も直さずに済みます。

### 1-6. 個人開発にしたことで、運営はここが難しくなる

この章では、個人作業で特に注意する運営上の違いを説明します。

#### (1) 詰まりが表面化しない

チーム開発では、詰まっている人の周りで会話が起きます。
「これどうなってるんだっけ」「Issue にはこう書いてある」——**その声が講師に聞こえます。**

個人作業では、問題を抱えていても周囲に状況が伝わりにくくなります。
Claude Codeとのやり取りが続いていても、実装が進んでいるとは限りません。
発言の有無ではなく、Issueやコマンドの結果から進み具合を確認してください。

埋め方は3つあります。

1. **`npm run status` を節目ごとに投影し、対応が必要な参加者を確認する**（4章）
2. **机間巡視で「手が止まっていないか」「`verify` を通さずに進んでいないか」だけを見る**（3-3）
3. **「手が止まったら状況を整理して講師に見せる」ことを最初に宣言する**

#### (2) 早めに相談させる仕組みが要る

チームなら相談相手が2〜4人います。**個人開発では相談相手が講師しかいません。**
作業が止まっている参加者には、次のプロンプトを入力してもらいます。
コードを変更せずに、ブランチ・`scope`・`lint`・`typecheck`・`test` の事実だけが並びます。

```text
同じエラーで手が止まっています。<困っていることを一言で> という状態です。

まず git branch --show-current / git status --short / npm run scope / npm test を実行して、
いま起きている事実を集めてください。エラーは最初の1件だけを引用してください。
そのうえで docs/troubleshooting.md と照らし合わせ、次に試すことを1つだけ挙げてください。

コードは変更しないでください。私が講師に相談してから決めます。
```

**講師はその出力を見るだけで判断できます。** 状況説明を口頭で聞き出す時間が要りません。

当日の最初に、次のとおり宣言してください。

> 「**手が止まったら、状況を整理させて私を呼んでください。**
> 作業を続けられない場合は、上の形式で講師に相談してください。
> 今日は1人で作業するため、問題があれば早めに知らせてください。」

この文面には、状況を確認する前に大きな変更を始めないようにする目的もあります。
「コードは変更しないでください」を文面に入れてあるので、事実を集める間にファイルが変わりません。

#### (3) Issue のチェックリストで進み具合を確認する

チーム制では「今どこ？」と聞ける相手が同じ島にいました。個人開発ではいません。
講師は、Issueの必須要件にあるチェックボックスを主な確認材料にします。

Issue 本文は `docs/games/<ゲームID>.md` から機械生成していて、必須要件がそのままチェックリストになっています。
当日の最初に次を徹底してください。

> 「**1つ終わるたびに Issue のチェックを入れてください。**
> 私が見るのはそこだけです。チェックが増えていない人には私から声をかけます」

チェックが更新されていない場合は、実装状況と記録状況の両方を確認してください。

なお、**Issue 本文の書き換え（`gh issue edit`）は参加者の Claude Code からは拒否されます。**
チェックボックスは GitHub の画面で本人がクリックします。
「要件は講師が管理し、進捗は本人が申告する」という線引きを、コマンドの可否で表しています。

#### (4) 代わりに、無くなった手間もある

個人作業にしたことで簡略化できる運営もあります。

- 役割分担（Driver / Navigator / …）の説明は不要になりました
- 各参加者が、自分の担当ゲームに必要な操作をすべて行います
- チーム内の合意形成で止まることがなくなり、**削る判断が本人と講師の2者で完結します**

**空いた講師の時間は、そのまま (1) の見回りに使ってください。**

### 1-7. プロンプト駆動にしたことで、運営はここが変わる

今回の版から、参加者はプロンプトを入力して進めます。
`docs/handson-steps.md` に載せた**コピペできる定型プロンプト**だけで、最初から最後まで通ります。
覚えるスラッシュコマンドはありません。

**最初に認めておくべきことがあります。**

> **この変更は、研修の目的である「AI の出力を確認しながら進めること」と両立しません。**

定型文を配布すると、内容を確認せずに入力することも可能になります。
それでも配ったのは、**プロンプトを自分で考えさせると、そこで大きく時間を失う**からです。
考えさせたいのは「どう頼むか」ではなく「上がってきたものが正しいか」のほうです。

だから、釣り合わせ方をこう決めました。

> **AI に任せる範囲を広げる場合は、参加者が確認する操作を別の場所に分ける。**

その中心が**ターミナル2本体制**です。

| | ターミナルA（Claude Code） | ターミナルB（参加者が操作） |
|---|---|---|
| 常駐 | Claude Code のセッション | **`npm run dev`（研修中は起動したままにする）** |
| やること | 調査・実装の依頼・差分の確認・文章の下書き | 実機で遊ぶ / `npm test` の自分確認 / `gh pr ready` |

**ターミナルA では `npm run dev` を実行できません**（`.claude/hooks/guard-bash.mjs` が拒否します）。
「遊んで判断する」という工程は、**やろうと思ってもターミナルB でしか行えません。**
ルールではなく場所で分けてあるので、講師が同じ注意を9回する必要がありません。

参加者による確認を維持するため、操作する場所を2つのターミナルに分けます。
開発サーバーをターミナルBで動かし、参加者がブラウザを操作して確認します。

#### (1) プロンプトの入力だけで進める参加者が出やすくなる

注意すべき点は、手順書の文面を入力するだけでもフェーズ6まで進められることです。
`npm run status` の画面では順調に見えます。テストも成功します。**数字の上では区別が付きません。**

**手順には中間確認の工程がありません。** 参加者同士のレビューも設けていないため、
気づけるのは**机間巡視（3-3）だけ**です。
ターミナルA だけを見ていてブラウザを触っていない人を、講師が拾ってください。

**入力するだけの参加者を責めないでください。** 手順書の構成がそうさせているなら、改善すべきは運営側です。
拾ったときに言うのは「読んでいないですね」ではなく、
**「いま一度、自分のゲームを最初から最後まで1回遊んでください」**です。

#### (2) ターミナルの役割を開始時に説明する

2つのターミナルを開く前に、それぞれの役割を説明してください。
説明がないと、コマンドを実行する場所を判断できません。

フェーズ1で、ターミナルA（`claude` を起動する画面）とターミナルB（`npm run dev` を動かす画面）を
**実際に1枚ずつ作成します。** 作成を始める前に、次の3行をそのまま伝えてください。

> PowerShell を**2枚**開きます。
> 片方でClaude Codeを起動します（ターミナルA）。もう片方では起動しません（ターミナルB）。
> ターミナルBでは、研修中 `npm run dev` を起動したままにします。

当日のオープニングでもう一度、**「増やした窓はぜんぶ B です。A は1枚だけ」**と言い切ってください。
テスト用にターミナルを追加しても構いません。追加したターミナルはすべてBとして扱います。
**A と B の違いは枚数ではなく、Claude Code が入っているかどうかだけです。**

#### (3) 開発サーバーの停止による表示エラーに対応する

当日は、開発サーバーの停止に関する相談が多くなると見込まれます。主な症状は次のとおりです。

> 「画面が出ません」「さっきまで動いていました」「真っ白です」

まず、ターミナルBで `npm run dev` が動いているか確認します。停止する主な理由は3つあります。

1. テストを打とうとして、`dev` の動いている窓で `Ctrl + C` を押した
2. `gh pr checkout` を実行するために、`dev` を動かしているターミナルを使ってしまった
3. スリープ復帰や PowerShell の再起動で消えた

対処は1つです。**ターミナルB で `npm run dev` を再実行してもらいます。** 原因の説明は後で構いません。

予防として、参加者向けの手順書の「当日の進め方」に、`npm run dev` を止めないことと、
停止した場合は、同じターミナルで再実行することも記載しています。

机間巡視のときは、画面の中身ではなく**タスクバーを見てください。**
PowerShell が1枚しかない人は、その時点で `dev` が止まっています（3-3 の (1)）。

#### (4) プロンプト駆動でも変えていないこと

念のため書いておきます。**次の3つは今回の変更で1ミリも緩めていません。**

- `npm run verify` が成功するまで「できました」と言わせない
- Pull RequestとIssueへの投稿は参加者が行う（`gh pr review` / `gh pr comment` / `gh issue comment` は拒否）
- 画面の確認は、参加者が実際にゲームを操作して行う

**プロンプトで速く進めるようにしたのは、この3つに時間を回すためです。**
この順序を省略している参加者がいないか、講師が当日に確認します。

## 2. 講師の事前準備チェックリスト

### 2-1. 誰にどのゲームを渡すか（**講師の判断ポイント**）

9本のゲームは **初級3 / 中級4 / 上級2** に分かれています。
**難易度はゲーム側に固定されていて、人に合わせて変えられません。**
担当の割り当ては、当日の進み具合に大きく影響します。

| 難易度 | ゲーム | 渡す相手 |
|---|---|---|
| 初級（3本） | ババ抜き / 神経衰弱 / ぶたのしっぽ | **経験の浅い人。** React も Git も初めてに近い人はここ |
| 中級（4本） | スピード / 七並べ / ダウト / ページワン | 業務で1つはアプリを書いたことがある人 |
| 上級（2本） | 大富豪 / ポーカー | **慣れている人。** 自分でテストを書いた経験がある人 |

原則は1つだけです。

> **経験の浅い人に初級を、慣れている人に上級を渡す。**

「成長のために背伸びさせる」は、この研修ではやらないでください。
上級を経験の浅い人に渡すと、**ルールが固まらないまま時間が過ぎ、削る決断をしても間に合いません。**
背伸びさせたいなら、初級を渡したうえで「発展課題まで行ってみて」と言うほうが確実です。

**プロンプト駆動にしたことで、この判断が甘くなりやすくなりました。**
定型プロンプトを入力すれば、実装の途中までは進められるためです。
差が出るのは机間巡視（3-3）と、マージ前に講師がコードを読むときで、
**そこで初めて「中身を分かっていない」が表に出ます。** 割り当ての基準は今までどおりにしてください。

#### 上級2本の違い — **ポーカーのほうが見積もりが立てやすい**

上級は2本ありますが、**難しさの質が違います。** ここを取り違えると割り当てを間違えます。

|---|---|---|

**講師は成功しているテストの件数を数えるだけで進み具合が分かります。**

**大富豪はそうはいきません。** ルールどうしが干渉するので、
たとえば、革命を追加したあとに8切りの場流れが動作しなくなる場合があります。
`docs/games/daifugo.md` はルールを3段に割っていますが、
**この3段のどこで止まっているかは、本人に聞かないと分かりません。**

割り当ての結論はこうです。

- **経験が最も多い人 → 大富豪（担当2）。** 手戻りが起きた場合に自力で対応できる人を割り当てる
- **次に経験が多い人 → ポーカー（担当4）。** 判定ロジックの実装に集中できる人を割り当てる
- 上級を任せられる人が1人しかいないときは、**大富豪を経験の浅い人に渡さないでください。**
  そのときは大富豪の「革命」を最初から外して配る（`docs/games/daifugo.md` の削る順番の2番）と講師が宣言します

### 3-3. 机間巡視で見るポイント

コードの内容ではなく、参加者の作業手順とターミナルの状態を確認します。会場を定期的に巡回してください。
**プロンプト駆動にしたことで、見るべき対象が「誰が操作しているか」から「どちらの窓を使っているか」に変わりました。**

#### (1) 窓が2枚あるか — **最初に見るのはここ**

タスクバーを確認します。PowerShellが1つしか開いていない場合は、`npm run dev` が停止していないか確認してください。

介入の言い方:

> 「ターミナルB を開き直して、`npm run dev` を打ってください。**今日はこれを閉じません。**」

開発サーバーが停止している場合は、画面確認の前に再起動します。
**先に見つけたほうが、9人分では大きな差になります。**

#### (2) ターミナルA の画面を眺めているだけになっていないか

プロンプトを中心に進める場合、この状況が起こりやすくなります。
Claude が出した長い応答をスクロールしているだけで、**B のブラウザを一度も触っていない**状態です。

見分け方: **ブラウザのタブが最小化されたまま、長く開かれていない。**

介入の言い方:

> 「いま一度、ブラウザを開いて自分のゲームを触ってください。**最初から最後まで1回**です。
> テストが成功していても、遊べないゲームは今日の評価では0点と同じです」

#### (3) 遊んで直すループが回っているか

**このフェーズの中身は「ブラウザで遊ぶ → 気づいたことを伝える → 直してもらう → もう一度遊ぶ」です。**
ブラウザを再読み込みせず、ターミナルAだけで作業を続けている場合は、実機確認の手順を案内してください。

見分け方: **ターミナルA だけを見ていて、ブラウザの画面が実装前のまま止まっている。**

介入の言い方:

> 「いま直してもらったところを、ブラウザを再読み込みして触ってください。
> 修正後は、同じ操作を行って問題が解消したことを確認してください。」

もう1つ、**不具合を「直して」とだけ伝えている人**にも声をかけてください。
手順書では、**プランモード（`/plan`）で原因と改善策を計画させてから実行させる**形にしてあります。
計画を確認せずに修正を依頼すると、対象外の箇所が変わり、元の不具合が残ることがあります。

> 「何が起きて、どうなってほしいのかを書いてから頼んでください。
> 作成された計画を確認してから、実装を依頼してください」

#### (4) verify を通さずに Pull Request を Ready にしようとしていないか

見分け方: `gh pr ready` の承認ダイアログが出ているのに、直前に `npm run verify` を打った形跡がない。

介入の言い方:

> 「ready にする前に `npm run verify` です。**GitHub で同じことが起きます。**
> 手元のほうが早く結果が出ます。
> そして `gh pr ready` を押した瞬間から、**相手があなたのコードを触り始めます**」

`.claude/hooks/require-verify.mjs` が1回だけ引き止めますが、**2回目は必ず通します**（作業が詰まらないようにするため）。
つまり、**機械による停止は1回だけです。2回目以降は参加者が判断します。**

#### (5) 問題を共有できているか

**同じエラーの前で止まっている人がいれば必ず声をかけてください。**
参加者は「聞くのが恥ずかしい」で時間を失います。

まず、1-6の(2)にある相談用のプロンプトを入力してもらいます。
事実（ブランチ / `scope` / `lint` / `typecheck` / `test`）が整理されて出るので、
講師はそれを見るだけで判断できます。文面に「コードは変更しないでください」が入っているので、
状況を確認する前に大きな変更を始めることも防げます。

### 3-4. 削る決断の下ろし方

#### 講師が代わりに決める

**参加者に「何を削りますか」と聞いてはいけません。**
参加者は遠慮して削れません。「もう少しで終わりそうなので、このままやります」と必ず言います。
そして終盤になっても何も終わっていません。**これは能力の問題ではなく、立場の問題です。**
だから、**削る決断は講師が代わりに下します。**

言い方はこの形に固定してください。

> 「担当7、七並べの**パス回数の制限は今日は実装しません。**
> **私が決めました。** Issue のその行は無視してください。
> ここからは『7の隣にカードを置ける』ところだけに使ってください。
> **減点にはなりません。** 削ったことを Pull Request の『発展課題・未対応事項』に1行書けば、むしろ加点です」

ポイントは4つです。

- 講師が決めたことを明確に伝える
- 省略する項目を具体的に示す
- 次に行う作業を1つに絞る
- 要件の省略自体は減点にならないことを伝える

#### 省略候補（ルール文書の「時間が足りないときの省略順」から）

実装項目を省略する場合は、次の表を上から順に適用します。各ゲームの詳細は、`docs/games/<ゲームID>.md` の末尾に記載しています。

| 担当 | ゲーム | 最初に削るもの | 次に削るもの |
|---|---|---|---|
| 担当1 | ババ抜き | 発展課題を省略する | 引いたカードを見せる演出（`Phase` から `"revealing"` を外す） |
| 担当2 | 大富豪 | 発展課題を省略する | **革命**（`isRevolution` を `false` 固定。8切りは残す） |
| 担当3 | 神経衰弱 | 見た目の作り込み（めくり演出・凝った CSS） | 経過時間の表示 → ベスト手数の保存（`useHighScore`） |
| 担当4 | ポーカー | 発展課題を省略する | 同じ役どうしの比較（`tiebreak`）を省略して引き分け扱いにする |
| 担当5 | ぶたのしっぽ | 発展課題を省略する | 引き取りの演出（`Phase` から `"collecting"` を外す） |
| 担当6 | スピード | 発展課題を省略する | CPU の速度調整と補充の演出（`CPU_INTERVAL_MS` / `REFILL_DELAY_MS` を固定値にする） |
| 担当7 | 七並べ | 進行ログと演出（`LogPanel`） | CPU の賢さ（`legalMoves` の先頭をそのまま出す）→ パス残り回数の表示 |
| 担当8 | ダウト | `LogPanel` の進行ログ | `revealing` の演出時間（即決着にする） |
| 担当9 | ページワン | 発展課題を省略する | `ScoreBoard` と `LogPanel`（残り枚数をテキストで表示する） |

担当2の大富豪は、講師の判断で必須要件の「革命」を省略できます。
**担当4のポーカーは、役を7種類（フルハウスまで）に減らしても必須テスト8件がそのまま残ります。**

#### 終盤の「削る決断」の下ろし方

時間内に提出できない場合は、講師が実装対象を調整します。変更内容は参加者にも説明してください。

```text
1. 参加者の画面で `npm run verify` を実行してもらい、結果を確認する
2. 最初に失敗した項目を確認する（後続の失敗は、最初の失敗による場合が多い）
3. 失敗の原因が未実装の機能であれば、その機能を実装対象から外すと伝える
4. index.ts の status は "coming-soon" のままにする
5. PR の「発展課題・未対応事項」に、省略した項目を記載してもらう
```

手順4では、`status` を `"ready"` にすると、契約テスト（`tests/contract/manifest.contract.test.tsx`）が
**「`logic.test.ts` に `it(` が3件以上」** と **「画面が例外なく描画でき `GameShell` を使っている」** を要求します。
未完成のまま `"ready"` にすると、契約テストが失敗します。

**`status: "coming-soon"` のままでも Pull Request は出せますし、マージもできます。**
アーケードの一覧には `ComingSoonPanel` が出るだけです。
**未完成のままマージすることは失敗ではありません。**
時間内に完了できない範囲を明示し、動作を確認できた部分だけをマージする方針を説明してください。

要件を省略する方針は、対象者だけでなく全員に共有してください。

## 4. 介入の基準

次の表に示す状態を基準に、講師が対応します。

上から順に、先に起きたものから対応します。

| 見えている状態 | 講師がやること |
|---|---|
| `npm test` が**成功しない**まま作業が止まっている | 状況を確認する。ルール解釈が原因なら講師が解釈を決め、実装が原因ならテストを1本だけ成功させる作業に絞る |
| 画面に**何も表示されていない** | 3-4 の表に従って要件を削る。UI は `GameShell` + `Hand` + `Button` の3つで十分だと指示する |
| **ブラウザで一度も遊ばずに実装を続けている** | その場で止める。「いまの状態を1回遊んでください」とだけ言う（3-3 の (3)） |
| 必須要件の半数以上が未完了 | 講師が3-4の表に従って、実装対象から外す要件を決める |
| 残り時間に対して**まだ実装を続けている** | 実装を中断するよう伝え、その時点の状態でPull Requestの作成を依頼する |
| `npm run verify` が**成功しない** | 未達の必須要件を外し、`status` は `"coming-soon"` のままPull Requestの作成を依頼する |
| Pull Request が **Ready になっていない**（Draft のまま / まだ無い） | 講師が代わりに `.pr-body.md` の骨子を口述する。**Ready にならないとマージできず、その1本が公開されません** |
| マージが**残っている** | 残りを講師がまとめてマージする。CI が失敗したままの PR は `status: "coming-soon"` で通す |

**`npm run status` は節目ごとに投影してください。** 上の表のうち、テスト・画面・PR・マージの状態は
この画面で分かります。

### 画面に出ない介入の基準

**「ブラウザで一度も遊ばずに実装を続けている」だけは、`npm run status` に出ません。**
画面の数字ではなく、人の様子でしか分かりません。

参加者同士のレビューも中間確認も置いていないので、
「進んでいるように見えて中身を知らない」状態を検出できるのは、**机間巡視のこの1回だけ**です。
ここを飛ばすと、**遊べないゲームのまま Pull Request が出ます。**

**この行を削らないでください。**
時間が押しているときに削るのは、ここではなくゲームの中身です（5章）。

## 5. 遅延時の省略順

全体が遅れているときは、**上から順に**切ります。**順番を入れ替えないでください。**

| # | 切るもの | 判断の目安 |
|---|---|---|
| 1 | **発展課題を全面禁止**（`stretch-goal` の Issue を全部閉じる） | **4人以上**がロジック未完 |
| 2 | **UI の作り込み**（CSS Modules 禁止。`GameShell` + `Hand` + `Button` だけ） | **3人以上**が画面未表示 |
| 3 | **PR 本文を簡素にする**（「実装内容」と `Closes #` だけ） | Ready の PR が**6本以下** |
| 4 | **Ready になったものから順にマージする**（9本そろうのを待たない） | マージが**5本以下** |

### 省略できない4項目

次の4項目は、進行が遅れている場合も省略しません。

1. **Draft PRを作成すること** — 実装途中の状態を共有する
2. **Pull Requestを提出すること** — 変更内容を参加者の言葉で説明する
3. **実際に遊んで修正すること** — テスト結果だけで判断せず、画面で動作を確認する
4. **マージすること** — 変更を `main` に反映し、公開する

ブラウザでの動作確認は省略しないでください。机間巡視では、ブラウザを操作していない参加者がいないか確認します。

### 全体が大きく押した場合の非常手段

**マージを待たずに進めます。**

- Ready になった Pull Request から**順にマージしていく**（9本そろうのを待たない）
- `status: "coming-soon"` のままの PR も、CI が成功していればマージする

この場合も、Pull Request本文の説明量は減らせますが、ブラウザでの動作確認は省略しません。
遊んでいないゲームを公開すると、その1本だけが動かないまま公開されます。

## 6. 緊急時の対応（優先度順・**焦っているときに判断させない**）

**上から順に試してください。** 番号の小さいものほど影響範囲が狭く、後始末が要りません。
**4以降は研修後の後始末が必要です。**

### 1. Pull Request 単位の管理者マージ（**最初にこれ**）

CI が失敗している / 時間が無い — **理由を問わず、まずこれで1本だけ通します。**
ブランチ保護は `enforce_admins: false` なので、講師（管理者）は貫通できます。
**影響はその PR 1本だけ**で、他の8人の保護は生きたままです。

```powershell
gh pr merge <番号> --squash --admin --delete-branch
```

### 2. CIが利用できない（GitHub Actionsの障害、Node.jsのバージョン変更など）

9人全員のCIが失敗している場合に限り、この手順を使います。1人だけ失敗している場合は、そのPull Requestの内容を確認してください。

```powershell
gh api -X DELETE "repos/Daisuke0719/card_arcade/branches/main/protection/required_status_checks"
```

**研修後に必ず戻します。**

```powershell
node scripts/setup-github.mjs protect
```

### 4. ブランチ保護を一時的に解除する

3 でも通らないときだけ。**残り時間がわずかで、まだ1本もマージできていない**ような状況専用です。

```powershell
node scripts/setup-github.mjs unprotect
```

**→ 研修後に必ず戻してください。**

```powershell
node scripts/setup-github.mjs protect
```

**この復旧コマンドを、当日の朝にメモ帳へコピーしておいてください。** 焦っているときには探せません。

### 5. 誤ってマージしたものを巻き戻す

`main` が壊れると9人全員が止まります。
**`git reset` ではなく `revert` を使ってください**（履歴を書き換えると他の8人の作業が壊れます）。

```powershell
git switch main
git pull
git log --oneline -5
git revert <コミットSHA>
git push
```

**Squash マージにしているのでマージコミットにはなりません。** `-m 1` は不要です。

変更を戻した場合は、対象の参加者に理由を説明してください。説明がないと、自分の変更が消えた理由を判断できません。

### 6. ハーネス全停止（`CARD_ARCADE_HARNESS=off`）

特定の1台で、フックが誤作動して作業が完全に止まった場合です。

**Claude Code を起動する前に**、その端末の PowerShell で次を実行します。

```powershell
$env:CARD_ARCADE_HARNESS = "off"
claude
```

- 効くのは **`.claude/hooks/` のフック**と **`.githooks/pre-commit`** と **`npm run scope`** だけです。
- **CI は引き続き動作します。** 範囲外を変更するとPull Requestの検証は失敗します。
- **`npm run dev` の拒否も外れます。** 外した端末では、参加者がターミナルA で `dev` を起動できてしまい、
  **ターミナルB の 5173 とポートが衝突します。** 外したことを本人に必ず伝えてください。
- **Claude Code のセッションの中からは設定できません。** `.claude/` は保護領域なので、
  設定ファイルの書き換えもフックが止めます。必ず**起動前**に、講師が端末で設定してください。
- 元に戻すときは PowerShell を閉じるか、次を実行します。

  ```powershell
  Remove-Item Env:CARD_ARCADE_HARNESS
  ```

### 7. 参加者のPCを利用できなくなった

個人作業では担当を別の参加者へ引き継がないため、講師が支援する範囲を明確にします。

対応は次の順です。

1. **予備 PC を1台用意しておく**（前日の準備で最も費用対効果が高い1台です）
2. 予備が無ければ、**講師の端末を貸して本人に操作させる。**
   `gh auth login` を本人のアカウントでやり直せば、その人の Pull Request として出せます
3. どちらもできないときは、**他の参加者の画面を一緒に見てもらう。**
   自分のゲームは提出できない状態を受け入れ、他の人のマージと公開までは一緒に見てもらいます

**3 を選んだ場合は、評価でその人の「実装」を空欄にしないでください。**
状況を自分の言葉で説明できたことを見ます。

### 補足A. 範囲チェックだけが失敗するPull Requestを個別に許可する

**1（`--admin`）を使う前に検討できる、より影響の小さい手**です。

その Pull Request に **`harness:override` ラベル**を付けると、CI の範囲チェックが**警告のみ**に降格します
（`.github/workflows/ci.yml` がラベルを見て `scope-guard.mjs` に `--warn-only` を渡します）。
lint / 型 / テスト / ビルドは**通常どおり必須のまま**です。

```powershell

gh pr checks <番号> --watch
```

**このラベルの存在は参加者に教えないでください。** 教えた瞬間にハーネスが機能しなくなります。

### 補足B. 当日の朝、メモ帳にコピーしておくコマンド

```powershell

npm run status

# Pull Request を1本だけ強引に通す
gh pr merge <番号> --squash --admin --delete-branch

# 保護を戻す（研修後に必ず実行）
```

## 7. 研修前の検証手順（**省略不可**）

**本番の前に実施してください。** やることは2つです。

> 1. **わざと壊して、止まるはずのものが止まるかを確認する。**
> 2. **止めてはいけないものが、承認なしで通るかを確認する。**

拒否される操作だけでなく、許可される操作も確認してください。必要な操作まで拒否されると、当日の作業を進められません。
通しすぎ（止まるはずのものが通る）は、最後に CI が受け止めてくれます。
必要な操作まで拒否されると、その参加者は作業を継続できません。
たとえば、`npm test` の実行ごとに承認が必要になると、9人全員に不要な確認作業が発生します。
**だから 2 の確認を必ず入れてください。**

準備として、講師の端末で作業用のブランチを1本切り、**ターミナルB で `npm run dev` を動かしておきます。**
（当日と同じ2窓の状態にしないと、`npm run dev` の拒否メッセージが正しく出るかを判断できません。）

```powershell
git switch main
git pull
git switch -c feature/speed
```

### 7-6. Windows 固有 — 改行コードで PR 差分が壊れないか

**9台の Windows 端末で改行が揺れると、Pull Request の差分がファイル全体になって読めなくなります。**

```powershell
git config --global core.autocrlf true
git clone https://github.com/Daisuke0719/card_arcade.git C:/temp/ca-crlf-check
cd C:/temp/ca-crlf-check
npm ci
git status
```

**期待する結果: `nothing to commit, working tree clean`。**

ここで大量の変更が表示された場合は、当日に全参加者の `npm run scope` が開始時点から失敗します。
`.gitattributes` が正しく取り込まれているかを確認してください。

確認後、後片付けします。

```powershell
cd C:/Users/daisu/project/card_arcade
Remove-Item -Recurse -Force C:/temp/ca-crlf-check
```

## 8. 想定トラブルと対応

### 8-1. 参加者が自力で解決できるもの

**`docs/troubleshooting.md`（T-01〜）を見せてください。** 講師が説明する必要はありません。
相談用のプロンプト（1-6の (2)）をClaude Codeに入力すると、該当するT-xx番号も提示されます。

**番号で呼べる形にしてあることが、個人開発では効きます。**
チーム制なら「隣の人と同じエラーですね」で共有できましたが、今回は9人が別々のエラーに当たります。
番号が無いと、**講師が同じ説明を9回することになります。**

| 症状 | 対処 | 番号 |
|---|---|---|
| **画面が出ない / 真っ白 / さっきまで動いていた** | **ターミナルBで `npm run dev` を再実行する** | T-14 |
| ポート 5173 が使用中で `dev` が起動しない | 前の `dev` が残っている。プロセスを止めてから起動し直す | T-03 |
| Claude Code が「`npm run dev` は実行できません」と言う | **想定された動作です。** ターミナルBで参加者が起動する | T-33 |
| Claude Code が返ってこない | 監視モードに入るコマンドを打っている。`Ctrl + C` で抜けて `npm test` を使う | T-34 |
| 他の人のブランチでそのコードを直そうとして止められた | **正常です。** 自分のブランチに戻らせる | T-35 |
| `npm run scope` が失敗する | 出力された `git restore ...` を**そのまま**実行する | T-09 |
| 一覧に自分のゲームが出ない | `index.ts` の `export const game` と `id` を確認する | T-13 |
| CPU が1回しか動かない | `useCpuTurn` に渡す関数の作り方。`docs/troubleshooting.md` の該当項目へ | T-16 |
| テストが実行ごとに成功したり失敗したりする | `Math.random()` を使っている。`createRng(seed)` を引数で渡す | T-17 |
| lint が「@ui は使えません」と言う | 画面の処理を `logic.ts` に書いている。`.tsx` へ移す | T-19 |
| `status` を `"ready"` にしたらテストが失敗した | テスト3件以上と描画が要求される。まだ `"coming-soon"` に戻す | T-20 |
| コミットできない | pre-commit が範囲外を検出している。`npm run scope` を見る | T-10 |
| 手元の検証は成功するがCIは失敗する | ブランチ全体の差分を見ている。`git diff origin/main...HEAD` を確認 | T-21 |

### 8-2. プロンプト駆動にしたことで増えたトラブル

| 症状 | 実際に起きていること | 講師の対応 |
|---|---|---|
| 「画面が出ません」 | **ターミナルBの `dev` が止まっている**（1-7の(3)） | `npm run dev` を再実行してもらう。原因の説明は復旧後でよい |
| 「どちらのターミナルで実行しますか」 | ターミナルの役割が分からなくなっている | 「Claude Codeを起動しているほうがA。追加したターミナルはすべてB」と説明する |
| Claude が `npm ci` を実行しようとする | ブランチを移った直後に依存を入れ直そうとしている | **`Esc` で止めさせる。** 依存は全ブランチで同じなので不要。`dev` が動いたままだと Windows では失敗する |
| プロンプトを入力しても進まない | ターミナルAで `dev` や `test:watch` の実行を繰り返している | 拒否メッセージを一緒に読み、ターミナルBで実行してもらう |
| 「Claudeが動くと言っています」 | **ブラウザで一度も操作していない**（3-3の(3)） | 現在の状態で1回プレイしてもらい、結果を確認する |

### 8-3. **講師しか対応できないもの**

次の3種類は、参加者が何をしても直りません。**症状を聞いた瞬間に講師が動いてください。**

#### (1) 権限（403 / Permission denied）

collaboratorの招待を承諾していない場合に起こりやすい問題です。まず招待の状態を確認してください。

```powershell
node scripts/setup-github.mjs collaborators
node scripts/setup-github.mjs collaborators <GitHubユーザー名>
```

参加者に招待メールを開いて承諾してもらいます。**メールが見つからない場合は、参加者のブラウザで
https://github.com/Daisuke0719/card_arcade を開くと画面上部に承諾ボタンが出ます。**

招待を承諾するまで、その参加者は自分のアカウントでPull Requestを作成できません。

#### (2) ブランチ保護（マージできない / チェックが終わらない）

| 症状 | 原因 | 対処 |
|---|---|---|
| 「Expected — Waiting for status to be reported」が消えない | 必須チェックの名前が実際のジョブ名と違う | 6章 3 で必須チェックを外すか、`contexts` を実名に直す |
| CIは成功しているがマージできない | CODEOWNERS が所有する場所を触っている | `gh pr diff <番号>` で範囲を確認。運営領域を触っているなら差し戻す |
| 承認済みなのにマージできない | 単に CI がまだ実行中 | `gh pr checks <番号> --watch` で待つ |
| 何をやってもマージできない | — | 6章 1 の `--admin` で通す |

#### (3) GitHub Pages（公開されない / 404 になる）

```powershell
gh run list --workflow=deploy-pages.yml --limit 5
gh run view --log-failed
```

| 症状 | 原因 | 対処 |
|---|---|---|
| ワークフローが起動しない | Pages の Source が `Deploy from a branch` になっている | Settings > Pages で **GitHub Actions** に変える |
| 404 になる | 初回デプロイがまだ終わっていない | 2〜3分待つ。`gh run list` で `completed` を確認 |
| 画面は出るが真っ白 | `base` の設定 | `vite.config.ts` の `base: "./"` を確認（変更不要のはず） |
| マージしたのに反映されない | デプロイが順番待ちしている | 順に流れます。**待てば必ず反映されます** |

**研修の終わりに全員で公開 URL を開く前に、必ず講師が先に開いて確認してください。**
9本目のマージからデプロイ完了まで2〜3分かかります。**最後のマージは、締めの前に余裕をもって終わらせてください。**

#### (4) ハーネス自体の誤作動

「正しいことをしているのに止められた」という報告が来た場合です。

1. **まず、拒否メッセージと操作内容を照合します。** 担当外の変更や、ターミナルAでの `dev` 実行が原因の場合があります。
   拒否メッセージの全文をそのまま見せてもらってください。
2. 本当に誤作動なら、その端末だけ 6章 6（`$env:CARD_ARCADE_HARNESS = "off"`）で止めます。
3. **CI は引き続き動作するため、範囲外を変更すると検証は失敗します。** そのことを参加者に伝えてください。
4. **`dev` の拒否も外れる**ので、ターミナルA で起動してポートを衝突させないよう本人に念を押してください。
5. 範囲チェックだけが原因でPull Requestの検証が失敗する場合は、6章 補足Aの `harness:override` ラベルをPull Request単位で適用できます。

## 9. 評価

### 9-1. 配点

| 評価項目 | 配点 |
|---|---|
| Issue の必須要件を満たした | 25 |
| 担当範囲を守った | 10 |
| 適切なテストを作成した | 20 |
| Pull Request を分かりやすく書いた | 15 |
| 実際に遊んで不具合を見つけ、修正した | 20 |
| UI とゲームとしての工夫 | 10 |
| **合計** | **100** |

**「ゲームが完成したか」に直接の配点はありません。** これは意図的です。
100点のうち**65点**（担当範囲10 + テスト20 + PR15 + 実機確認20）が**作り方**に振られています。
1章の目的をそのまま数字にしたものです。

**プロンプト駆動にしても、この配点は変えていません。**
むしろ、プロンプトで実装が速くなったぶん、**65点側の比重が実質的に上がっています。**
「速く作れた人」ではなく「自分で確かめて、他人に読ませられる形にできた人」が高くなる、という設計です。

### 9-2. 集計の材料

機械が数えられる部分は、2つのコマンドで集まります。**評価の前に両方を実行してください。**

```powershell
npm run status
node scripts/score.mjs
```

`node scripts/score.mjs` が9人分について出すのは次の4つです。

- 完成宣言（`index.ts` が `status: "ready"` になっているか）
- **テスト件数**（`logic.test.ts` などの `it(` の数）
- Pull Request の有無と状態
- **PR 本文の文字数**

### 9-3. 自動判定できない項目を講師が確認する

`score.mjs` は最後にこう出力します。

> ※ テストの中身の妥当性や命名の分かりやすさは機械では測れません。
> そこは講師が実際に遊び、コードを読んで評価してください。

**この線引き自体が、この研修で伝えたい設計思想です。**
件数や成否は自動で判定し、内容の質は講師が確認します。CIも同じ方針で設計しています。

| 項目 | 自動で確認する内容 | 講師が確認する内容 |
|---|---|---|
| 必須要件を満たした 25 | `status: "ready"` / CI が成功 | Issue の必須要件と実装の突き合わせ。**実際に遊んでみる** |
| 担当範囲を守った 10 | CI の範囲チェックが成功 / `harness:override` を使っていない | — |
| 適切なテストを作成した 20 | テスト件数（3件が下限） | **境界値と異常系があるか。** 正常系だけなら半分以下 |
| PR を分かりやすく書いた 15 | 本文の文字数 / `Closes #` の有無 | **「自分でも不安なところ」が自分の言葉で具体的か** |
| 実際に遊んで修正した 20 | 実装中のコミット数 | 不具合を見つけて修正した履歴があるか。机間巡視の記録（3-3 の (3)）と合わせて確認する |
| UI とゲームの工夫 10 | — | 講師が実際に遊んで判断 |

**未達の要件を記載したこと自体は減点しないでください。**
省略した要件を説明できているかを確認します（手順書でも参加者に同じ指示をしています）。

### 9-4. プロンプト駆動で、講師が手元に残しておくメモ

**数字に出ない情報が1つあります。** 当日その場でしか取れません。

- **ブラウザで実際に遊んで直していたか**（3-3 の (3)）。名前だけ控えておきます

**これを配点に直接足す必要はありません。**
使うのは、`score.mjs` の数字と食い違ったときです。
「テスト件数は多いが、ブラウザで一度も遊んでいなかった」という人は、
**テスト20点を満点にしないでください。** 中身を見ていない可能性が高いからです。

未完成の場合も、実際に遊んで問題を見つけ、修正した過程は評価してください。
それがこの研修で測りたかったものです。

### 9-5. 採点の実務

**研修中に採点しないでください。** 講師の時間は介入に使います。

`npm run status` のスクリーンショットを**節目ごとに**撮っておき、
研修後に `node scripts/score.mjs` の出力と合わせて採点します。
この4枚があれば、「誰がどこで詰まったか」まで後から再現できます。
