「Claude Code × GitHub 共同開発ハンズオン — みんなでつくる CARD ARCADE」を運営する人のための文書です。
**当日はこれ1本で回せます。** 事前準備・時間割・介入の基準・緊急時の逃げ道までここに入っています。

チーム開発ではありません。**調査・実装・テスト・Pull Request・レビューまで、全部を1人でやります。**

## 1. 研修の設計意図

### 1-1. 主目的はゲーム制作ではない

180分でトランプゲームを1本仕上げるのは、正直に言えばおまけです。
**この研修が測っているのは「他人がいる共有リポジトリで、自分の担当範囲を守って完成まで持っていけるか」だけ**です。

参加者が持ち帰る経験は次の5つです。

1. 自分の担当範囲がコードで機械的に定義されている状態で作業した
2. `npm run verify` が緑になるまで「できました」と言わなかった
3. 他人に読まれる前提で Pull Request を書いた
4. **他人のコードを実際に動かして**レビューした（差分を眺めるだけではない）
5. 指摘を受けて直し、マージされ、公開された

ゲームの出来は6番目です。**時間が足りないときに削るのは常にゲームの中身**で、この5つではありません。
5章の「切り捨て順」はこの優先順位をそのまま数字にしたものです。

### 1-2. なぜ「間違いを機械が止める」ようにしてあるのか

9名が1つの `main` を共有します。この規模で口頭ルールは必ず破られます。
破られたときに困るのは破った人ではなく、**他の8名**です。

そこで、この研修では規約を文章ではなく**動くコード**にしてあります。

- 「他人のフォルダを触らないでください」→ `scripts/scope-guard.mjs` が差分を見て落とす
- 「依存を追加しないでください」→ `.claude/settings.json` の deny と `.claude/hooks/guard-bash.mjs` が止める
- 「`logic.ts` に `Math.random()` を書かないでください」→ ESLint が error にする
- 「ESLint を無効化して回り込まないでください」→ `tests/contract/boundaries.contract.test.ts` が落とす
- 「開発サーバーは自分のターミナルで動かしてください」→ `guard-bash.mjs` が `npm run dev` を拒否する

**講師が注意する回数を減らすことが目的ではありません。**
「なぜダメか」を人間が説明するのは1回で済み、2回目以降は機械が同じ言葉で説明してくれる、という状態を作るのが目的です。
講師の時間は、機械が判定できないこと（ルール解釈・要件の削り方・レビューの質）に使ってください。

**個人開発ではこの効果がチーム開発のときより大きくなります。**
チームなら「それ触っちゃダメじゃない？」と隣の人が言ってくれますが、1人だと誰も言いません。
**機械が唯一の隣の人**になります。

### 1-3. ハーネスは5層。Layer 4 だけがバイパス不能

| 層 | 実体 | 役割 | 抜けられるか |
|---|---|---|---|
| Layer 1 予防 | `scripts/scaffold-game.mjs` / `templates/game/` | そもそも間違った形を作らせない | 手で書けば抜けられる |
| Layer 2 伝える | `CLAUDE.md` / `src/games/CLAUDE.md` | 何が禁止かを AI と人間の両方に伝える | 読まなければ抜けられる |
| Layer 3 その場で止める | `.claude/settings.json` の deny / `.claude/hooks/` | 範囲外の編集・依存追加・迂回コマンドを止める | `CARD_ARCADE_HARNESS=off` で抜けられる |
| **Layer 4 コミットさせない** | **ESLint / `tests/contract/` / `.githooks/pre-commit`** | **境界違反をコミット不能・マージ不能にする** | **pre-commit は `--no-verify` で抜けられるが、ESLint と契約テストは CI で必ず走る** |
| Layer 5 マージさせない | `.github/workflows/ci.yml` / `CODEOWNERS` / ブランチ保護 | 赤い Pull Request をマージできなくする | 管理者権限が要る |

**「Layer 4 だけがバイパス不能」の意味**を正確に押さえてください。

- Layer 1〜3 は参加者の手元にあります。手元にあるものは必ず抜けられます。フックを承認しない、
  環境変数を立てる、Claude Code を使わずエディタで直接書く — どれも可能です。
- Layer 4 の実体は **ソースコードそのものの性質** です。`logic.ts` に `Math.random()` が書いてあるという事実は、
  誰がどんな手順でコミットしても消えません。`npm run lint` と `npm test` はそれを必ず見つけます。
- そして CI（Layer 5）は必ず Layer 4 を実行します。つまり **Layer 4 の判定からは逃げられない**。
- Layer 5 は講師（管理者）が外せます。だから Layer 5 は「最後の砦」ではなく「**運用の砦**」です。

この役割分担は当日 Step 4 のデモでそのまま説明できます。
「手元の3つは君の味方（早く気づかせるためのもの）で、CI の1つは全員の味方（壊れたものを入れないためのもの）」
という言い方が通りやすいです。

### 1-4. 単一の真実源

参加者・ゲーム・保護対象パスは **`harness/config.json` の1箇所だけ**に書いてあります。
`scope-guard` / `scaffold` / 契約テスト / `.claude` のフック / `doctor` / `status` / `score` /
`build-issue-bodies` / `setup-github.mjs` が **すべてこのファイルを読みます。**
**当日、担当を入れ替える必要が出たらここだけを直してください。**

配列の名前は `participants` です（チーム制の名残りの `teams` はもうありません）。1要素が1人です。

```json
{
  "participant": "participant-1",
  "displayName": "担当1",
  "gameId": "babanuki",
  "name": "ババ抜き",
  "difficulty": "easy",
  "issue": 1,
  "reviews": "participant-2"
}
```

- `participant` … 参加者の ID。**当日ここを GitHub のアカウント名に書き換えます**（2-3）
- `displayName` … 画面と Issue とセッション開始メッセージに出る表示名
- `reviews` … **この人がレビューする相手**の `participant`

コード側では `GameManifest` の `owner` フィールドがこの `participant` を指します
（型は `src/core/types.ts` の `OwnerId`。中身は文字列です）。
アーケードの並び順は `src/app/registry/gameOrder.ts` が `harness/config.json` の並び順から作ります。
**参加者が自分のタイルを先頭に持ってくることはできません。**

**参加者向けの手順書に、担当名やゲーム名を直接書いていないのも同じ理由です。**
プロンプトはすべて `<ゲームID>` `<Issue番号>` `<相手のPR番号>` というプレースホルダで書いてあるので、
当日 `participant` を GitHub のアカウント名へ差し替えても、手順書を1文字も直さずに済みます。

#### リングの並びには意図があります

**上級を担当している人がレビューするのは、初級のゲームにしてあります。**

- 担当2（大富豪・上級）→ レビューするのは担当3（神経衰弱・初級）
- 担当4（ポーカー・上級）→ レビューするのは担当5（ぶたのしっぽ・初級）

上級の2人は115分の時点でまだ実装が押している可能性が高いので、**レビューの負担を最初から軽くしてあります。**

**逆に、上級の Pull Request をレビューするのは、早く終わる初級の担当**にしてあります。

- 担当2（大富豪）の PR をレビューするのは担当1（ババ抜き・初級）
- 担当4（ポーカー）の PR をレビューするのは担当3（神経衰弱・初級）

差分がいちばん大きい2本に、**いちばん時間の余っている2人**が当たる形です。
**この設計を当日の最初（10〜18分の担当確認）で参加者に説明してください。**
「なぜ自分がこの人を見るのか」が分かっていると、115分からのレビューの入りが速くなります。

#### リングが切れると2人が止まる

輪になっているので、**どこか1人が Pull Request を出さないと、その人をレビューする担当がやることを失います。**
チーム制なら「他のメンバーが代わりに出す」がありましたが、**個人開発にはそれがありません。**
1人が止まると、確実に2人分の時間が死にます。
4章の「127分に Pull Request が Ready になっていない」を介入ラインに入れているのはこのためです。

### 1-6. 個人開発にしたことで、運営はここが難しくなる

**この章がこの文書でいちばん重要です。** チーム制のときと同じ運営をすると必ず取りこぼします。

#### (1) 詰まりが表面化しない

チーム開発では、詰まっている人の周りで会話が起きます。
「これどうなってるんだっけ」「Issue にはこう書いてある」——**その声が講師に聞こえます。**

**個人開発では、詰まった人は黙ります。** 画面に向かったまま、20分でも30分でも止まります。
本人に自覚がないこともあります（AI と往復しているうちに時間だけが過ぎる形が典型です）。
**「静かな部屋 = 順調」ではありません。静かな部屋のほうが危険です。**

埋め方は3つあります。

1. **`npm run status` を70分・95分・118分の3回投影し、遅れている人を名指しで拾う**（3-3）
2. **机間巡視で「手が止まっていないか」「`verify` を通さずに進んでいないか」だけを見る**（3-4）
3. **`/stuck` を「詰まったら打つもの」ではなく「15分進まなければ打つもの」として最初に宣言する**

#### (2) `/stuck` の重要度が上がる

チームなら相談相手が2〜4人います。**個人開発では相談相手が講師しかいません。**
`/stuck` はコードを変更せずに、ブランチ・`scope`・`lint`・`typecheck`・`test` の事実を並べて出すコマンドです。
**講師はその出力を見るだけで判断できます。** 状況説明を口頭で聞き出す時間が要りません。

当日の最初に、次のとおり宣言してください。

> 「**15分やって1ミリも進まなかったら、`/stuck` を打って私を呼んでください。**
> 相談は遅れではありません。手順です。
> 今日は1人で作っているので、**黙っていると誰にも気づかれません。**」

`/stuck` にはもう1つ効果があります。**詰まった人が焦って大きな作り直しを始める事故を防ぎます。**
このコマンドは `Edit` / `Write` が禁止されているので、**絶対にコードを壊しません。**

#### (3) Issue のチェックリストが唯一の進捗指標になる

チーム制では「今どこ？」と聞ける相手が同じ島にいました。個人開発ではいません。
**外から進捗が見えるのは、Issue の必須要件のチェックボックスだけです。**

Issue 本文は `docs/games/<ゲームID>.md` から機械生成していて、必須要件がそのままチェックリストになっています。
当日の最初に次を徹底してください。

> 「**1つ終わるたびに Issue のチェックを入れてください。**
> 私が見るのはそこだけです。チェックが増えていない人には私から声をかけます」

チェックが動いていない人は、**進んでいないか、進捗を出す習慣が抜けているかのどちらか**です。
どちらも介入の対象です。

なお、**Issue 本文の書き換え（`gh issue edit`）は参加者の Claude Code からは拒否されます。**
チェックボックスは GitHub の画面で本人がクリックします。
「要件は講師が管理し、進捗は本人が申告する」という線引きを、コマンドの可否で表しています。

#### (4) レビューは1対1で、逃げ場がない

チームなら、1人が見落としても他のメンバーが気づきます。
**個人開発では、あなたのコードを見る他人はレビュアー1人だけです。** 見落としたらそのまま `main` に入ります。

だから、レビューの手順を守らせる仕組みがチーム制のときより重要になります。
**`gh pr checkout` して実際に遊ぶ**、という手順を飛ばさせないでください（3-4 の (4) と 4章 145分）。
`docs/games/<ゲームID>.md` の「レビュアー向けミッション」は、**そのゲームの壊れやすい所を先に指定してあります。**
「どこを見ればいいか分からない」で止まらないようにするためのものです。

#### (5) 代わりに、無くなった手間もある

正直に書いておくと、個人開発のほうが楽になった部分もあります。

- 役割分担（Driver / Navigator / …）の説明が丸ごと要らなくなり、**開始18〜24分が軽くなりました**
- 「1人が全部操作していないか」を見る必要がなくなりました（全員が1人で全部操作します）
- チーム内の合意形成で止まることがなくなり、**削る判断が本人と講師の2者で完結します**

**空いた講師の時間は、そのまま (1) の見回りに使ってください。**

### 1-7. プロンプト駆動にしたことで、運営はここが変わる

今回の版から、参加者は**プロンプトを打って**進みます。
スラッシュコマンド8本（`/kickoff` `/implement` `/verify` `/pr` `/review` `/fix-review` `/stuck` `/handoff`）と、
`docs/handson-steps.md` に載せた**コピペできる定型プロンプト**だけで Step 1 から Step 18 まで通ります。

**最初に認めておくべきことがあります。**

> **この変更は、この研修の主目的（AI に丸投げしない）と構造的に逆向きです。**

打つ文面を配れば配るほど、参加者は「考えずに打つ」ことができます。
それでも配ったのは、**プロンプトを自分で考えさせると、180分のうち30分以上がそこで溶ける**からです。
考えさせたいのは「どう頼むか」ではなく「上がってきたものが正しいか」のほうです。

だから、釣り合わせ方をこう決めました。

> **丸投げできる範囲を広げたぶん、丸投げできない場所を物理的に切り出す。**

その中心が**ターミナル2本体制**です。

| | ターミナルA（Claude Code） | ターミナルB（自分の手だけ） |
|---|---|---|
| 常駐 | Claude Code のセッション | **`npm run dev`（研修中つけっぱなし）** |
| やること | 調査・計画・実装・差分読み・下書き | 実機で遊ぶ / `npm test` の自分確認 / `gh pr ready` / Approve / `gh pr checkout` / テストを疑う儀式 |

**ターミナルA では `npm run dev` が物理的に起動できません**（`.claude/hooks/guard-bash.mjs` が拒否します）。
「遊んで判断する」という工程は、**やろうと思ってもターミナルB でしか行えません。**
ルールではなく場所で分けてあるので、講師が同じ注意を9回する必要がありません。

人間の確認が消えないようにする機構は6つあり、参加者向けの手順書にも同じ表を出してあります。

| # | 機構 | 出てくる Step | 講師が現場で見るもの |
|---|---|---|---|
| 1 | ターミナル2本体制 | 全 Step | **窓が2枚あるか。** B に `dev` の出力が流れているか |
| 2 | `/handoff` で事実と違う行を1つ探す | Step 9 / Step 12 の直前 | 「1行も見つからなかった」と言う人 |
| 3 | 遊ぶ前に壊し方を3つ手で書く | Step 10（自分）/ Step 13（相手） | 紙かエディタに3行あるか |
| 4 | テストを疑う儀式を A から隔離 | Step 11 | **その5分、A に何も打っていないか** |
| 5 | レビュアーを検問にする | Step 13 | 「レビューしてほしい点」への指摘が出ているか |
| 6 | 講師の口頭1問 | Step 9 | **3-3 で講師が自分の口で聞く**（省略不可） |

#### (1) 「プロンプトを打つだけの人」が出やすくなる

**これが最大の副作用です。** 手順書のとおりに打てば、中身を1行も読まないまま Step 12 までは進めます。
`npm run status` の画面では順調に見えます。テストも緑です。**数字の上では区別が付きません。**

**区別が付くのは、機構5と機構6の2か所だけです。**

- **機構5（レビュアーの検問）** — Step 13 で、相手の PR の「レビューしてほしい点」が具体的かを確かめさせます。
  自分のコードを読んでいない人は、ここを**書けません。** テンプレのまま出てきます。
  そしてレビュアーがそれ自体を指摘するので、**読んでいないことが本人と相手の両方に見えます。**
- **機構6（講師の口頭1問）** — 3-3 で、講師が1人ずつに口頭で聞きます。**省略しないでください。**
  進みすぎている人を止められるのは、この時刻だけです。

**「打つだけの人」を責めないでください。** 手順書がそう作られている以上、そうなるのは設計の側の責任です。
拾ったときに言うのは「読んでいないですね」ではなく、
**「今この5分で `logic.ts` を上から読んでください。あとで必ず取り返せます」**です。

#### (2) ターミナル2本体制は**前日に告知する**

**当日いきなり「窓を2枚開いてください」と言うと必ず混乱します。**
どちらで何を打つのかが分からなくなり、開始30分で「どっちで打つんでしたっけ」が9人分飛んできます。

事前課題の P-4（ターミナルA を作る）と P-6（ターミナルB を作る）で**すでに1回作らせてあります。**
前日の案内には、次の3行をそのまま入れてください。

> 明日は PowerShell を**2枚**開きます。


- 必須チェック: `verify` 1本のみ

### 3-2. Step 4 講師デモ「ハーネス一周」の台本（8分）

### 3-3. Step 9（70〜75分）中間チェックポイント — **口頭1問は省略不可**

**進み具合がよい人にも、必ず聞いてください。** むしろ**進みすぎている人にこそ聞きます。**

### 3-4. 机間巡視で見るポイント

コードは見なくて構いません。**人の動き方と、窓の状態だけを見ます。** 1周3分、5〜6周してください。
**プロンプト駆動にしたことで、見るべき対象が「誰が操作しているか」から「どちらの窓を使っているか」に変わりました。**

#### (1) 窓が2枚あるか — **最初に見るのはここ**

**タスクバーを見てください。** PowerShell が1枚しかない人は、その時点で `npm run dev` が止まっています。

介入の言い方:

> 「ターミナルB を開き直して、`npm run dev` を打ってください。**今日はこれを閉じません。**」

止まっていることに本人が気づくのは、たいてい「画面が出ません」と言い出す10分後です。
**先に見つけたほうが、9人分で30分は変わります。**

#### (2) ターミナルA の画面を眺めているだけになっていないか

**プロンプト駆動でいちばん増えた形がこれです。**
Claude が出した長い応答をスクロールしているだけで、**B のブラウザを一度も触っていない**状態です。

見分け方: **ブラウザのタブが最小化されたまま、10分以上開かれていない。**

介入の言い方:

> 「今から2分だけ、ブラウザを開いて自分のゲームを触ってください。**最初から最後まで1回**です。
> テストが緑でも遊べないゲームは、今日の評価では0点と同じです」

#### (3) Step 11 の儀式を、ターミナルA から隔離できているか（95〜105分）

**この5分だけは、A に1文字も打たないのが正解です。**
テストの期待値をわざと逆にして、赤くなるのを自分の目で見る時間です。

見分け方: **儀式の時間帯に、A へプロンプトを打っている。**

介入の言い方:

> 「その5分は Claude に何も言わなくて大丈夫です。**エディタとターミナルB だけでやってください。**
> 『このテストは正しいですか』と Claude に聞いた時点で、確かめたのはあなたではなくなります」

儀式が終わったあと、参加者は A に**1回だけ**「`git diff` で元に戻っているか確認して。直さないで」と打ちます。
**このプロンプトは、儀式をやっていない人には打てません**（書き換えて戻した事実が無いため）。
**打っている人＝やった人**なので、講師はそこを見れば済みます。

#### (4) `gh pr checkout` して遊ばずにレビューしていないか（115〜140分）

見分け方: **`/review` を打っているのに、ブラウザが相手のゲームに切り替わっていない。**

介入の言い方:

> 「先にターミナルB で `gh pr checkout <相手のPR番号>` して、ブラウザを再読み込みしてください。
> **`docs/games/<相手のゲームID>.md` のミッション1〜3を、そのまま自分の手で書き写してから**遊びます。
> 差分を眺めるだけのレビューは、今日は成果として数えません」

**`npm ci` を打たせないでください。** 依存は全ブランチで同じですし、
ターミナルB で `dev` が動いたまま `npm ci` を打つと、Windows ではファイル使用中で失敗します。

#### (5) verify を通さずに Pull Request を Ready にしようとしていないか

見分け方: `gh pr ready` の承認ダイアログが出ているのに、直前に `npm run verify` を打った形跡がない。

介入の言い方:

> 「ready にする前に `npm run verify` です。**GitHub で同じことが起きます。**
> 手元なら40秒、GitHub なら2分待たされます。
> そして `gh pr ready` を押した瞬間から、**相手があなたのコードを触り始めます**」

`.claude/hooks/require-verify.mjs` が1回だけ引き止めますが、**2回目は必ず通します**（作業が詰まらないようにするため）。
つまり、**機械は1回しか止めません。2回目以降は人間の仕事です。**

#### (6) 詰まったまま黙っていないか

**15分以上、同じエラーの前で止まっている人がいれば必ず声をかけてください。**
参加者は「聞くのが恥ずかしい」で20分溶かします。

まず `/stuck` を打たせてください。事実（ブランチ / `scope` / `lint` / `typecheck` / `test`）が整理されて出るので、
講師はそれを見るだけで判断できます。`/stuck` はコードを変更しないので、
**焦って大きな作り直しを始める事故も同時に防げます。**

### 3-5. 削る決断の下ろし方（70分・95分・118分）

#### 講師が代わりに決める

**参加者に「何を削りますか」と聞いてはいけません。**
参加者は遠慮して削れません。「もう少しで終わりそうなので、このままやります」と必ず言います。
そして118分に何も終わっていません。**これは能力の問題ではなく、立場の問題です。**
だから、**削る決断は講師が代わりに下します。**

言い方はこの形に固定してください。

> 「担当7、七並べの**パス回数の制限は今日は実装しません。**
> **私が決めました。** Issue のその行は無視してください。
> 次の15分は『7の隣にカードを置ける』ところだけに使ってください。
> **減点にはなりません。** 削ったことを Pull Request の『発展課題・未対応事項』に1行書けば、むしろ加点です」

ポイントは4つです。

- **「私が決めました」と言い切る**（相談の形にしない）
- **削るものを具体的に名指しする**（「どこか削って」では削れません）
- **次にやることを1つだけ指定する**（選択肢を出さない）
- **減点にならないことを明言する**（これを言わないと、隠れて実装を続けます）

#### 削る候補（正典の「時間が足りないときに落とす順番」から）

**迷ったら上から削ってください。** 正確な順番は各ゲームの `docs/games/<ゲームID>.md` の末尾にあります。

| 担当 | ゲーム | 最初に削るもの | 次に削るもの |

| 担当1 | ババ抜き | 発展課題を全部やめる | 引いたカードを見せる演出（`Phase` から `"revealing"` を外す） |
| 担当2 | 大富豪 | 発展課題を全部やめる | **革命**（`isRevolution` を `false` 固定。8切りは残す） |
| 担当3 | 神経衰弱 | 見た目の作り込み（めくり演出・凝った CSS） | 経過時間の表示 → ベスト手数の保存（`useHighScore`） |

| 担当5 | ぶたのしっぽ | 発展課題を全部やめる | 引き取りの演出（`Phase` から `"collecting"` を外す） |

| 担当9 | ページワン | 発展課題を全部やめる | `ScoreBoard` と `LogPanel`（残り枚数を素のテキストで出す） |

**スピードの正典には「落とす順番」の節がありません。** ここだけは講師が指示してください。
**担当2の大富豪は、必須要件のうち「革命」を削っても成立します。** 迷わず削ってください。
**担当4のポーカーは、役を7種類（フルハウスまで）に減らしても必須テスト8件がそのまま残ります。**

#### 118分の「削る決断」の下ろし方

118分は**この研修で唯一、講師が参加者の合意なしに仕様を変更する時刻**です。ためらわないでください。

```text
1. その人の画面で npm run verify を打たせる（口頭報告を信じない）
2. 最初に落ちたものだけを見る（後続は最初の失敗の影響であることが多い）
3. 落ちている原因が「未実装」なら、その機能を今日は作らないと宣言する
4. index.ts の status は "coming-soon" のままにさせる
5. PR の「発展課題・未対応事項」に、削った項目をそのまま書かせる
```

**4 が重要です。** `status` を `"ready"` にすると、契約テスト（`tests/contract/manifest.contract.test.tsx`）が
**「`logic.test.ts` に `it(` が3件以上」** と **「画面が例外なく描画でき `GameShell` を使っている」** を要求します。
未完成のまま `"ready"` にすると確実に赤くなります。

**`status: "coming-soon"` のままでも Pull Request は出せますし、マージもできます。**
アーケードの一覧には `ComingSoonPanel` が出るだけです。
**未完成のままマージすることは失敗ではありません。**
むしろ「間に合わない範囲を正直に切って、動くものだけをマージする」のは実務そのものです。そう言い切ってください。

**個人単位では、この宣言を全員に向けて出してください。** 個別に囁くと、
「自分だけが未完成」に見えて、隠れて実装を続けます。

### プロンプト駆動で増えた介入ライン

上の表のうち、**70分の口頭1問**と**105分の儀式**の2行は今回の版で足したものです。

- **105分の儀式** … 「テストが本当に落ちるか」を人間が確かめる唯一の時刻。
  ここを A に頼ると、**確かめたのが人間ではなくなります**

**この2つを削ると、プロンプト駆動にした副作用がそのまま残ります。**
時間が押しているときに削るのは、ここではなくゲームの中身です（5章）。

## 5. 遅延時の切り捨て順

全体が遅れているときは、**上から順に**切ります。**順番を入れ替えないでください。**

| # | 切るもの | 稼げる時間 | 判断の目安 |
|---|---|---|---|
| 1 | **発展課題を全面禁止**（`stretch-goal` の Issue を全部閉じる） | 0分（ただし脱線を防ぐ） | 70分の時点で**4人以上**がロジック未完 |
| 2 | **UI の作り込み**（CSS Modules 禁止。`GameShell` + `Hand` + `Button` だけ） | 10〜15分 | 95分の時点で**3人以上**が画面未表示 |
| 3 | **中間チェックを短縮**（70分を5分 → 3分。95分と118分は投影のみ） | 2〜3分 | 開始が押している場合のみ。**口頭1問は残す**（4章） |
| 4 | **レビュー 25分 → 18分**（指摘は3点セットの1番目だけ） | 7分 | 127分の時点で Ready の PR が**6本以下** |
| 5 | **大会 12分 → 6分**（自分がレビューした1本 + 3本に絞る） | 6分 | 160分の時点でマージが**5本以下** |

### **絶対に削らない5つ**

この5つは、**研修が10分押していても削りません。** 削った瞬間に、この研修は「ゲームを作った日」になります。

1. **Draft PR を出すこと** — 「まず不完全な状態を共有する」体験そのものです。個人単位では**最初の生存信号**でもあります
2. **Pull Request を出すこと** — 自分の言葉で説明を書くところまで
3. **相互レビューを行うこと** — 他人のコードを**実際に動かして**指摘する経験。**唯一の他人の目**です
4. **マージすること** — 自分のコードが `main` に入り、公開される瞬間
5. **振り返りを行うこと** — 経験を言葉にしないと持ち帰れません

**5 の振り返りが一番削られやすく、一番削ってはいけないものです。**
時間が無ければ大会を全部やめて構いません。**振り返りの時間は必ず確保してください。**

**そして、6つの機構（1-7）も削りません。**
機構はどれも5分以下です。削っても稼げるのは合計10分程度で、
**その10分と引き換えに「AI に丸投げしない」という研修の主目的が消えます。**

### 全体が20分以上押した場合の非常手段

レビューを**同時並行**にします。

- 通常: 自分の PR を出す → 相手の PR をレビューする（直列）
- 非常時: **PR を Ready にした瞬間に、レビュー担当へその場で口頭で伝える**（`gh pr list` を待たない）
- レビューの必須項目を **「再現手順つきの指摘1件」だけ**に減らす（`/review` が出す3点セットの1番目だけ）

**このとき削るのは指摘の件数であって、`gh pr checkout` して実際に動かす手順ではありません。**
動かさないレビューは、9本のうち1本を「誰も遊んでいないまま公開する」ことと同じです。

## 6. 緊急時の逃げ道（優先度順・**焦っているときに判断させない**）

**上から順に試してください。** 番号の小さいものほど影響範囲が狭く、後始末が要りません。
**4以降は研修後の後始末が必要です。**

### 1. Pull Request 単位の管理者マージ（**最初にこれ**）

CI が赤い / 承認が足りない / 時間が無い — **理由を問わず、まずこれで1本だけ通します。**
ブランチ保護は `enforce_admins: false` なので、講師（管理者）は貫通できます。
**影響はその PR 1本だけ**で、他の8人の保護は生きたままです。

```powershell
gh pr merge <番号> --squash --admin --delete-branch
```

### 2. 承認が足りない

レビュアーが席を外している、承認の操作が分からない、などのときです。

```powershell
gh pr review <番号> --approve --body "講師承認"
```

**注意: 自分が作成した Pull Request は自分では承認できません**（GitHub の仕様）。
講師が作った PR（7章の検証用など）を通したいときは、1（`--admin`）を使ってください。

**このコマンドは講師の端末で打ちます。** 参加者の Claude Code からは `gh pr review` は拒否されます。

### 3. CI 自体が壊れた（GitHub Actions の障害、Node のバージョン変更など）

**9人全部が赤い**ときだけこれを使います。1人だけ赤いのは CI の故障ではありません。

```powershell
gh api -X DELETE "repos/Daisuke0719/card_arcade/branches/main/protection/required_status_checks"
```

**研修後に必ず戻します。**

```powershell
node scripts/setup-github.mjs protect
```

### 4. 保護を丸ごと外す（**最終手段**）

3 でも通らないときだけ。**残り10分を切っていて、まだ1本もマージできていない**ような状況専用です。

```powershell
node scripts/setup-github.mjs unprotect
```

**→ 研修後に必ず戻してください。**

```powershell
node scripts/setup-github.mjs protect
```

**この復旧コマンドを、当日の朝にメモ帳へコピーしておいてください。** 焦っているときには探せません。

### 5. 誤ってマージしたものを巻き戻す

`main` が壊れると9人全員が止まります。
**`git reset` ではなく `revert` を使ってください**（履歴を書き換えると他の8人の作業が壊れます）。

```powershell
git switch main
git pull
git log --oneline -5
git revert <コミットSHA>
git push
```

**Squash マージにしているのでマージコミットにはなりません。** `-m 1` は不要です。

**巻き戻した人には必ず理由を説明してください。** 黙って消すと、その人は以降の研修に参加しなくなります。

### 6. ハーネス全停止（`CARD_ARCADE_HARNESS=off`）

特定の1台で、フックが誤作動して作業が完全に止まった場合です。

**Claude Code を起動する前に**、その端末の PowerShell で次を実行します。

```powershell
$env:CARD_ARCADE_HARNESS = "off"
claude
```

- 効くのは **`.claude/hooks/` のフック**と **`.githooks/pre-commit`** と **`npm run scope`** だけです。
- **CI は残ります。** 範囲外を触れば Pull Request は赤くなります。**逃げ切れません。**
- **`npm run dev` の拒否も外れます。** 外した端末では、参加者がターミナルA で `dev` を起動できてしまい、
  **ターミナルB の 5173 とポートが衝突します。** 外したことを本人に必ず伝えてください。
- **Claude Code のセッションの中からは設定できません。** `.claude/` は保護領域なので、
  設定ファイルの書き換えもフックが止めます。必ず**起動前**に、講師が端末で設定してください。
- 元に戻すときは PowerShell を閉じるか、次を実行します。

  ```powershell
  Remove-Item Env:CARD_ARCADE_HARNESS
  ```

### 7. PC が壊れた参加者が出た

**個人開発では、他の人が肩代わりできません。** ここがチーム制といちばん違うところです。

対応は次の順です。

1. **予備 PC を1台用意しておく**（前日の準備で最も費用対効果が高い1台です）
2. 予備が無ければ、**講師の端末を貸して本人に操作させる。**
   `gh auth login` を本人のアカウントでやり直せば、その人の Pull Request として出せます
3. どちらもできないときは、**その人を「レビュー専任」に切り替える。**
   自分のゲームは `status: "coming-soon"` のまま出せない状態を受け入れ、
   **リングの相手のレビューだけは必ずやってもらいます**（リングが切れると、さらに2人が止まります）

**3 を選んだ場合は、評価でその人の「実装」を空欄にしないでください。**
レビュー15点と、状況を `/handoff` で説明できたことを見ます。

### 補足A. 範囲チェックだけが原因で赤い PR を、PR 単位で救う

**1（`--admin`）を使う前に検討できる、より影響の小さい手**です。

その Pull Request に **`harness:override` ラベル**を付けると、CI の範囲チェックが**警告のみ**に降格します
（`.github/workflows/ci.yml` がラベルを見て `scope-guard.mjs` に `--warn-only` を渡します）。
lint / 型 / テスト / ビルドは**通常どおり必須のまま**です。

```powershell
gh pr edit <番号> --add-label "harness:override"
gh pr checks <番号> --watch
```

**このラベルの存在は参加者に教えないでください。** 教えた瞬間にハーネスが機能しなくなります。

### 補足B. 当日の朝、メモ帳にコピーしておくコマンド

## 7. 研修前の検証手順（**省略不可**）

**本番の前に30〜40分で実施してください。** やることは2つです。

> 1. **わざと壊して、止まるはずのものが止まるかを確認する。**
> 2. **止めてはいけないものが、承認なしで通るかを確認する。**

1 だけをやって当日を迎えないでください。**止めすぎの事故のほうが、通しすぎより高くつきます。**

**だから 2 の確認を必ず入れてください。**

準備として、講師の端末で作業用のブランチを1本切り、**ターミナルB で `npm run dev` を動かしておきます。**

```powershell
git switch main
git pull
git switch -c feature/speed
```

### 8-3. **講師しか対応できないもの**

次の3種類は、参加者が何をしても直りません。**症状を聞いた瞬間に講師が動いてください。**

#### (1) 権限（403 / Permission denied）

**当日いちばん多い講師案件です。** ほぼ100%、collaborator の招待を承諾していないことが原因です。

```powershell
node scripts/setup-github.mjs collaborators
node scripts/setup-github.mjs collaborators <GitHubユーザー名>
```

招待メールを開かせて承諾させます。**メールが見つからない場合は、本人のブラウザで
https://github.com/Daisuke0719/card_arcade を開くと画面上部に承諾ボタンが出ます。**

**個人開発では、他の人が肩代わりできません。** 本人が承諾するまでその人の成果は出せません。

#### (2) ブランチ保護（マージできない / チェックが終わらない）

| 症状 | 原因 | 対処 |
|---|---|---|
| 「Expected — Waiting for status to be reported」が消えない | 必須チェックの名前が実際のジョブ名と違う | 6章 3 で必須チェックを外すか、`contexts` を実名に直す |
| CI は緑なのにマージできない | CODEOWNERS が所有する場所を触っている | `gh pr diff <番号>` で範囲を確認。運営領域を触っているなら差し戻す |
| 承認済みなのにマージできない | 単に CI がまだ実行中 | `gh pr checks <番号> --watch` で待つ |
| 何をやってもマージできない | — | 6章 1 の `--admin` で通す |

#### (3) GitHub Pages（公開されない / 404 になる）

```powershell
gh run list --workflow=deploy-pages.yml --limit 5
gh run view --log-failed
```

| 症状 | 原因 | 対処 |
|---|---|---|
| ワークフローが起動しない | Pages の Source が `Deploy from a branch` になっている | Settings > Pages で **GitHub Actions** に変える |
| 404 になる | 初回デプロイがまだ終わっていない | 2〜3分待つ。`gh run list` で `completed` を確認 |
| 画面は出るが真っ白 | `base` の設定 | `vite.config.ts` の `base: "./"` を確認（変更不要のはず） |
| マージしたのに反映されない | デプロイが順番待ちしている | 順に流れます。**待てば必ず反映されます** |

**大会（160分〜）の直前には、必ず講師が公開 URL を開いて確認してください。**
9本目のマージからデプロイ完了まで2〜3分かかります。**マージは160分より前に終わらせてください。**

#### (4) ハーネス自体の誤作動

「正しいことをしているのに止められた」という報告が来た場合です。

1. **まず本当に誤作動か確かめます。** 9割は正しく止まっています（担当外を触っている / A で `dev` を打っている）。
   拒否メッセージの全文をそのまま見せてもらってください。
2. 本当に誤作動なら、その端末だけ 6章 6（`$env:CARD_ARCADE_HARNESS = "off"`）で止めます。
3. **CI は残るので、範囲外を触れば結局赤くなります。** そのことを本人に必ず伝えてください。
4. **`dev` の拒否も外れる**ので、ターミナルA で起動してポートを衝突させないよう本人に念を押してください。
5. 範囲チェックだけが原因で PR が赤いなら、6章 補足A の `harness:override` ラベルで PR 単位に救えます。

## 9. 評価

### 9-1. 配点

| 評価項目 | 配点 |
|---|---|
| Issue の必須要件を満たした | 20 |
| 担当範囲を守った | 10 |
| 適切なテストを作成した | 20 |
| Pull Request を分かりやすく書いた | 15 |

むしろ、プロンプトで実装が速くなったぶん、**60点側の比重が実質的に上がっています。**
「速く作れた人」ではなく「他人に読ませられる形にできた人」が高くなる、という設計です。

- 完成宣言（`index.ts` が `status: "ready"` になっているか）
- **テスト件数**（`logic.test.ts` などの `it(` の数）
- Pull Request の有無と状態
- **受けたレビュー件数**
- **PR 本文の文字数**
- 他の人へのレビュー総数（リポジトリ全体の参考値）

### 9-3. 機械が測れないもの — **ここは人間が見る**

`score.mjs` は最後にこう出力します。

> ※ テストの中身の妥当性・命名の分かりやすさ・レビューの質は機械では測れません。
> そこは相互レビューと講師の目で評価してください。

**この線引き自体が、この研修で伝えたい設計思想です。**
数えられるものだけを機械に任せ、質は人間が見る。CI の設計もまったく同じ考え方でできています。

| 項目 | 機械で見る | 人間で見る |
|---|---|---|
| 必須要件を満たした 20 | `status: "ready"` / CI が緑 | Issue の必須要件と実装の突き合わせ。**実際に遊んでみる** |
| 担当範囲を守った 10 | CI の範囲チェックが緑 / `harness:override` を使っていない | — |
| 適切なテストを作成した 20 | テスト件数（3件が下限） | **境界値と異常系があるか。** 正常系だけなら半分以下 |
| PR を分かりやすく書いた 15 | 本文の文字数 / `Closes #` の有無 | **「レビューしてほしい点」が自分の言葉で具体的か** |
| 他の人のレビューを行った 15 | レビュー件数 | **再現手順が書かれているか。**「LGTM」だけなら0点 |
| レビュー指摘を反映した 10 | 指摘後のコミット数 | **「直さない」判断に理由が書かれているか**（理由があれば満点） |
| UI とゲームの工夫 10 | — | 大会で実際に遊んで判断 |

**「直さない」を選んだこと自体は減点しないでください。**
理由を説明できているかだけを見ます（`/fix-review` も参加者にそう指示しています）。

### 9-4. プロンプト駆動で、講師が手元に残しておくメモ

**数字に出ない情報が2つあります。** どちらも当日その場でしか取れません。

1. **Step 9 の口頭1問に答えられたか**（3-3 の (c)）。名前だけ控えておきます
2. **Step 11 の儀式を、ターミナルB でやっていたか**（3-4 の (3)）

**この2つを配点に直接足す必要はありません。**
使うのは、`score.mjs` の数字と食い違ったときです。
「テスト件数は多いが、口頭1問に答えられず、儀式も A に頼んでいた」という人は、
**テスト20点を満点にしないでください。** 中身を見ていない可能性が高いからです。

逆に、**「未完成だが、口頭1問に答えられて、レビューが具体的だった」人は高く付けてください。**
それがこの研修で測りたかったものです。

### 9-5. 採点の実務

**研修中に採点しないでください。** 講師の時間は介入に使います。

`npm run status` のスクリーンショットを **70分 / 118分 / 152分 / 178分** の4回撮っておき、

## 10. 表彰と振り返り（172〜180分）

### 10-1. 表彰（172〜178分）

**9人いるので、賞も6つ用意して、なるべく多くの人が何かを取る**ようにしてください。
「自分だけ何もなかった」を作らないことが目的です。

| 賞 | 選び方 |
|---|---|
| **ベストゲーム賞** | 大会（160〜172分）で最も遊ばれたゲーム。挙手で決めてよい |
| **ベストUI賞** | 見た目と分かりやすさ。`src/styles/tokens.css` の `--ca-*` を使って統一感が出ているものを優先 |
| **ベストテスト賞** | **件数ではなく、境界値と異常系を見ているか。**「同じ数字」「最後の1枚」「0枚」「二重クリック」を押さえているものを選ぶ |
| **ベストレビュー賞** | **下の数えられる基準で選ぶ**（次項） |
| **ベスト正直賞** | **削ったものを PR に正直に書いた人。** 118分に要件を削った人から選ぶ。**「未完成を隠さなかったこと」を表彰します** |
| **最も意外なバグ賞** | 大会中に見つかった想定外のバグ。**見つけた人ではなく、バグを作った人を表彰する** |

**「ベスト正直賞」は個人単位にしてから足した賞です。**
1人1ゲームだと、削った結果が「自分だけ未完成」に見えます。
**そこを表彰の対象にしておくと、削る判断のハードルが翌年から下がります。**

#### ベストレビュー賞は「数えられる基準」で選ぶ

**「一番いいレビューをした人」では選べません。** 印象で選ぶと、声の大きい人が取ります。
**次の3つを数えて、合計が最も多い人を選んでください。**

1. **再現手順つき指摘の数**
   「〇〇を〇回すると〇〇になります。Issue では〇〇のはずです」の形で書かれたコメントの数。
   **「ここが怪しいです」「LGTM」は数えません。**
2. **採用された `suggestion` の数**
   GitHub の suggestion 機能で提案し、**相手が「Commit suggestion」を押したもの**の数。
3. **「レビューしてほしい点」への指摘**（機構5）
   相手の PR 本文がテンプレのままだったときに、**それ自体を指摘できたか。**
   **これは1件で2件分に数えてよいです。** 今回いちばん見たかった行動だからです。

```powershell
gh pr view <番号> --comments
node scripts/score.mjs
```

**この基準は研修の最初（Step 3 の担当確認のあたり）で予告しておいてください。**
「レビューはこの3つで数えます」と先に言っておくと、115分からのレビューの質がはっきり変わります。
