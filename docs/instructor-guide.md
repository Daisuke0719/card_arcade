# 講師ガイド

「Claude Code × GitHub 共同開発ハンズオン — みんなでつくる CARD ARCADE」の講師向けガイドです。
事前準備、当日の進行、参加者への対応、緊急時の手順をまとめています。

この研修では、参加者9名が1人1ゲームを担当します。
チームには分かれません。各参加者が、調査、実装、テスト、Pull Requestの提出までを担当します。
個人作業での注意点と対応は1-6で説明します。

今回の版では、参加者はClaude Codeにプロンプトを入力して作業を進めます。
そのまま利用できるプロンプトは `docs/handson-steps.md` に掲載しています。
運営時に確認する内容は1-7で説明します。

参加者向けの文書は、次の順に案内します。

| 文書                        | 案内する時点                                                   |
| --------------------------- | -------------------------------------------------------------- |
| `docs/handson-steps.md`     | 当日の最初から最後まで（フェーズ1〜7）                         |
| `docs/claude-code-guide.md` | Claude Codeへの依頼方法を確認するとき（3原則とプロンプトの型） |
| `docs/games/<ゲームID>.md`  | 担当ゲームのルール文書                                         |
| `docs/harness.md`           | 操作が拒否されたとき（拒否メッセージの読み方）                 |
| `docs/troubleshooting.md`   | 問題が起きたとき（T-01〜）                                     |

## 1. 研修の設計意図

### 1-1. 主目的はゲーム制作ではない

ゲームの完成だけが研修の目的ではありません。
共有リポジトリで担当範囲を守り、確認を重ねながら提出まで進める過程を重視します。

この研修では、次の5項目を達成することを目標とします。

1. コードで定義された担当範囲を守って作業する
2. `npm run verify` の成功を確認してから完了を報告する
3. レビューを想定した Pull Request を書く
4. ゲームを操作して不具合を見つけ、修正する
5. 変更をマージし、公開する

ゲームの完成度は、この5項目を満たしたうえで評価します。時間が足りない場合は、ゲーム内の実装項目を減らします。
5章の「省略順」は、この優先順位に沿って定めています。

### 1-2. 自動検査を設ける理由

9名が1つの `main` を共有するため、口頭での説明だけではルールの見落としが起こり得ます。
担当範囲外の変更は、同じリポジトリで作業する他の参加者にも影響します。

そこで、規約を文書に記載するだけでなく、自動検査でも確認します。

- 「他人のフォルダは変更しないでください」→ `scripts/scope-guard.mjs` が差分を検査し、違反があれば処理を失敗させる
- 「依存を追加しないでください」→ `.claude/settings.json` の deny と `.claude/hooks/guard-bash.mjs` が実行を拒否する
- 「`logic.ts` に `Math.random()` を書かないでください」→ ESLint がエラーとして検出する
- 「ESLint を無効化して回り込まないでください」→ `tests/contract/boundaries.contract.test.ts` が違反を検出する
- 「開発サーバーはターミナルBで動かしてください」→ `guard-bash.mjs` がターミナルAでの `npm run dev` を拒否する

禁止する理由は講師が説明します。自動検査では、同じ違反に対して同じ案内を返します。
講師は、ルールの解釈、要件の調整、実装内容など、自動判定できない点を確認します。

個人作業中の見落としを減らすため、問題は自動検査で早めに検出します。

### 1-3. ハーネスを構成する5つの層

| 層                                   | 実体                                                     | 役割                                           | 無効化の可否                                                                            |
| ------------------------------------ | -------------------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------- |
| Layer 1 予防                         | `scripts/scaffold-game.mjs` / `templates/game/`          | 規定の構成でファイルを作成する                 | 手作業で作成すれば適用されない                                                          |
| Layer 2 ルールの明文化               | `CLAUDE.md` / `src/games/CLAUDE.md`                      | 禁止事項を Claude Code と参加者に伝える        | 文書を確認しなければ見落とす可能性がある                                                |
| Layer 3 実行時の制限                 | `.claude/settings.json` の deny / `.claude/hooks/`       | 範囲外の編集・依存追加・迂回コマンドを拒否する | `CARD_ARCADE_HARNESS=off` で無効にできる                                                |
| **Layer 4 コミット前と CI での検査** | **ESLint / `tests/contract/` / `.githooks/pre-commit`**  | **境界違反を検出する**                         | **pre-commit は `--no-verify` で省略できるが、ESLint と契約テストは CI でも実行される** |
| Layer 5 マージ時の制限               | `.github/workflows/ci.yml` / `CODEOWNERS` / ブランチ保護 | 検証に失敗した Pull Request のマージを制限する | 管理者権限があれば設定を変更できる                                                      |

各層の違いは次のとおりです。

- Layer 1〜3はローカル環境で動作します。フックを承認しない、環境変数で無効にする、
  Claude Code を使わずに編集する、といった方法では適用されない場合があります。
- Layer 4は変更後のソースコードを検査します。たとえば、`logic.ts` に `Math.random()` が含まれていれば、
  `npm run lint` または `npm test` の対象になります。
- CI（Layer 5）でも Layer 4 を実行するため、同じ基準で変更内容を検査できます。
- Layer 5は講師が管理者権限で解除できるため、運用によって維持する制限です。

この役割分担は、当日のハーネスのデモ（3-2）で説明します。
手元の検証は問題の早期発見、CIは問題のある変更を `main` に入れないことが目的です。

### 1-4. 設定の参照元

参加者、ゲーム、保護対象パスは `harness/config.json` で管理します。
`scope-guard`、`scaffold`、契約テスト、`.claude` のフック、`doctor`、`status`、`score`、
`build-issue-bodies`、`setup-github.mjs` は、このファイルを参照します。
当日に担当を入れ替える場合は、このファイルを変更します。

配列の名前は `participants` です（チーム制の名残りの `teams` はもうありません）。1要素が1人です。

```json
{
  "participant": "participant-1",
  "displayName": "担当1",
  "gameId": "babanuki",
  "name": "ババ抜き",
  "difficulty": "easy",
  "issue": 1,
  "reviews": "participant-2"
}
```

- `participant`: 参加者のID。当日にGitHubのアカウント名へ書き換えます（2-3）
- `displayName`: 画面、Issue、セッション開始メッセージに表示する名前

コード側では `GameManifest` の `owner` フィールドがこの `participant` を指します
（型は `src/core/types.ts` の `OwnerId`。中身は文字列です）。
アーケードの並び順は、`src/app/registry/gameOrder.ts` が `harness/config.json` の記載順をもとに決めます。
参加者ごとに並び順を変更することはできません。

参加者向けの手順書にも、担当名やゲーム名を直接記載していません。
プロンプトはすべて `<ゲームID>` `<Issue番号>` `<相手のPR番号>` というプレースホルダで書いてあるので、
当日に `participant` をGitHubのアカウント名へ差し替えても、手順書の変更は不要です。

### 1-6. 個人作業で注意すること

この章では、個人作業で特に注意する運営上の違いを説明します。

#### (1) 作業の停滞を把握しにくい

個人作業では、問題が共有されないまま作業が止まることがあります。
Claude Code とのやり取りの回数は進捗の判断材料にせず、Issue やコマンドの結果を確認してください。

次の3つの方法で進行状況を確認します。

1. 節目ごとに `npm run status` を投影し、対応が必要な参加者を確認する（4章）
2. 机間巡視で、作業の停滞や `verify` を実行しないまま次へ進んでいないかを確認する（3-3）
3. 作業を続けられない場合の相談方法を開始時に説明する

#### (2) 相談時の共有形式を決める

参加者から講師へ状況を正確に共有できるよう、報告の形式を統一します。
作業が止まっている参加者には、次のプロンプトを入力してもらいます。
このプロンプトではコードを変更せず、ブランチ、`scope`、`lint`、`typecheck`、`test` の結果を確認します。

```text
同じエラーで手が止まっています。<困っていることを一言で> という状態です。

まず git branch --show-current / git status --short / npm run scope / npm test を実行して、
いま起きている事実を集めてください。エラーは最初の1件だけを引用してください。
そのうえで docs/troubleshooting.md と照らし合わせ、次に試すことを1つだけ挙げてください。

コードは変更しないでください。私が講師に相談してから決めます。
```

講師はこの出力と参加者からの補足をもとに、次の対応を判断します。

当日の最初に、次のように案内します。

> 「作業を続けられなくなった場合は、上の形式で状況を整理し、早めに講師へ相談してください。」

この文面には、状況を確認する前に大きな変更を始めないようにする目的もあります。
「コードは変更しないでください」を文面に入れてあるので、事実を集める間にファイルが変わりません。

#### (3) Issue のチェックリストで進み具合を確認する

講師は、Issueの必須要件にあるチェックボックスを主な確認材料にします。

Issue 本文は `docs/games/<ゲームID>.md` から機械生成していて、必須要件がそのままチェックリストになっています。
当日の最初に次を徹底してください。

> 「1つ完了するたびに、Issueの該当するチェックボックスを更新してください。
> チェックの更新が止まっている場合は、講師から進行状況を確認します」

チェックが更新されていない場合は、実装状況と記録状況の両方を確認してください。

なお、参加者がClaude CodeからIssue本文を書き換える操作（`gh issue edit`）は拒否されます。
チェックボックスは GitHub の画面で本人がクリックします。
「要件は講師が管理し、進捗は本人が申告する」という線引きを、コマンドの可否で表しています。

#### (4) 個人作業で簡略化できる運営

個人作業にしたことで簡略化できる運営もあります。

- 役割分担（Driver / Navigatorなど）の説明は不要です
- 各参加者が、自分の担当ゲームに必要な操作をすべて行います
- 要件を減らす判断は、参加者と講師の2者で行います

講師は、(1)で説明した進行状況の確認に時間を割きます。

### 1-7. プロンプト中心の進行で注意すること

今回の版から、参加者はプロンプトを入力して進めます。
`docs/handson-steps.md` には、各工程で使用するプロンプトを掲載しています。
覚えるスラッシュコマンドはありません。

定型文を配布すると入力時間を短縮できますが、内容を確認する時間を別に設ける必要があります。
この研修では、依頼文の作成よりも、出力や動作を参加者が確認する工程を重視します。
確認作業を省略しにくくするため、Claude Codeへの依頼と参加者による操作を2つのターミナルに分けます。

|      | ターミナルA（Claude Code）                 | ターミナルB（参加者が操作）                              |
| ---- | ------------------------------------------ | -------------------------------------------------------- |
| 常駐 | Claude Code のセッション                   | **`npm run dev`（研修中は起動したままにする）**          |
| 用途 | 調査・実装の依頼・差分の確認・文章の下書き | ブラウザでの動作確認 / `npm test` の実行 / `gh pr ready` |

ターミナルAでは `npm run dev` を実行できません（`.claude/hooks/guard-bash.mjs` が拒否します）。
開発サーバーの起動とブラウザでの動作確認は、ターミナルBを使用します。

参加者による確認を維持するため、操作する場所を2つのターミナルに分けます。
開発サーバーをターミナルBで動かし、参加者がブラウザを操作して確認します。

#### (1) ブラウザでの確認が省略されていないかを確認する

手順書のプロンプトを順に入力すれば、ブラウザで動作を確認しないままフェーズ6まで進むこともできます。
`npm run status` やテストの結果だけでは、ブラウザで確認したかどうかは分かりません。
机間巡視（3-3）では、ターミナルAだけで作業していないかを確認します。
ブラウザでの確認が不足している場合は、ゲームを最初から最後まで1回操作してもらいます。

#### (2) ターミナルの役割を開始時に説明する

2つのターミナルを開く前に、それぞれの役割を説明します。
説明がないと、コマンドを実行する場所を判断できません。

フェーズ1で、ターミナルA（`claude` を起動する画面）とターミナルB（`npm run dev` を動かす画面）を
1つずつ開きます。作業を始める前に、次の内容を伝えます。

> PowerShellを2つ開きます。
> 片方でClaude Codeを起動します（ターミナルA）。もう片方では起動しません（ターミナルB）。
> ターミナルBでは、研修中 `npm run dev` を起動したままにします。

オープニングでも、Claude Codeを起動するターミナルAは1つだけであり、追加したターミナルはBとして扱うと説明します。
ターミナルAとBは、Claude Codeを起動しているかどうかで区別します。

#### (3) 開発サーバーの停止による表示エラーに対応する

当日は、開発サーバーの停止に関する相談が多くなると見込まれます。主な症状は次のとおりです。

> 「画面が出ません」「さっきまで動いていました」「真っ白です」

まず、ターミナルBで `npm run dev` が動いているか確認します。停止する主な理由は3つあります。

1. テストを実行するため、`dev` を起動しているターミナルで `Ctrl + C` を押した
2. `gh pr checkout` を実行するために、`dev` を動かしているターミナルを使ってしまった
3. スリープからの復帰やPowerShellの再起動により、プロセスが終了した

ターミナルBで `npm run dev` を再実行してもらいます。必要に応じて、停止した原因も確認します。

予防として、参加者向けの手順書の「当日の進め方」に、`npm run dev` を止めないことと、
停止した場合は、同じターミナルで再実行することも記載しています。

机間巡視では、タスクバーと各ターミナルの状態を確認します。
PowerShellが1つしか開かれていない場合は、`dev` の実行状況を確認します（3-3の(1)）。

#### (4) プロンプト駆動でも変えていないこと

プロンプト中心の進行でも、次の3項目は必須です。

- `npm run verify` が成功してから完了を報告する
- Pull RequestとIssueへの投稿は参加者が行う（`gh pr review` / `gh pr comment` / `gh issue comment` は拒否）
- 画面の確認は、参加者が実際にゲームを操作して行う

講師は、この順序を省略している参加者がいないかを当日に確認します。

## 2. 講師の事前準備チェックリスト

### 2-1. ゲームの割り当て

9本のゲームは、初級3本、中級4本、上級2本に分かれています。
難易度はゲームごとに決まっています。
担当の割り当ては、当日の進み具合に大きく影響します。

| 難易度      | ゲーム                                  | 渡す相手                                             |
| ----------- | --------------------------------------- | ---------------------------------------------------- |
| 初級（3本） | ババ抜き / 神経衰弱 / ぶたのしっぽ      | 経験の浅い人。ReactやGitをほとんど使ったことがない人 |
| 中級（4本） | スピード / 七並べ / ダウト / ページワン | 業務で1つはアプリを書いたことがある人                |
| 上級（2本） | 大富豪 / ポーカー                       | 開発に慣れており、自分でテストを書いた経験がある人   |

経験の浅い人には初級を、開発に慣れている人には上級を割り当てます。
経験の浅い人に追加の課題が必要な場合は、初級ゲームの発展課題を利用します。

定型プロンプトを入力すれば実装の途中までは進められるため、プロンプトの使用状況だけで難易度を判断しないでください。
割り当てには、参加者の開発経験とテスト作成の経験を用います。

#### 上級2本の違い

上級の2本では、実装の難しさが異なります。

|                | 大富豪（担当2 / #6）                                                  | ポーカー（担当4 / #8）                                 |
| -------------- | --------------------------------------------------------------------- | ------------------------------------------------------ |
| 難しさの内容   | ルールが多く、複数の状態が関係する                                    | 役の判定に実装が集中する                               |
| 状態遷移       | 場・パス・場流れ・8切り・革命・順位。手番の進み方がルールごとに変わる | 配る → 一度だけ交換 → 勝負                             |
| プレイ人数     | 4人（プレイヤー + CPU3人）                                            | 2人（プレイヤー + CPU1人）                             |
| 実装の進め方   | ルールを3段（出せる判定 → 8切り → 革命）に分けて実装する              | 時間の8割を `evaluateHand` に使い、9種類の役を判定する |
| 進行状況の確認 | どの状態遷移で問題が起きているかを確認する                            | 成功している役判定のテスト件数を確認する               |
| 要件の減らし方 | 革命 → CPUの複数枚出し → 8切りの順に減らせる                          | 同じ役どうしの比較を省く、または役を7種類に減らせる    |

ポーカーは上級ですが、状態遷移が単純なため、残りの作業量を把握しやすいゲームです。
`docs/games/poker.md` は役の判定を先に固める形にしてあり、
役ごとのテスト結果から進行状況を確認できます。

大富豪ではルールどうしが関係するため、
たとえば、革命を追加したあとに8切りの場流れが動作しなくなる場合があります。
`docs/games/daifugo.md` はルールを3段に割っていますが、
講師は、どの段階で問題が起きているかを参加者に確認します。

上級ゲームは、次の基準で割り当てます。

- 経験が最も多い人には、大富豪（担当2）を割り当てる
- 次に経験が多い人には、ポーカー（担当4）を割り当てる
- 上級を担当できる人が1人しかいない場合は、大富豪の「革命」を開始時点で要件から外す

- マージ方式をSquashのみにする（マージ後にブランチを自動削除）。

- `main` のブランチ保護（`.github/branch-protection.json` を適用）

- 必須チェック: `verify` 1本のみ
- レビュー承認: **不要**（`required_pull_request_reviews` は `null`。マージするのは講師だけです）
- `enforce_admins: false` … 緊急時には講師が `--admin` を指定してマージできます。`true` には変更しません

空だった場合は、手順5のテストPull Requestをもう一度実行してから、`protect` を再実行してください。

### 3-3. 机間巡視で見るポイント

コードの内容ではなく、参加者の作業手順とターミナルの状態を確認します。会場を定期的に巡回してください。
プロンプト中心の進行では、ターミナルAとBが用途に沿って使われているかを確認します。

#### (1) ターミナルが2つ開いているか

タスクバーを確認します。PowerShellが1つしか開いていない場合は、`npm run dev` が停止していないか確認してください。

案内例:

> 「ターミナルBを開き直して、`npm run dev` を実行してください。研修中は起動したままにします」

開発サーバーが停止している場合は、画面確認の前に再起動します。
開発サーバーが停止していた場合は、早めに再起動します。

#### (2) ブラウザで動作を確認しているか

プロンプトを中心に進める場合、この状況が起こりやすくなります。
Claude Codeの応答だけを確認し、ブラウザを操作していない場合があります。

確認方法: ブラウザが長時間開かれていない場合は、動作確認の状況を尋ねます。

案内例:

> 「ブラウザを開き、担当ゲームを最初から最後まで1回操作してください。
> テストだけでなく、画面上でも問題なく操作できることを確認します」

#### (3) 動作確認と修正を繰り返しているか

このフェーズでは、「ブラウザで操作する → 問題を伝える → 修正を依頼する → もう一度操作する」の順に進めます。
ブラウザを再読み込みせず、ターミナルAだけで作業を続けている場合は、ブラウザでの確認手順を案内します。

確認方法: ブラウザの画面が実装前の状態で止まっている場合は、再読み込みと操作を依頼します。

案内例:

> 「いま修正した箇所を、ブラウザを再読み込みして操作してください。
> 修正後は、同じ操作を行って問題が解消したことを確認してください。」

不具合の内容を示さず「直してください」とだけ依頼している場合も、依頼内容を確認します。
手順書では、プランモード（`/plan`）で原因と修正方針を整理し、内容を確認してから実装を依頼します。
計画を確認せずに修正を依頼すると、対象外の箇所が変わり、元の不具合が残ることがあります。

> 「何が起きて、どうなってほしいのかを書いてから頼んでください。
> 作成された計画を確認してから、実装を依頼してください」

#### (4) `verify` の成功後にPull RequestをReadyへ変更しているか

確認方法: `gh pr ready` の承認画面が表示されている場合は、直前の `npm run verify` の結果を確認します。

案内例:

> 「Readyにする前に `npm run verify` を実行してください。ローカルで成功したことを確認してから、
> `gh pr ready` を実行します」

`.claude/hooks/require-verify.mjs` は初回の実行を拒否しますが、2回目は許可します。
2回目以降は、参加者が検証結果を確認してから実行します。

#### (5) 問題を共有できているか

同じエラーが続いている参加者には、講師から状況を確認します。

まず、1-6の(2)にある相談用のプロンプトを入力してもらいます。
事実（ブランチ / `scope` / `lint` / `typecheck` / `test`）が整理されて出るので、
講師はその出力と参加者からの補足をもとに対応を判断します。文面には「コードは変更しないでください」と記載しているため、
状況を整理している間はファイルが変更されません。

### 3-4. 実装対象を減らすときの判断

#### 講師が省略する項目を決める

実装対象を減らす必要がある場合は、講師が省略する項目を決めます。
参加者には、省略する項目と、残りの時間で優先する作業を伝えます。

案内例:

> 「担当7、七並べの**パス回数の制限は今日は実装しません。**
> 講師判断で省略します。Issueのその行は対応不要です。
> ここからは『7の隣にカードを置ける』ところまでの実装を優先してください。
> 省略自体による減点はありません。Pull Requestの『発展課題・未対応事項』に、省略した内容を1行記載してください」

案内には次の4点を含めます。

- 講師が決めたことを明確に伝える
- 省略する項目を具体的に示す
- 次に行う作業を1つに絞る
- 要件の省略自体は減点にならないことを伝える

#### 省略候補（ルール文書の「時間が足りないときの省略順」から）

実装項目を省略する場合は、次の表を上から順に適用します。各ゲームの詳細は、`docs/games/<ゲームID>.md` の末尾に記載しています。

| 担当  | ゲーム       | 最初に削るもの                             | 次に削るもの                                                                       |
| ----- | ------------ | ------------------------------------------ | ---------------------------------------------------------------------------------- |
| 担当1 | ババ抜き     | 発展課題を省略する                         | 引いたカードを見せる演出（`Phase` から `"revealing"` を外す）                      |
| 担当2 | 大富豪       | 発展課題を省略する                         | **革命**（`isRevolution` を `false` 固定。8切りは残す）                            |
| 担当3 | 神経衰弱     | 見た目の作り込み（めくり演出・凝った CSS） | 経過時間の表示 → ベスト手数の保存（`useHighScore`）                                |
| 担当4 | ポーカー     | 発展課題を省略する                         | 同じ役どうしの比較（`tiebreak`）を省略して引き分け扱いにする                       |

| 担当8 | ダウト       | `LogPanel` の進行ログ                      | `revealing` の演出時間（即決着にする）                                             |
| 担当9 | ページワン   | 発展課題を省略する                         | `ScoreBoard` と `LogPanel`（残り枚数をテキストで表示する）                         |

担当2の大富豪は、講師の判断で必須要件の「革命」を省略できます。
**担当4のポーカーは、役を7種類（フルハウスまで）に減らしても必須テスト8件がそのまま残ります。**

#### 終盤に実装対象を減らす手順

時間内に提出できない場合は、講師が実装対象を調整します。変更内容は参加者にも説明してください。

```text
1. 参加者の画面で `npm run verify` を実行してもらい、結果を確認する
2. 最初に失敗した項目を確認する（後続の失敗は、最初の失敗による場合が多い）
3. 失敗の原因が未実装の機能であれば、その機能を実装対象から外すと伝える
4. index.ts の status は "coming-soon" のままにする
5. PR の「発展課題・未対応事項」に、省略した項目を記載してもらう
```

手順4では、`status` を `"ready"` にすると、契約テスト（`tests/contract/manifest.contract.test.tsx`）が
「`logic.test.ts` に `it(` が3件以上」と「画面が例外なく描画でき `GameShell` を使っている」ことを要求します。
未完成のまま `"ready"` にすると、契約テストが失敗します。

`status: "coming-soon"` のままでもPull Requestを作成し、マージできます。
アーケードの一覧には `ComingSoonPanel` が出るだけです。
未実装の項目がある場合は、その内容を明示します。
時間内に完了できない範囲を明示し、動作を確認できた部分だけをマージする方針を説明してください。

要件を省略する方針は、対象者だけでなく全員に共有してください。

次の表を上から確認し、該当する状態に対応します。

| 見えている状態                                                 | 講師がやること                                                                                          |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `npm test` が**成功しない**まま作業が止まっている              | 状況を確認する。ルール解釈が原因なら講師が解釈を決め、実装が原因ならテストを1本だけ成功させる作業に絞る |
| 画面に何も表示されていない                                     | 3-4の表に従って要件を減らす。UIは `GameShell` + `Hand` + `Button` の3つに絞る                           |

| 必須要件の半数以上が未完了                                     | 講師が3-4の表に従って、実装対象から外す要件を決める                                                     |

| `npm run verify` が**成功しない**                              | 未達の必須要件を外し、`status` は `"coming-soon"` のままPull Requestの作成を依頼する                    |

`npm run status` は節目ごとに投影します。上の表のうち、テスト・画面・PR・マージの状態は
この画面で分かります。

### `npm run status` では確認できない項目

ブラウザで操作したかどうかは、`npm run status` には表示されません。

参加者同士のレビューも中間確認も置いていないので、
机間巡視では、参加者がブラウザでゲームを操作していることを確認します。
時間が不足していても、この確認は省略せず、5章に従ってゲームの実装項目を減らします。

## 5. 遅延時の省略順

全体の進行が遅れている場合は、次の表を上から順に適用します。

| #   | 省略・変更する内容                                                                    | 判断の目安            |
| --- | ------------------------------------------------------------------------------------- | --------------------- |
| 1   | 発展課題を省略する（`stretch-goal` のIssueをすべて閉じる）                            | 4人以上がロジック未完 |
| 2   | UIの作り込みを省略する（CSS Modulesは使わず、`GameShell` + `Hand` + `Button` に絞る） | 3人以上が画面未表示   |
| 3   | PR本文を簡素にする（「実装内容」と `Closes #` だけ）                                  | ReadyのPRが6本以下    |
| 4   | ReadyになったPull Requestから順にマージする（9本そろうのを待たない）                  | マージが5本以下       |

### 省略できない4項目

次の4項目は、進行が遅れている場合も省略しません。

1. **Draft PRを作成すること** — 実装途中の状態を共有する
2. **Pull Requestを提出すること** — 変更内容を参加者の言葉で説明する
3. **ブラウザで操作して修正すること** — テスト結果だけで判断せず、画面で動作を確認する
4. **マージすること** — 変更を `main` に反映し、公開する

ブラウザでの動作確認は省略しないでください。机間巡視では、ブラウザを操作していない参加者がいないか確認します。

### 全体の進行が大幅に遅れている場合

次の方針でマージを進めます。

- ReadyになったPull Requestから順にマージする（9本そろうのを待たない）
- `status: "coming-soon"` のままの PR も、CI が成功していればマージする

この場合も、Pull Request本文の説明量は減らせますが、ブラウザでの動作確認は省略しません。
動作を確認していないゲームを公開すると、不具合に気づかないまま公開する可能性があります。

## 6. 緊急時の対応

影響範囲が狭いものから順に記載しています。上から順に確認します。
手順3以降を実行した場合は、研修後に設定や変更を元に戻します。

### 1. Pull Request単位の管理者マージ

CIが失敗している、または時間がない場合に、対象のPull Requestだけを管理者権限でマージします。
ブランチ保護は `enforce_admins: false` のため、講師（管理者）は `--admin` を指定できます。
他のPull Requestにはブランチ保護が引き続き適用されます。

```powershell
gh pr merge <番号> --squash --admin --delete-branch
```

### 2. CIが利用できない（GitHub Actionsの障害、Node.jsのバージョン変更など）

9人全員のCIが失敗している場合に限り、この手順を使います。1人だけ失敗している場合は、そのPull Requestの内容を確認してください。

```powershell
gh api -X DELETE "repos/Daisuke0719/card_arcade/branches/main/protection/required_status_checks"
```

研修後に、次のコマンドで設定を戻します。

```powershell
node scripts/setup-github.mjs protect
```

### 3. ブランチ保護を一時的に解除する

手順1と2で対応できず、残り時間がわずかで1本もマージできていない場合に限って実行します。

```powershell
node scripts/setup-github.mjs unprotect
```

研修後に、次のコマンドで設定を戻します。

```powershell
node scripts/setup-github.mjs protect
```

この復旧コマンドは、当日の朝にメモ帳へコピーしておきます。

### 4. 誤ってマージした変更を元に戻す

`main` に問題のある変更をマージした場合は、`git reset` ではなく `revert` を使います。
履歴を書き換えず、取り消し用のコミットを追加するためです。

```powershell
git switch main
git pull
git log --oneline -5
git revert <コミットSHA>
git push
```

Squashマージを使用しているため、マージコミットにはなりません。`-m 1` は不要です。

変更を戻した場合は、対象の参加者に理由を説明してください。説明がないと、自分の変更が消えた理由を判断できません。

### 5. ハーネスを無効にする（`CARD_ARCADE_HARNESS=off`）

特定の1台で、フックが誤作動して作業が完全に止まった場合です。

Claude Codeを起動する前に、その端末のPowerShellで次を実行します。

```powershell
$env:CARD_ARCADE_HARNESS = "off"
claude
```

- 効くのは **`.claude/hooks/` のフック**と **`.githooks/pre-commit`** と **`npm run scope`** だけです。
- CIは引き続き動作します。範囲外を変更するとPull Requestの検証は失敗します。
- `npm run dev` の拒否も無効になります。ターミナルAとBで同時に起動すると5173番ポートが競合するため、
  ハーネスを無効にしたことを参加者へ伝えます。
- Claude Codeのセッション内からは設定できません。`.claude/` は保護領域であり、
  設定ファイルの変更もフックが拒否します。起動前に講師が端末で設定します。
- 元に戻すときは PowerShell を閉じるか、次を実行します。

  ```powershell
  Remove-Item Env:CARD_ARCADE_HARNESS
  ```

### 6. 参加者のPCを利用できなくなった

個人作業では担当を別の参加者へ引き継がないため、講師が支援する範囲を明確にします。

対応は次の順です。

1. 事前に用意した予備PCを使用する
2. 予備がなければ、講師の端末を貸して参加者本人に操作してもらう
   `gh auth login` を本人のアカウントでやり直せば、その人の Pull Request として出せます
3. どちらもできないときは、他の参加者の画面で作業内容を確認してもらう。
   担当ゲームは提出できませんが、他の参加者のマージと公開を確認します

手順3の場合は、実装以外に確認できた内容を評価へ記録します。

### 補足A. 範囲チェックだけが失敗するPull Requestを個別に許可する

管理者マージ（手順1）より影響を抑えて、範囲チェックだけを警告に変更する方法です。

対象のPull Requestに `harness:override` ラベルを付けると、CIの範囲チェックが警告のみになります
（`.github/workflows/ci.yml` がラベルを見て `scope-guard.mjs` に `--warn-only` を渡します）。
lint / 型 / テスト / ビルドは**通常どおり必須のまま**です。

```powershell
gh pr edit <番号> --add-label "harness:override"
gh pr checks <番号> --watch
```

このラベルは講師だけが使用します。参加者への案内は不要です。

### 補足B. 当日の朝、メモ帳にコピーしておくコマンド

```powershell
# 進み具合を投影する
npm run status

# Pull Request を1本だけ管理者権限でマージする
gh pr merge <番号> --squash --admin --delete-branch

# 保護を戻す（研修後に必ず実行）
node scripts/setup-github.mjs protect
```

## 7. 研修前の検証手順

研修前に、次の2点を確認します。

> 1. 制限対象の操作が拒否されることを確認する。
> 2. 許可対象の操作が承認なしで実行されることを確認する。

拒否される操作だけでなく、許可される操作も確認してください。必要な操作まで拒否されると、当日の作業を進められません。
ローカルで検出できなかった違反はCIでも検査されますが、必要な操作まで拒否されると作業を継続できません。
たとえば、`npm test` の実行ごとに承認が必要になると、9人全員に不要な確認作業が発生します。
そのため、許可対象の操作も事前に確認します。

準備として、講師の端末で作業用のブランチを1本作り、ターミナルBで `npm run dev` を実行します。
（当日と同じ2窓の状態にしないと、`npm run dev` の拒否メッセージが正しく出るかを判断できません。）

```powershell
git switch main
git pull
git switch -c feature/speed
```

### 7-6. Windows固有 — 改行コードによってPRの差分がファイル全体にならないか

Windows端末の改行コードが統一されていないと、Pull Requestの差分がファイル全体に及ぶ場合があります。
この誤操作は複数の参加者に影響するため、事前に確認してください。

```powershell
git config --global core.autocrlf true
git clone https://github.com/Daisuke0719/card_arcade.git C:/temp/ca-crlf-check
cd C:/temp/ca-crlf-check
npm ci
git status
```

期待する結果は `nothing to commit, working tree clean` です。

`.gitattributes` に `* text=auto eol=lf` を書いてあるので、`core.autocrlf=true` の端末でも
作業ツリーは LF のままになり、clone 直後に差分は出ません。

ここで大量の変更が表示された場合は、当日に全参加者の `npm run scope` が開始時点から失敗します。
`.gitattributes` が正しく取り込まれているかを確認してください。

確認後、後片付けします。

```powershell
cd C:/Users/daisu/project/card_arcade
Remove-Item -Recurse -Force C:/temp/ca-crlf-check
```

### 8-3. 講師の対応が必要なもの

次の3種類は講師の権限や設定変更が必要です。参加者から報告を受けたら、講師が対応します。

#### (1) 権限（403 / Permission denied）

collaboratorの招待を承諾していない場合に起こりやすい問題です。まず招待の状態を確認してください。

```powershell
node scripts/setup-github.mjs collaborators
node scripts/setup-github.mjs collaborators <GitHubユーザー名>
```

参加者に招待メールを開いて承諾してもらいます。メールが見つからない場合は、参加者のブラウザで
https://github.com/Daisuke0719/card_arcade を開きます。画面上部に承諾ボタンが表示されます。

招待を承諾するまで、その参加者は自分のアカウントでPull Requestを作成できません。

#### (2) ブランチ保護（マージできない / チェックが終わらない）

| 症状                                                       | 原因                                        | 対処                                                                   |
| ---------------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------- |
| 「Expected — Waiting for status to be reported」が消えない | 必須チェックの名前が実際のジョブ名と違う    | 6章2で必須チェックを外すか、`contexts` を実名に直す                    |
| CIは成功しているがマージできない                           | CODEOWNERS が所有するファイルを変更している | `gh pr diff <番号>` で範囲を確認。運営領域を変更している場合は差し戻す |
| 承認済みなのにマージできない                               | 単に CI がまだ実行中                        | `gh pr checks <番号> --watch` で待つ                                   |
| 上記を確認してもマージできない                             | —                                           | 6章1の `--admin` でマージする                                          |

#### (3) GitHub Pages（公開されない / 404 になる）

```powershell
gh run list --workflow=deploy-pages.yml --limit 5
gh run view --log-failed
```

| 症状                       | 原因                                                   | 対処                                                      |
| -------------------------- | ------------------------------------------------------ | --------------------------------------------------------- |
| ワークフローが起動しない   | Pages の Source が `Deploy from a branch` になっている | Settings > Pages で **GitHub Actions** に変える           |
| 404 になる                 | 初回デプロイがまだ終わっていない                       | 2〜3分待つ。`gh run list` で `completed` を確認           |
| 画面は出るが真っ白         | `base` の設定                                          | `vite.config.ts` の `base: "./"` を確認（変更不要のはず） |
| マージしたのに反映されない | デプロイが順番待ちしている                             | `gh run list` で実行状況を確認し、完了を待つ              |

研修の終了時に全員で公開URLを開く前に、講師が表示を確認します。
9本目のマージからデプロイ完了まで2〜3分かかるため、最後のマージは余裕をもって行います。

#### (4) ハーネス自体の誤作動

「正しいことをしているのに止められた」という報告が来た場合です。

1. 拒否メッセージと操作内容を照合します。担当外の変更や、ターミナルAでの `dev` 実行が原因の場合があります。
   拒否メッセージの全文を確認します。
2. 誤作動であれば、その端末だけ6章5（`$env:CARD_ARCADE_HARNESS = "off"`）で無効にします。
3. CIは引き続き動作するため、範囲外を変更すると検証は失敗します。そのことを参加者に伝えます。
4. `dev` の拒否も無効になるため、ターミナルAで起動してポートを競合させないよう参加者へ伝えます。
5. 範囲チェックだけが原因でPull Requestの検証が失敗する場合は、6章 補足Aの `harness:override` ラベルをPull Request単位で適用できます。

## 9. 評価

### 9-1. 配点

| 評価項目                                   | 配点    |
| ------------------------------------------ | ------- |
| Issue の必須要件を満たした                 | 25      |
| 担当範囲を守った                           | 10      |
| 適切なテストを作成した                     | 20      |
| Pull Request を分かりやすく書いた          | 15      |
| ブラウザで操作して不具合を見つけ、修正した | 20      |
| UI とゲームとしての工夫                    | 10      |
| **合計**                                   | **100** |

ゲームの完成自体には直接配点していません。
100点のうち65点（担当範囲10 + テスト20 + PR15 + 動作確認20）は、作業手順と確認内容に対する配点です。
プロンプト中心の進行でも、この配点は変わりません。

### 9-2. 集計の材料

自動集計できる項目は、評価前に次の2つのコマンドで確認します。

```powershell
npm run status
node scripts/score.mjs
```

`node scripts/score.mjs` が9人分について出すのは次の4つです。

- 完成宣言（`index.ts` が `status: "ready"` になっているか）
- テスト件数（`logic.test.ts` などの `it(` の数）
- Pull Request の有無と状態
- PR本文の文字数

### 9-3. 自動判定できない項目を講師が確認する

`score.mjs` は最後に次の案内を出力します。

> ※ テストの中身の妥当性や命名の分かりやすさは機械では測れません。
> そこは講師が実際に遊び、コードを読んで評価してください。

件数や成否は自動で判定し、内容の質は講師が確認します。CIも同じ方針で設計しています。

| 項目                       | 自動で確認する内容                                          | 講師が確認する内容                                                                   |
| -------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 必須要件を満たした 25      | `status: "ready"` / CI が成功                               | Issueの必須要件と実装を照合し、ブラウザで操作する                                    |
| 担当範囲を守った 10        | CI の範囲チェックが成功 / `harness:override` を使っていない | —                                                                                    |
| 適切なテストを作成した 20  | テスト件数（3件が下限）                                     | 境界値と異常系があるか。正常系だけなら半分以下                                       |
| PR を分かりやすく書いた 15 | 本文の文字数 / `Closes #` の有無                            | 「自分でも不安なところ」が具体的に書かれているか                                     |
| 実際に遊んで修正した 20    | 実装中のコミット数                                          | 不具合を見つけて修正した履歴があるか。机間巡視の記録（3-3 の (3)）と合わせて確認する |
| UI とゲームの工夫 10       | —                                                           | 講師がブラウザで操作して判断                                                         |

未達の要件を記載したこと自体は減点しません。
省略した要件を説明できているかを確認します（手順書でも参加者に同じ指示をしています）。

### 9-4. 講師が当日に記録する項目

次の項目は自動集計できないため、当日に記録します。

- ブラウザで操作し、問題を修正していたか（3-3の(3)）。該当者の名前を記録します

この記録は、`score.mjs` の集計結果と実際の作業状況が一致しない場合に参照します。
「テスト件数は多いが、ブラウザで一度も遊んでいなかった」という人は、
テスト内容を確認したうえで、テスト項目の点数を判断します。

未完成の場合も、実際に遊んで問題を見つけ、修正した過程は評価してください。
完成状況だけでなく、確認と修正の過程も評価対象です。

### 9-5. 採点の実務

採点は研修後に行います。研修中は参加者への対応を優先します。

`npm run status` のスクリーンショットを節目ごとに保存し、
研修後に `node scripts/score.mjs` の出力と合わせて採点します。
この4枚を、研修後に進行状況を確認するための記録として使用します。
