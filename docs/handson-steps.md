# ハンズオン手順

「Claude Code × GitHub 共同開発ハンズオン — みんなでつくる CARD ARCADE」で使用する手順書です。
**上から順に進めてください。** 迷ったときは、いま取り組んでいるフェーズの「完了条件」を確認してください。

- **参加者9名が、1人1ゲームずつ担当します。** チームには分かれません。調査から実装、Pull Request の提出まで、各自で一通り行います。
- 当日はフェーズ1〜7の順に進みます。**環境の用意もフェーズ1で行います。** 事前の準備は要りません。
- 各フェーズには、入力するプロンプトと完了条件を記載しています。
- 当日の作業は、**Claude Code に日本語で依頼しながら進めます。** 覚えるコマンドはありません。
  掲載しているプロンプトは、そのままコピーして使用できます。
- 一部の作業は、Claude Codeを使わずに参加者が行います。作業場所を区別するため、次の「ターミナル2本体制」を採用します。

## この手順書の読み方

プロンプトやコマンドに含まれる `< >` は、自分の値に置き換えてください。**変更するのはこの部分だけです。**

| 書き方 | 意味 | 例 |
|---|---|---|
| `<ゲームID>` | 自分が担当するゲームのゲームID（ローマ字） | `babanuki` |
| `<Issue番号>` | 自分のゲームの Issue 番号 | `1` |
| `<自分のPR番号>` | 自分が作った Pull Request の番号 | `13` |

各フェーズは、次の3項目で構成しています。

| 区画 | 中身 |
|---|---|
| **入力するプロンプト** | ターミナルA（Claude Code）に貼り付ける文面。全文をそのまま使ってください |
| **ターミナルB でやること** | 参加者が入力するコマンドと、画面を見ながら行う作業 |
| **完了条件** | すべて満たしたら次のフェーズに進みます |

プロンプトを自分の言葉に書き換えても構いませんが、**次の3つは消さないでください。**

1. **対象範囲を限定する言葉**（「`src/games/<ゲームID>/` の中だけ」「ほかのファイルは変更しないで」）
2. **止める言葉**（「まだ直さないで」「投稿はしないで」「要約しないで」）
3. **実行させない言葉**（「`npm run dev` は実行しないで」「`gh pr ready` は実行しないで」）

この3つによって、Claude Code に任せる範囲と、自分で判断する範囲を分けます。

## 2つのターミナルの役割を確認する

**当日は PowerShell を2つ開きます。** 片方でのみ Claude Code を起動し、もう片方では**起動しないでください。**

| | ターミナルA（Claude Code を使用） | ターミナルB（参加者が直接操作） |
|---|---|---|
| 常に動かしておくもの | Claude Code のセッション | **`npm run dev`（研修中は起動したままにします）** |
| ここで行うこと | 調査 / 実装の依頼 / 差分の確認 / 文章の下書き | 実際に遊ぶ / `npm test` の手動確認 / `gh pr ready` |
| ここでは行わないこと | `npm run dev`（**仕組み上、起動できません**）／PR・Issue への投稿 | Claude Code の起動 |

### なぜ2本に分けるのか

当日の作業は、そのほとんどを Claude Code へのプロンプトで進めます。
そのぶん、どこまでを Claude Code に任せ、どこからを自分で判断するのかが曖昧になりがちです。
そこでこの研修では、**参加者が行う作業を別のターミナルに分けています。**

- ゲームを実際に操作し、不具合がないか参加者が判断します。
  Claude Code はブラウザ上でゲームを操作できません。
- Pull Requestを提出してよいかは、参加者が判断します。
  動作を確認した参加者が `gh pr ready` を実行します。
- 役割分担を維持するため、ターミナルBで行う作業の一部は、ターミナルAでは実行できない仕組みになっています。

### A と B の見分け方（画面を追加した場合）

ターミナルB では `npm run dev` を起動したままにします。別のコマンドを入力したい場合は、**PowerShell を追加で開いて構いません。**

> **追加で開いた画面は、すべて「B」として扱います。**
> A と B の違いは画面の数ではなく、**Claude Code を起動しているかどうか**です。
> Claude Code を起動する画面は、当日を通して**1つだけ**にしてください。

Windows Terminal を使っている場合は、タブを追加すると便利です（`Ctrl + Shift + T`）。

## 当日の進め方（フェーズ1〜7）

| フェーズ | 内容 | 主に使うターミナル |
|---|---|---|
| フェーズ1 | 環境を用意して、担当を確認する | A → B |
| フェーズ2 | 担当ゲームのルールを読む | A → B |
| フェーズ3 | ブランチと雛形を用意し、Draft の Pull Request を出す | A → B |
| フェーズ4 | まず最後まで遊べる形にする | A → B |

| フェーズ6 | Pull Request を提出する | A → B |
| フェーズ7 | マージ | B → A |

進む速さは人によって違います。フェーズの区切りごとに講師が全体の進み具合を確認するので、
先に進んでいても、遅れていても、そのまま自分のペースで続けてください。

> **`npm run dev` は、フェーズ1で起動してから研修が終わるまで動かしたままにします。**
> 誤って `Ctrl + C` を押さないよう注意してください。
> コードの変更を画面に反映するときは、**ブラウザを再読み込み（F5）**します。開発サーバーを再起動する必要はありません。
> 誤って停止した場合は、同じターミナルで `npm run dev` をもう一度実行すれば再開できます。

### フェーズ1｜環境を用意して、担当を確認する

#### 1. 必要なツールをインストールする（自分で操作）

Node.js 22 以上、Git、GitHub CLI の3つをインストールします。

| ツール | 入手先 | 備考 |
|---|---|---|
| Node.js 22.x | https://nodejs.org/ | LTS の 22 系。20 以下では動きません |
| Git for Windows | https://git-scm.com/download/win | |
| GitHub CLI (`gh`) | https://cli.github.com/ | |

インストール後、**PowerShell を開き直してから**確認します。

```powershell
node -v
git --version
gh --version
```

#### 2. GitHub の招待を承諾し、gh にログインする（自分で操作）

講師から届く**招待メール**（リポジトリ `Daisuke0719/card_arcade` へのコラボレーター招待）を承諾します。
承諾していないと、あとで push が 403 で失敗します。

```powershell
gh auth login
```

画面の案内に従って、次の項目を選びます。

1. `GitHub.com`
2. `HTTPS`
3. `Login with a web browser`（ブラウザが開くのでコードを貼り付ける）

終わったら確認します。

```powershell
gh auth status
gh repo view Daisuke0719/card_arcade --json name
```

`gh auth status` に `Logged in to github.com` と出て、`Token scopes` に `repo` が含まれていれば成功です。
`gh repo view` で 403 が出たら、招待がまだ承諾できていません。


#### 3. リポジトリを clone する（自分で操作）

```powershell
cd [任意のフォルダ]
git clone https://github.com/Daisuke0719/card_arcade.git
cd card_arcade
git status
```

`card_arcade` フォルダの中に `package.json` と `CLAUDE.md` があり、
`git status` が `On branch main` と `nothing to commit, working tree clean` を返せば成功です。

#### 4. ターミナルA で Claude Code を起動する

clone したフォルダで Claude Code を起動します。**この画面を「ターミナルA」と呼びます。**

```powershell
cd [任意のフォルダ]/card_arcade
claude
```

画面下のステータスラインに `担当未設定 ⋅ main ⋅ 変更なし` のような表示と、
起動時の「今のセッションの前提」という案内が出れば起動できています
（まだブランチを作っていないので「担当未設定」で正常です）。

#### 5. 依存関係をインストールし、環境を確認する

**入力するプロンプト**

```text
環境の準備をします。次の2つを、この順番で実行してください。

1. npm ci
2. npm run doctor

npm install は使わないでください（package-lock.json が書き換わるとCIが失敗します）。
npm run dev は実行しないでください。私が別のターミナルで動かします。

npm run doctor に ✗ が出たら、直そうとしないでください。
✗ の行と、その直下にある「→」の行を、そのまま表示してください。
```

`npm ci` には3〜5分かかります。最後に `prepare` が動き、コミット前チェックが自動で有効になります。

#### 6. ターミナルB を開き、画面が表示されることを確認する（自分で操作）

**PowerShell をもう1つ開きます。こちらを「ターミナルB」と呼びます。**
**ターミナルAの `npm ci` が完了したこと**を確認してから実行してください。

```powershell
cd [任意のフォルダ]/card_arcade
npm run dev
```

> **`npm ci` より先に `npm run dev` を起動しないでください。**
> 開発サーバーが `node_modules` 内のファイルを使用したままになるため、Windows では `npm ci` が
> ファイル使用中のエラーで失敗します。**順番は必ず `npm ci` → `npm run dev` です。**

ブラウザで `http://localhost:5173/` を開き、CARD ARCADE の一覧と「ハイ＆ロー」（運営のお手本ゲーム）が
**最後まで1回遊べること**を確認します。

**ここから研修が終わるまで、`npm run dev` は起動したままにします。**
テストなどのコマンドを自分で実行するときは、**PowerShell をもう1つ開いてください。** 追加した画面も「B」として扱います。

**完了条件**

- [ ] 自分の担当（担当1〜9）とゲーム名、ゲームID、Issue 番号をメモした
- [ ] 「編集してよいのは `src/games/<ゲームID>/` の中だけ」を理解した
- [ ] `node -v` が `v22.` で始まり、`gh auth status` が `Logged in` を返す
- [ ] `card_arcade` を clone し、`git status` が `nothing to commit, working tree clean`
- [ ] ターミナルA で Claude Code が起動し、「今のセッションの前提」が出ている
- [ ] `npm run doctor` が `すべて問題ありません。` で終わる（9項目に ✗ が無い）
- [ ] ターミナルB で `npm run dev` が動いていて、CARD ARCADE の一覧が出ている
- [ ] 「ハイ＆ロー」を最後まで1回遊べた
- [ ] ターミナルA とターミナルB の役割の違いを説明できる

### フェーズ2｜担当ゲームのルールを読む

自分が担当するゲームのルールは `docs/games/<ゲームID>.md` にあります。まずここを確認してください。
あわせて、GitHub の Issue に記載されている内容も確認します。

**入力するプロンプト**

1つ目 — Issueの原文を表示するよう依頼します。

```text
gh issue view <Issue番号> を実行して、出力をそのまま全文表示してください。
要約・省略・並べ替え・言い換えをしないでください。原文のまま出してください。

最後に、必須要件（チェックボックスの行）の件数だけを教えてください。
解説や所感は不要です。
```

2つ目 — ルール文書から、間違えやすい2か所を引用します。

```text
docs/games/<ゲームID>.md を開き、次の2つの見出しに含まれる内容を原文のまま表示してください。

- 「今回は実装しないルール」の表
- 「時間が足りないときの省略順」

要約しないでください。解釈や補足も足さないでください。原文のまま出してください。
```

**ターミナルB でやること**

あとで実装内容と照合できるよう、Issue をブラウザでも開いておきます。

```powershell
gh issue view <Issue番号> --web
```

（`npm run dev` が動いているターミナルとは**別のターミナル**で実行してください）

**読みながら確認する2点**

1. **必須要件が何件あるか**を数える（この件数を進捗確認に使います）
2. **「今回は実装しないルール」**を確認する（Issue に無いことは実装しません）

**完了条件**

- [ ] Issue が**原文のまま**表示され、最後まで読んだ（要約させていない）
- [ ] 必須要件の**件数**を言える
- [ ] 「今回は実装しないルール」を確認した（Issue に無いことは実装しません）

### フェーズ3｜ブランチと雛形を用意し、Draft の Pull Request を出す

作業ブランチを作り、雛形（5ファイル）を生成してから、**実装前の状態で Pull Request を作成します。**

実装前に Pull Request を作るのは、権限設定（招待の未承諾）、CI、改行コードなどの問題を早めに見つけるためです。先に一連の流れを通しておけば、完成後に問題が判明して大きな手戻りが生じるのを防げます。

**入力するプロンプト**

1つ目 — ブランチを作り、雛形を生成します。

```text
これから <ゲームID> の実装を始めます。次の5つを、この順番で実行してください。

1. git switch main
2. git pull
3. git switch -c feature/<ゲームID>
4. npm run scaffold -- --game <ゲームID>
5. npm test

そのあと、src/games/<ゲームID>/ に生成された5つのファイルについて、
「ファイル名 … 役割」の形式で、1ファイルにつき1行、合計5行で説明してください。

ファイルは変更せず、まだ実装を始めないでください。
```

このプロンプトの実行が終わったら、**いったん `/exit` し、`claude` を起動し直してください。**
起動時の案内とステータスラインが、自分の担当に切り替わります。

生成されるファイル:

```text
src/games/<ゲームID>/
├─ index.ts            ゲームの公開情報（GameManifest）
├─ <Xxx>Game.tsx       画面
├─ logic.ts            ルール（純粋関数だけ）
├─ logic.test.ts       ロジックのテスト
└─ README.md           遊び方 / ルール / 実装メモ
```

`index.ts` には自分の担当が `owner` として書き込まれています。
`id` / `name` / `owner` / `difficulty` は運営が決めた値なので変更しないでください（変更すると契約テストとCIが失敗します）。


2つ目 — 変更内容を確認してからコミットします。

```text
コミットの前に git status --short を実行し、変更されたファイルの一覧をそのまま表示してください。

そのうえで、git add の対象は src/games/<ゲームID> だけにして、
次のメッセージでコミットしてください。

  chore(<ゲームID>): 雛形を追加する

src/games/<ゲームID> の外にあるファイルは、1つも add しないでください。
```

3つ目 — push と Draft の Pull Request の作成。**ここで実行の承認を求められます。**

```text
push して、Draft の Pull Request を作ってください。

- push: git push -u origin HEAD
- PR: gh pr create --draft --title "<ゲームID> を実装する" --body "雛形を置いただけの Draft です。実装はこれから進めます。Closes #<Issue番号>"

作成した Pull Request の番号を最後に教えてください。
gh pr ready は実行しないでください。Draft のままにします。
```

**Claude Codeに依頼すること**

| 実行されるコマンド | 承認 |
|---|---|
| `git switch` / `git pull` / `npm run scaffold` / `npm test` | 確認なしで通る |
| `git status --short` / `git add src/games/<ゲームID>` / `git commit` | 確認なしで通る（pre-commit が走ります） |
| `git push -u origin HEAD` | **実行前に承認が必要** |
| `gh pr create --draft ...` | **実行前に承認が必要** |

**ターミナルB でやること**

1. ブラウザ（`http://localhost:5173/`）を **F5 で再読み込み**します。
   自分のゲームが一覧に「準備中（coming soon）」として出ていれば成功です。
2. ターミナルA を `/exit` → `claude` で起動し直したら、**画面下のステータスライン**を見ます。

```text
担当1 ババ抜き ⋅ feature/babanuki ⋅ 変更なし
```

のように、**担当名・ゲーム名・ブランチ名**が出ていれば、ハーネスが自分を正しく認識しています。
`担当未設定` のままなら、ブランチができていません。1つ目のプロンプトの 3 番からやり直してください。

3. CI が完了するまで状態を確認します。

```powershell
gh pr checks <自分のPR番号> --watch
gh pr view <自分のPR番号>
```

`verify` が成功したら、**PR 番号を手順書の先頭にあるメモ欄へ記入してください。**

**完了条件**

- [ ] ステータスラインに**自分の担当名とゲーム名**が出ている
- [ ] `src/games/<ゲームID>/` に5ファイルができている
- [ ] ブラウザの一覧に自分のゲームが「準備中」で出ている
- [ ] `git push` が成功した（403 が出たら**すぐ手を挙げる**。招待が未承諾です）
- [ ] push と PR 作成の承認を押す前に、画面に出ているコマンドを読んだ
- [ ] Draft の Pull Request ができている
- [ ] `gh pr checks` で `verify` が成功した
- [ ] 自分の PR 番号をメモした
- [ ] コミットに `src/games/<ゲームID>` の外のファイルが入っていない

> **CI が失敗した場合は、ここで修正します。** 解決するまで実装には進まないでください。
> よくある原因は「担当フォルダの外を `git add` してしまった」です。次のプロンプトで直せます。
>
> ```text
> npm run scope を実行して、範囲外の変更があるか確認してください。
> 範囲外があれば、scope が出す git restore のコマンドをそのまま実行して戻してください。
> src/games/<ゲームID> の中身は消さないでください。
> ```

### フェーズ4｜まず最後まで遊べる形にする

細かい仕上げは後にして、**最初から最後まで遊べる状態**を先に作ります。発展課題には手を付けません。動くものができてから、フェーズ5で遊びながら直していきます。

実装を依頼する前に、**予定している変更内容の説明を求めます。**

Issueと計画が一致していることを、参加者が確認してください。不一致のまま実装すると、手戻りが発生します。

**入力するプロンプト**

1つ目では、実装計画の作成だけを依頼します。この段階ではコードを変更しません。

```text
GitHub の Issue #<Issue番号> と docs/games/<ゲームID>.md を読んで、
src/games/<ゲームID>/ にこのゲームをどう実装するか計画を立ててください。

- Issue にも docs/games/<ゲームID>.md にも書かれていないルールは足さないでください。
- まだコードは書かないでください。ファイルも変更しないでください。
```

表示された計画を、Issue の必須要件と上から順に照らし合わせてください。
**どの実装が対応するのか分からない要件があれば、その場で伝えます。**

```text
必須要件の「<Issue の要件の文言をそのまま貼る>」に対応する項目が計画にありません。
どこで実現するつもりなのかを計画に足してください。まだ実装はしないでください。
```

```text
計画の「<計画の中の1行をそのまま貼る>」は、Issue にも docs/games/<ゲームID>.md にも書かれていないルールです。
Issue に無いものは実装しないので、計画から外してください。まだ実装はしないでください。
```

2つ目 — 計画に納得できたら、実装を依頼します。

```text
その計画で実装してください。まず最後まで遊べる状態にすることを優先し、発展課題には手を付けないでください。
```

3つ目 — 依頼していない範囲まで変更が広がったときに入力します。

```text
src/games/<ゲームID>/ の外が変更されています。
その変更を元に戻してから、変更したファイルの一覧をもう一度報告してください。
```

**ターミナルB でやること**

1. **自分でテストを1回実行します。**

```powershell
npm test
```
（`npm run dev` が動いているターミナルとは別のターミナルで実行します）

2. **ブラウザを F5 で再読み込みし、最初から最後まで1回遊びます。**

途中で操作できなくなる、画面が真っ白になる、決着がつかない、といった状態であれば、
そのままフェーズ5に進んで直していきます。**この時点で完璧である必要はありません。**

3. **終わった必須要件に、GitHub の Issue 画面でチェックを入れます。**

**完了条件**

- [ ] 実装の計画を読み、Issue の必須要件と照らし合わせた
- [ ] `npm test` が成功した（**ターミナルBで1回実行した**）
- [ ] ブラウザで自分のゲームが表示され、操作できる
- [ ] `git status` の変更が `src/games/<ゲームID>/` の中だけに収まっている

### フェーズ5｜遊んで、気づいたところを直す

**遊ぶ → 気づいたことを伝える → 直してもらう → もう一度遊ぶ**、これを繰り返します。
このフェーズには、ほかのフェーズより多くの時間を割り当てます。

#### ターミナルB でやること

ブラウザを **F5 で再読み込み**して遊びます。

1. **最初から最後まで、途中で止めずに1回遊ぶ**
2. **やってはいけない操作を試す**（CPU の手番中に連打する / 出せないカードを出す / 0枚のときに引く）
3. リセット後に、2回目のゲームが正しい初期状態で始まるか確認する

（神経衰弱のように1人用のゲームは、CPU と他プレイヤーの項目を自分のゲームに読み替えてください）

#### 不具合が見つかったときに入力するプロンプト（ターミナルA）

プランモードで改善計画を立てる。

/planを実行後いかを入力
```text
ブラウザで遊んだところ <起きたこと> になりました。期待する動作は <期待していたこと> です。

原因を特定して改善策を計画してください。
まだファイルは変更しないでください。
```

計画を確認し問題なければ実行させる。
直したあとは、**もう一度ブラウザを再読み込みして同じ操作を試します。** これを繰り返します。

#### 残りの必須要件を実装する

遊べる状態になったら、まだ足りていない必須要件を追加します。

```text
Issue #<Issue番号> の必須要件のうち、まだ実装できていないものを一覧にしてください。
そのうえで、上から順に実装してください。

終わったら npm test を実行し、結果を報告してください。
```

必須要件がすべて揃ったら、アーケードの一覧で遊べる状態にします。

```text
src/games/<ゲームID>/index.ts の status を "ready" にしてください。
ほかの項目（id / name / owner / difficulty）は変更しないでください。
そのあと npm test を実行して、結果を報告してください。
```

**完了条件**

- [ ] ブラウザで**最初から最後まで1回遊び切れた**（自分で実際に操作した）
- [ ] やってはいけない操作を試し、弾かれることを確認した
- [ ] 見つけた不具合を伝えて直してもらい、**直ったことをブラウザで確認した**
- [ ] `npm test` が成功する
- [ ] Issue の必須要件チェックリストが満たされている

### フェーズ6｜Pull Request を提出する

`npm run verify` を成功させて、Pull Request の本文を仕上げます。
このコマンドでは、CI とまったく同じ検証が行われます。**成功してから提出してください。**

**入力するプロンプト**

```text
Pull Request を提出します。次を順に実行してください。

1. npm run verify
2. git add src/games/<ゲームID>
3. git commit -m "feat(<ゲームID>): ゲームを実装する"
4. git push
5. .github/PULL_REQUEST_TEMPLATE.md の形式で、Pull Request の本文を .pr-body.md に書く
6. gh pr edit <自分のPR番号> --body-file .pr-body.md

npm run verify が失敗したら、そこで止めて最初のエラーだけを報告してください。
本文は git diff origin/main...HEAD を読んで、実際の変更内容にもとづいて書いてください。
満たせていない必須要件があれば、「発展課題・未対応事項」に正直に書いてください。

gh pr ready は実行しないでください。私が自分で入力します。
```

**Claude Codeに依頼すること**

| 実行されるコマンド | 承認 |
|---|---|
| `npm run verify`（範囲チェック → lint → 型 → テスト → ビルド） | 確認なしで通る |
| `git diff` / `.pr-body.md` の作成 | 確認なしで通る |
| `git add` / `git commit` | 確認なしで通る |
| `git push` | **実行前に承認が必要** |
| `gh pr edit <自分のPR番号> --body-file .pr-body.md` | **実行前に承認が必要** |

**ターミナルB でやること**

Draft 状態を解除し、CI を確認します。

```powershell
gh pr ready <自分のPR番号>
gh pr checks <自分のPR番号> --watch
```

**完了条件**

- [ ] `npm run verify` が成功した
- [ ] Pull Request の Draft が解除されている（**`gh pr ready` を自分で実行した**）
- [ ] CI の `verify` が成功した
- [ ] 講師に PR 番号を伝えた

### フェーズ7｜マージ

**マージは講師が行います。** 参加者はマージしません。
9本の Pull Request が順に `main` に入り、そのたびに GitHub Pages への自動デプロイが動きます。

マージを待つ間は、ターミナルB で自分の Pull Request の CI を確認しておきます。

```powershell
gh pr checks <自分のPR番号>
```

`verify` が失敗したままだと講師はマージできません。失敗している場合は、この時間で直してください。

**入力するプロンプト**

自分の Pull Request がマージされたあとに入力します。

```text
私の Pull Request はマージされました。次の3つを順に実行してください。

1. git switch main
2. git pull
3. git log --oneline -5

そのあと、私のゲーム（src/games/<ゲームID>）のファイルが main に入っているかを確認して、1行で報告してください。
新しいブランチは作らないでください。ファイルも変更しないでください。
```

**ターミナルB でやること**

講師が投影する**公開URL**（GitHub Pages）を開き、
**自分のゲームが「準備中」からプレイ可能な状態に変わったこと**を確認してください。
`main` に切り替えたあとは、手元のブラウザ（`http://localhost:5173/`）もF5で再読み込みします。

終わったら、ターミナルB の `npm run dev` を `Ctrl + C` で停止します。

**完了条件**

- [ ] 自分の Pull Request がマージされた
- [ ] `git switch main` → `git pull` を実行し、自分のゲームが `main` に入っていることを確認した
- [ ] 公開URLで、自分のゲームがプレイ可能になったことを確認した
- [ ] ターミナルB の `npm run dev` を `Ctrl + C` で止めた
