# ハンズオン手順

「Claude Code と GitHub を使った共同開発ハンズオン — みんなでつくる CARD ARCADE」の手順書です。
最初の項目から順に進めます。各Stepの作業を終えたら、「完了条件」を確認してから次へ進んでください。

- 参加者9名が、それぞれ1つのゲームを担当します。チームには分かれません。調査、実装、Pull Request の提出までを各自で行います。
- 当日はStep A〜Dの順に進みます。環境構築もStep Aに含まれるため、事前準備は不要です。
- 各Stepには、Claude Code へ入力するプロンプト、参加者が行う操作、完了条件を記載しています。
- Claude Code への依頼は日本語で入力します。この手順書に掲載しているプロンプトは、そのままコピーして使えます。
- Claude Code を使用するターミナルと、参加者が直接操作するターミナルを分けます。

## この手順書の読み方

プロンプトやコマンドに含まれる `<...>` は、担当に応じた値に置き換えてください。それ以外の部分は変更しないでください。
`[任意のフォルダ]` は、リポジトリを保存するフォルダのパスに置き換えます。

| 書き方           | 意味                             | 例         |
| ---------------- | -------------------------------- | ---------- |
| `<ゲームID>`     | 担当ゲームのゲームID（ローマ字） | `babanuki` |
| `<Issue番号>`    | 担当ゲームの Issue 番号          | `1`        |
| `<自分のPR番号>` | 作成した Pull Request の番号     | `13`       |

各Stepは、主に次の3項目で構成されています。

| 項目                      | 内容                                                                 |
| ------------------------- | -------------------------------------------------------------------- |
| **入力するプロンプト**    | ターミナルA（Claude Code）に貼り付ける文面。全文をそのまま使用します |
| **ターミナルBで行うこと** | 参加者が入力するコマンドと、画面を見ながら行う作業                   |
| **完了条件**              | すべて満たしたら次のStepに進みます                                   |

プロンプトの言い回しは変えても構いません。ただし、次の3種類の指示は残してください。

1. **対象範囲を限定する指示**（「`src/games/<ゲームID>/` の中だけ」「ほかのファイルは変更しないで」）
2. **作業を止める条件**（「まだ直さないで」「投稿はしないで」「要約しないで」）
3. **実行しないコマンドの指定**（「`npm run dev` は実行しないで」「`gh pr ready` は実行しないで」）

これらの指示で、Claude Code に依頼する範囲と、参加者が操作・判断する範囲を明確にします。

## 2つのターミナルを使い分ける

当日は PowerShell を2つ開きます。Claude Code を起動するのは、ターミナルAだけです。

|                      | ターミナルA（Claude Code を使用）                                   | ターミナルB（参加者が直接操作）               |
| -------------------- | ------------------------------------------------------------------- | --------------------------------------------- |
| 常に動かしておくもの | Claude Code のセッション                                            | `npm run dev`（研修中は起動したままにします） |
| ここで行うこと       | 調査、実装の依頼、差分の確認、文章の下書き                          | ゲームの操作、`npm test`、`gh pr ready`       |
| ここでは行わないこと | `npm run dev`（ハーネスで実行を禁止しています）、PR・Issue への投稿 | Claude Code の起動                            |

### ターミナルを分ける理由

当日は、主に Claude Code へプロンプトを入力して作業します。
ゲームの動作確認と Pull Request を提出するかどうかの判断は、参加者が行います。操作する場所を区別して誤操作を防ぐため、ターミナルを分けています。ターミナルBで行う一部のコマンドは、ターミナルAから実行できません。

### PowerShell を追加で開く場合

ターミナルBでは `npm run dev` を起動したままにします。ほかのコマンドを入力するときは、PowerShell を追加で開いて構いません。

> 追加で開いた PowerShell も、ターミナルBとして扱います。
> Claude Code を起動する PowerShell は、ターミナルAの1つだけにしてください。

Windows Terminal を使っている場合は、`Ctrl + Shift + T` でタブを追加できます。

## 当日の進め方（Step A〜D）

| Step | 内容 | 完了時の状態 | 主に使うターミナル |
| ---- | ---- | ------------ | ------------------ |
| Step A | 開発環境を整える | サンプルゲームを最後まで遊べる | A → B |
| Step B | 実装範囲を決める | 作るものと作らないものを説明できる | A → B |
| Step C | 担当ゲームを作り、Pull Requestを提出する | Draftを解除し、CIが成功したPRを講師へ共有できる | AとBを手順に応じて使い分ける |
| Step D | 統合と公開を確認する | 公開先で担当ゲームを開始できる | B → A |

講師がStepの区切りで全体の進捗を確認します。それまでは、各自のペースで作業を進めてください。

> `npm run dev` は、Step Aで起動してから研修終了まで動かしたままにします。
> コードの変更は、ブラウザを `F5` キーで再読み込みすると反映されます。開発サーバーの再起動は不要です。
> `Ctrl + C` などで停止した場合は、同じターミナルでもう一度 `npm run dev` を実行してください。

## Step A｜開発環境を整える

#### 1. 必要なツールをインストールする（参加者が操作）

Node.js 22 以上、Git、GitHub CLI の3つをインストールします。

| ツール            | 入手先                                             | 備考                                           |
| ----------------- | -------------------------------------------------- | ---------------------------------------------- |
| Node.js 22.x      | [Node.js 公式サイト](https://nodejs.org/)          | LTS の22系。20系以前のバージョンでは動きません |
| Git for Windows   | [Git 公式サイト](https://git-scm.com/download/win) |                                                |
| GitHub CLI (`gh`) | [GitHub CLI 公式サイト](https://cli.github.com/)   |                                                |

インストール後に PowerShell を開き直し、バージョンを確認します。

```powershell
node -v
git --version
gh --version
```

#### 2. GitHub の招待を承諾し、gh にログインする（参加者が操作）

講師から届いたリポジトリ `Daisuke0719/card_arcade` へのコラボレーター招待を承諾します。
招待を承諾していない場合、このあとの push が 403 エラーで失敗します。

```powershell
gh auth login
```

画面の案内に従い、次の項目を選択します。

1. `GitHub.com`
2. `HTTPS`
3. `Login with a web browser`（表示されたコードをブラウザに貼り付けます）

ログイン後、接続状態とリポジトリへのアクセス権を確認します。

```powershell
gh auth status
gh repo view Daisuke0719/card_arcade --json name
```

`gh auth status` に `Logged in to github.com` と表示され、`Token scopes` に `repo` が含まれていればログインは完了です。
`gh repo view` で 403 エラーが出た場合は、リポジトリへの招待が承諾済みか確認してください。

#### 3. リポジトリをクローンする（参加者が操作）

```powershell
cd [任意のフォルダ]
git clone https://github.com/Daisuke0719/card_arcade.git
cd card_arcade
git status
```

`card_arcade` フォルダに `package.json` と `CLAUDE.md` があることを確認します。
`git status` に `On branch main` と `nothing to commit, working tree clean` が表示されれば、クローンは完了です。

#### 4. ターミナルAで Claude Code を起動する

クローンしたフォルダで Claude Code を起動します。この画面がターミナルAです。

```powershell
cd [任意のフォルダ]/card_arcade
claude
```

画面下のステータスラインに `担当未設定 ⋅ main ⋅ 変更なし` と表示され、起動時に「今のセッションの前提」という案内が出ることを確認します。
この時点では担当ブランチを作成していないため、`担当未設定` と表示されていて問題ありません。

#### 5. 依存関係をインストールし、環境を確認する

**入力するプロンプト**

```text
環境の準備をします。次の2つを、この順番で実行してください。

1. npm ci
2. npm run doctor

npm install は使わないでください（package-lock.json が書き換わると CI が失敗します）。
npm run dev は実行しないでください。私が別のターミナルで動かします。

npm run doctor に ✗ が出た場合は、修正せずに止めてください。
✗ の行と、その直下にある「→」の行を、そのまま表示してください。
```

`npm ci` には3〜5分かかります。処理の最後に `prepare` が実行され、コミット前のチェックが有効になります。

#### 6. ターミナルBを開き、画面を確認する（参加者が操作）

PowerShell をもう1つ開きます。この画面がターミナルBです。
ターミナルAの `npm ci` が完了してから、次のコマンドを実行します。

```powershell
cd [任意のフォルダ]/card_arcade
npm run dev
```

> `npm run dev` は、必ず `npm ci` の完了後に実行してください。
> 開発サーバーが `node_modules` 内のファイルを使用していると、Windows では `npm ci` がファイル使用中のエラーで失敗します。

ブラウザで `http://localhost:5173/` を開き、CARD ARCADE の一覧が表示されることを確認します。
続けて、サンプルとして用意された「ハイ＆ロー」を最後まで1回遊びます。

`npm run dev` は、ここから研修終了まで起動したままにします。
テストなどのコマンドを実行するときは PowerShell を追加で開き、その画面もターミナルBとして扱います。

**完了条件**

- [ ] 担当番号、ゲーム名、ゲームID、Issue 番号をメモした
- [ ] 編集できる範囲が `src/games/<ゲームID>/` の中だけであることを確認した
- [ ] `node -v` が `v22.` で始まり、`gh auth status` が `Logged in` を返す
- [ ] `card_arcade` をクローンし、`git status` に `nothing to commit, working tree clean` と表示された
- [ ] ターミナルAで Claude Code を起動し、「今のセッションの前提」が表示された
- [ ] `npm run doctor` が `すべて問題ありません。` で終わる（9項目に ✗ が無い）
- [ ] ターミナルBで `npm run dev` が動いていて、CARD ARCADE の一覧が表示された
- [ ] 「ハイ＆ロー」を最後まで1回遊べた
- [ ] ターミナルAとターミナルBの役割の違いを説明できる

## Step B｜実装範囲を決める

担当ゲームのルールは `docs/games/<ゲームID>.md` に記載されています。GitHub の Issue とあわせて確認します。

**入力するプロンプト**

最初のプロンプトでは、Issue 本文の表示を依頼します。

```text
gh issue view <Issue番号> を実行して、出力をそのまま全文表示してください。
要約・省略・並べ替え・言い換えをしないでください。原文のまま出してください。

最後に、必須要件（チェックボックスの行）の件数だけを教えてください。
解説や所感は不要です。
```

次のプロンプトでは、実装範囲を判断するために必要な2つの節を表示します。

```text
docs/games/<ゲームID>.md を開き、次の2つの見出しに含まれる内容を原文のまま表示してください。

- 「今回は実装しないルール」の表
- 「時間が足りないときの省略順」

要約しないでください。解釈や補足も足さないでください。原文のまま出してください。
```

**ターミナルBで行うこと**

実装中に内容を確認できるよう、Issue をブラウザで開いておきます。

```powershell
gh issue view <Issue番号> --web
```

このコマンドは、`npm run dev` を実行している画面とは別のターミナルBで実行します。

**確認すること**

1. 必須要件の件数を数えます。後の進捗確認では、この件数を基準にします。
2. 「今回は実装しないルール」を確認します。Issue とルール文書のどちらにも記載されていない機能は、実装対象に含めません。

**完了条件**

- [ ] Issue 本文が省略されずに表示され、最後まで読んだ
- [ ] 必須要件の件数を確認した
- [ ] 「今回は実装しないルール」を確認した

## Step C｜担当ゲームを作り、Pull Requestを提出する

Step Cでは、担当Issueを作業手順として使います。Issue内のC-1からC-5までを上から順に進めてください。
この手順書では、全員に共通する操作、確認方法、完了条件を説明します。

### C-1　作業ブランチと雛形を用意する

作業ブランチを作成し、5つの雛形ファイルを生成します。実装を始める前に、その状態で Draft の Pull Request を作成します。

この段階で Pull Request を作成すると、リポジトリへの招待、CI、改行コードなどの問題を実装前に確認できます。

**入力するプロンプト**

最初のプロンプトでは、ブランチの作成と雛形の生成を依頼します。

```text
これから <ゲームID> の実装を始めます。次の5つを、この順番で実行してください。

1. git switch main
2. git pull
3. git switch -c feature/<ゲームID>
4. npm run scaffold -- --game <ゲームID>
5. npm test

実行後、src/games/<ゲームID>/ に生成された5つのファイルについて、
「ファイル名 … 役割」の形式で1行ずつ、合計5行で説明してください。

ファイルは変更せず、まだ実装を始めないでください。
```

処理が終わったら、いったん `/exit` し、`claude` を起動し直します。起動時の案内とステータスラインに担当情報が表示されます。

生成されるファイルは次の5つです。

```text
src/games/<ゲームID>/
├─ index.ts            ゲームの公開情報（GameManifest）
├─ <Xxx>Game.tsx       画面
├─ logic.ts            ルール（純粋関数だけ）
├─ logic.test.ts       ロジックのテスト
└─ README.md           遊び方 / ルール / 実装メモ
```

`index.ts` の `owner` には担当者が設定されています。
`id`、`name`、`owner`、`difficulty` はあらかじめ決められた値です。
変更すると契約テストと CI が失敗するため、そのまま使用してください。

### C-2　Draft PRを作り、提出経路を確認する

次のプロンプトでは、変更内容の確認とコミットを依頼します。

```text
コミットの前に git status --short を実行し、変更されたファイルの一覧をそのまま表示してください。

そのうえで、git add の対象は src/games/<ゲームID> だけにして、
次のメッセージでコミットしてください。

  chore(<ゲームID>): 雛形を追加する

src/games/<ゲームID> の外にあるファイルは、1つも add しないでください。
```

最後のプロンプトでは、push と Draft の Pull Request 作成を依頼します。実行前に承認画面が表示されます。

```text
push して、Draft の Pull Request を作ってください。

- push: git push -u origin HEAD
- PR: gh pr create --draft --title "<ゲームID> を実装する" --body "雛形を置いただけの Draft です。実装はこれから進めます。Closes #<Issue番号>"

作成した Pull Request の番号を最後に教えてください。
gh pr ready は実行しないでください。Draft のままにします。
```

**Claude Code が実行する処理**

| コマンド                                                             | 承認                                               |
| -------------------------------------------------------------------- | -------------------------------------------------- |
| `git switch` / `git pull` / `npm run scaffold` / `npm test`          | 承認不要                                           |
| `git status --short` / `git add src/games/<ゲームID>` / `git commit` | 承認不要（コミット時に pre-commit が実行されます） |
| `git push -u origin HEAD`                                            | **実行前に承認が必要**                             |
| `gh pr create --draft ...`                                           | **実行前に承認が必要**                             |

**ターミナルBで確認すること**

1. ブラウザ（`http://localhost:5173/`）を `F5` で再読み込みします。担当ゲームが一覧に「準備中（coming soon）」と表示されることを確認します。
2. ターミナルAを `/exit`、`claude` の順に操作して起動し直し、画面下のステータスラインを確認します。

   ```text
   担当1 ババ抜き ⋅ feature/babanuki ⋅ 変更なし
   ```

   担当名、ゲーム名、ブランチ名が表示されれば、担当の設定が反映されています。
   `担当未設定` のままの場合は、最初のプロンプトの手順3から再実行してください。

3. CI が完了するまで状態を確認します。

```powershell
gh pr checks <自分のPR番号> --watch
gh pr view <自分のPR番号>
```

`verify` が成功したら、PR 番号を手順書の先頭にあるメモ欄へ記入します。

**完了条件**

- [ ] ステータスラインに担当名とゲーム名が表示されている
- [ ] `src/games/<ゲームID>/` に5つのファイルがある
- [ ] ブラウザの一覧に担当ゲームが「準備中」と表示されている
- [ ] `git push` が成功した（403エラーの場合は、招待の承諾状況を講師に確認する）
- [ ] push と PR 作成を承認する前に、画面に表示されたコマンドを確認した
- [ ] Draft の Pull Request が作成されている
- [ ] `gh pr checks` で `verify` が成功した
- [ ] PR 番号をメモした
- [ ] コミットに `src/games/<ゲームID>` の外のファイルが含まれていない

> CI が失敗した場合は、原因を解消してから実装へ進みます。
> 担当フォルダの外にあるファイルを `git add` したことが原因であれば、次のプロンプトを入力します。
>
> ```text
> npm run scope を実行して、範囲外の変更があるか確認してください。
> 範囲外があれば、scope の出力に示された git restore のコマンドをそのまま実行して戻してください。
> src/games/<ゲームID> の中身は消さないでください。
> ```

### C-3　実装計画を必須要件と照合する

実装を依頼する前に計画を作成し、Issue の必須要件と一致しているか確認します。

**入力するプロンプト**

最初のプロンプトでは、実装計画の作成だけを依頼します。この段階ではコードを変更しません。

```text
GitHub の Issue #<Issue番号> と docs/games/<ゲームID>.md を読んで、
src/games/<ゲームID>/ にこのゲームをどう実装するか計画を立ててください。

- Issue にも docs/games/<ゲームID>.md にも書かれていないルールは足さないでください。
- まだコードは書かないでください。ファイルも変更しないでください。
```

表示された計画を、Issue の必須要件と上から順に照合します。対応する項目が計画に見当たらない場合は、次のプロンプトを入力します。

```text
必須要件の「<Issue の要件の文言をそのまま貼る>」に対応する項目が計画にありません。
どの項目で実現するか分かるように、計画へ追記してください。まだ実装はしないでください。
```

計画に、Issue やルール文書に記載されていない機能が含まれている場合は、次のプロンプトを入力します。

```text
計画の「<計画の中の1行をそのまま貼る>」は、Issue にも docs/games/<ゲームID>.md にも書かれていないルールです。
実装対象ではないため、計画から外してください。まだ実装はしないでください。
```

### C-4　実装し、試遊しながら修正する

計画が Issue とルール文書に一致していれば、次のプロンプトで実装を依頼します。細かな調整よりも、最初から最後まで遊べる状態にすることを優先し、発展課題には手を付けません。

```text
その計画で実装してください。まず最後まで遊べる状態にすることを優先し、発展課題には手を付けないでください。
```

担当フォルダの外まで変更されていた場合は、次のプロンプトを入力します。

```text
src/games/<ゲームID>/ の外が変更されています。
その変更を元に戻してから、変更したファイルの一覧をもう一度報告してください。
```

**ターミナルBで行うこと**

1. テストを1回実行します。

   ```powershell
   npm test
   ```

   `npm run dev` を実行している画面とは別のターミナルBを使用します。

2. ブラウザを `F5` キーで再読み込みし、最初から最後まで1回遊びます。

途中で操作できなくなる、画面が真っ白になる、決着がつかないなどの不具合があった場合は、続けて原因を確認し、修正します。

3. 実装と確認が終わった必須要件に、GitHub の Issue 画面でチェックを入れます。

**完了条件**

- [ ] 実装計画を読み、Issue の必須要件と照合した
- [ ] ターミナルBで `npm test` を1回実行し、成功した
- [ ] ブラウザに担当ゲームが表示され、操作できる
- [ ] `git status` の変更が `src/games/<ゲームID>/` の中だけに収まっている

#### 試遊と不具合修正を繰り返す

ゲームを操作し、不具合があれば状況を記録して修正を依頼します。
修正後に同じ操作を行い、問題が解消したか確認します。この一連の作業を繰り返すため、Step Cの中ではC-4に長めの時間を取ります。

#### ターミナルBで行うこと

ブラウザを `F5` キーで再読み込みし、次の点を確認しながらゲームを操作します。

1. 最初から最後まで、途中で止めずに1回遊ぶ
2. 無効になるべき操作を試す（CPU の手番中に連打する、出せないカードを出す、山札が0枚のときに引く）
3. リセット後、2回目のゲームが正しい初期状態で始まるか確認する

神経衰弱などの1人用ゲームでは、CPU やほかのプレイヤーに関する項目を省き、そのゲームで無効になる操作を確認します。

#### 不具合が見つかった場合（ターミナルA）

Claude Code で `/plan` を実行してプランモードに切り替えたあと、次のプロンプトを入力します。

```text
ブラウザでゲームを操作すると、<起きたこと> が発生しました。期待する動作は <期待していたこと> です。

原因を特定して改善策を計画してください。
まだファイルは変更しないでください。
```

提示された計画が報告した不具合に対応していることを確認してから、計画に沿った修正を依頼します。
修正後はブラウザを再読み込みし、同じ操作で不具合が再現しないことを確認します。

#### 残りの必須要件を実装する

最後まで遊べるようになったら、未実装の必須要件を確認します。

```text
Issue #<Issue番号> の必須要件から、未実装の項目を一覧にしてください。
一覧を作成したあと、上から順に実装してください。

実装後に npm test を実行し、結果を報告してください。
```

必須要件をすべて満たしたら、アーケードの一覧からゲームを開始できるようにします。

```text
src/games/<ゲームID>/index.ts の status を "ready" にしてください。
ほかの項目（id / name / owner / difficulty）は変更しないでください。
変更後に npm test を実行し、結果を報告してください。
```

**完了条件**

- [ ] ブラウザで最初から最後まで1回遊んだ
- [ ] 無効になるべき操作を試し、状態が不正に変わらないことを確認した
- [ ] 見つけた不具合の修正を依頼し、解消したことをブラウザで確認した
- [ ] `npm test` が成功する
- [ ] Issue の必須要件をすべて満たしている

### C-5　verifyを実行し、Pull Requestを提出する

`npm run verify` を実行し、Pull Request の本文を完成させます。
検証が成功したことを確認してから Draft 状態を解除します。

**入力するプロンプト**

```text
Pull Request を提出します。次を順に実行してください。

1. npm run verify
2. git add src/games/<ゲームID>
3. git commit -m "feat(<ゲームID>): ゲームを実装する"
4. git push
5. .github/PULL_REQUEST_TEMPLATE.md の形式で、Pull Request の本文を .pr-body.md に書く
6. gh pr edit <自分のPR番号> --body-file .pr-body.md

npm run verify が失敗したら、そこで止めて最初のエラーだけを報告してください。
本文は git diff origin/main...HEAD を確認し、実際の変更内容にもとづいて書いてください。
満たせていない必須要件があれば、「発展課題・未対応事項」に明記してください。

gh pr ready は実行しないでください。ターミナルBで実行します。
```

**Claude Code が実行する処理**

| コマンド                                                       | 承認                   |
| -------------------------------------------------------------- | ---------------------- |
| `npm run verify`（範囲チェック → lint → 型 → テスト → ビルド） | 承認不要               |
| `git diff` / `.pr-body.md` の作成                              | 承認不要               |
| `git add` / `git commit`                                       | 承認不要               |
| `git push`                                                     | **実行前に承認が必要** |
| `gh pr edit <自分のPR番号> --body-file .pr-body.md`            | **実行前に承認が必要** |

**ターミナルBで行うこと**

Draft 状態を解除し、CI の結果を確認します。

```powershell
gh pr ready <自分のPR番号>
gh pr checks <自分のPR番号> --watch
```

**完了条件**

- [ ] `npm run verify` が成功した
- [ ] `gh pr ready` を実行し、Pull Request の Draft を解除した
- [ ] CI の `verify` が成功した
- [ ] 講師に PR 番号を伝えた

## Step D｜統合と公開を確認する

**マージは講師が行います。** 参加者はマージしません。
9件の Pull Request を順に `main` へマージします。マージのたびに、GitHub Pages へのデプロイが自動で実行されます。

マージを待つ間に、ターミナルBで Pull Request の CI を確認します。

```powershell
gh pr checks <自分のPR番号>
```

`verify` が失敗している Pull Request はマージできません。失敗している場合は、原因を確認して修正します。

**入力するプロンプト**

Pull Request がマージされたあと、次のプロンプトを入力します。

```text
私の Pull Request はマージされました。次の3つを順に実行してください。

1. git switch main
2. git pull
3. git log --oneline -5

実行後、私のゲーム（src/games/<ゲームID>）のファイルが main に反映されていることを確認し、結果を1行で報告してください。
新しいブランチは作らないでください。ファイルも変更しないでください。
```

**ターミナルBで行うこと**

講師が投影する GitHub Pages の公開 URL を開きます。
担当ゲームが「準備中」ではなく、開始できる状態になっていることを確認します。
`main` に切り替えたあとは、手元のブラウザ（`http://localhost:5173/`）も `F5` で再読み込みします。

確認が終わったら、ターミナルBの `npm run dev` を `Ctrl + C` で停止します。

**完了条件**

- [ ] 担当の Pull Request がマージされた
- [ ] `git switch main`、`git pull` の順に実行し、担当ゲームが `main` に反映されていることを確認した
- [ ] 公開 URL で、担当ゲームを開始できることを確認した
- [ ] ターミナルBの `npm run dev` を `Ctrl + C` で停止した
