# ハンズオン手順

「Claude Code × GitHub 共同開発ハンズオン — みんなでつくる CARD ARCADE」で使用する手順書です。
**上から順に進めてください。** 迷ったときは、まず現在の Step にある「完了条件」を確認しましょう。

- **参加者9名が、1人1ゲームずつ担当します。** チームには分かれません。調査から実装、テスト、PR、レビューまで、各自で一通り行います。
- 前半（事前課題 P-1 〜 P-6）は**前日までに**各自で終わらせます。
- 後半（Step 1 〜 Step 18）が当日の進行です。各 Step には、開始時刻、入力するプロンプト、完了条件を記載しています。
- 当日の作業は、主に **Claude Code へプロンプトを入力して進めます。**
  掲載しているプロンプトは、**そのままコピーして使える形式**になっています。
- 一部の作業は、Claude Code を使わずに参加者自身が行います。どちらで作業するか迷わないよう、次の「ターミナル2本体制」を採用します。

## この手順書の読み方

プロンプトやコマンドに含まれる `< >` は、自分の値に置き換えてください。**変更するのはこの部分だけです。**

| 書き方 | 意味 | 例 |
|---|---|---|
| `<ゲームID>` | 自分が担当するゲームのゲームID（ローマ字） | `babanuki` |
| `<Issue番号>` | 自分のゲームの Issue 番号 | `1` |
| `<自分のPR番号>` | 自分が作った Pull Request の番号 | `13` |
| `<相手のゲームID>` | 自分がレビューする相手のゲームID | `daifugo` |
| `<相手のPR番号>` | 自分がレビューする相手の Pull Request の番号 | `15` |

Step 1 〜 Step 18 は、**すべて次の4項目**で構成されています。

| 区画 | 中身 |
|---|---|
| **入力するプロンプト** | ターミナルA（Claude Code）に貼り付ける文面。全文をそのまま使ってください |
| **Claude Code がやること** | プロンプトによって実行されるコマンドの一覧。何が実行されるかを確認するための欄なので、**参加者が入力する必要はありません** |
| **ターミナルB でやること** | 参加者自身が入力するコマンドと、画面を見ながら行う作業。作業がない Step にも見出しを設けています |
| **完了条件** | すべて満たしたら次の Step に進みます |

プロンプトを自分の言葉に書き換えても構いませんが、**次の3つは消さないでください。**

1. **対象範囲を限定する言葉**（「`logic.ts` と `logic.test.ts` だけ」「他のファイルは触らないで」）
2. **止める言葉**（「まだ直さないで」「投稿はしないで」「要約しないで」）
3. **実行させない言葉**（「`npm run dev` は実行しないで」「`gh issue create` は実行しないで」）

この3つによって、Claude Code に任せる範囲と、自分で判断する範囲を明確にします。

## ターミナル2本体制（最初に必ず確認してください）

**当日は PowerShell を2つ開きます。** 片方でのみ Claude Code を起動し、もう片方では**起動しないでください。**

| | ターミナルA（Claude Code を使用） | ターミナルB（参加者が直接操作） |
|---|---|---|
| 常に動かしておくもの | Claude Code のセッション | **`npm run dev`（研修中は起動したままにします）** |
| ここで行うこと | 調査 / 計画 / 実装 / 差分の確認 / 文章の下書き | 実際に遊ぶ / `npm test` の手動確認 / `gh pr ready` / Approve / `gh pr checkout` / テストの有効性を確かめる作業 |
| ここでは行わないこと | `npm run dev`（**仕組み上、起動できません**）／PR・Issue への投稿 | Claude Code の起動 |

### なぜ2本に分けるのか

今回の手順書では、以前の版よりもプロンプトで進められる作業が増えています。
その分、どこまでを Claude Code に任せ、どこからを自分で判断するのかが曖昧になりがちです。
そこでこの研修では、**参加者自身が行う作業を、別のターミナルに明確に分けています。**

- 実際にゲームを操作し、不具合がないか判断するのは**参加者自身です。**
  Claude Code はブラウザ上でゲームを操作できません。
- 「投稿してよいのは、自分が実機で確認したことだけ」という原則を守るため、
  実際に確認した参加者自身が投稿します。
- 役割分担を確実に守れるよう、**作業内容をターミナルごとに分けます。**
  ターミナルB で行う作業の一部は、ターミナルA では仕組み上実行できません。

**「AI に任せる作業」と「自分で確かめる作業」の境界を、2つの画面で明確にします。**

### A と B の見分け方（画面を追加した場合）

ターミナルB では `npm run dev` を起動したままにします。別のコマンドを入力したい場合は、**PowerShell を追加で開いて構いません。**

> **追加で開いた画面は、すべて「B」として扱います。**
> A と B の違いは画面の数ではなく、**Claude Code を起動しているかどうか**です。
> Claude Code を起動する画面は、当日を通して**1つだけ**にしてください。

Windows Terminal を使っている場合は、タブを追加すると便利です（`Ctrl + Shift + T`）。

### ターミナルA では実行できない操作

次のコマンドを実行しようとすると、ハーネスによって拒否されます。

| 打っても実行されないコマンド | 理由 |
|---|---|
| `npm run dev` / `npm run preview` | プロセスが終了せず、セッションを占有する。また、ターミナルB で使用するポート 5173 と競合する |
| `npm run test:watch` / `npm test -- --watch` / `npx vitest`（`run` なし） | 監視状態のまま終了しない |
| `gh pr review` / `gh pr comment` / `gh issue comment` | 他の参加者の PR・Issue に直接投稿し、外部へ影響する |
| `gh api` | 上記の制限を迂回できるため（作業ブランチにいる場合のみ） |
| `node scripts/setup-github.mjs` / `node scripts/build-issue-bodies.mjs` | 講師専用で、参加者全員の設定に影響するため（作業ブランチにいる場合のみ） |
| `npm run scaffold -- --all` / `--force` | 同上 |
| `gh issue edit` | Issue 本文は講師が管理（作業ブランチのときだけ） |

拒否されるとき、Claude Code の画面にはこう出ます（`npm run dev` の場合）。

```text
npm run dev は Claude Code からは実行できません。
起動したままになるので、このセッションが返ってこなくなります。

開発サーバーは「あなたが、別のターミナルで」動かします。研修中はつけっぱなしです。

  1. PowerShell をもう1つ開く（これを「ターミナルB」と呼びます）
  2. cd してリポジトリのフォルダへ移動する
  3. npm run dev
  4. ブラウザで http://localhost:5173/ を開く
```

拒否された場合は、迂回せずにターミナルBへ切り替えて実行してください。

### 実行時に承認が必要なコマンド

`git push` / `gh pr create` / `gh pr merge` / `gh pr ready` / `gh pr edit` / `gh issue create`

承認する前に確認すべき3点を、Step 6 に記載しています。

### 確認なしで通るもの

`npm test` / `npm run verify` / `npm run build` / `npm run scaffold -- --game <ゲームID>` /
`git switch` / `git add` / `git commit` / `git status` / `git diff` / `git pull` /
`gh pr checkout` / `gh pr view` / `gh pr checks` / `gh pr diff` / `node -v` / `gh auth status`

### `owner.json` — レビュー中も自分の担当を識別する仕組み

`npm run scaffold -- --game <ゲームID>` を実行すると、`.claude/.state/owner.json` に
**自分のゲームIDが記録されます。**

この記録により、Step 13 で `gh pr checkout <相手のPR番号>` を実行し、**相手のブランチに切り替えている間も**、
Claude Code は自分の担当を正しく識別できます。
その状態で相手のコードを編集しようとすると、**拒否されます。**

```text
src/games/<相手のゲームID>/logic.ts は 担当N（ゲーム名）の担当です。

あなたの担当は <ゲームID> です。
いま相手のブランチを取ってきている（レビュー中）だけなので、
相手のコードは変更できません。
```

**レビューで気づいたことは、直すのではなくコメントで伝えます。**

## 自分で確認するための6つの仕組み

Claude Code を使う場面が増えても確認がおろそかにならないよう、**参加者自身が判断する場面を6か所に定めています。**

| # | 仕組み | 該当する Step | 内容 |
|---|---|---|---|
| 1 | **ターミナル2本体制** | 全 Step | 自分で行う作業を、専用のターミナルに分ける |
| 2 | **`/handoff` の誤りを1行探す** | Step 9・Step 12 の直前 | 出力された10行から**実際の状態と異なる行を1つ**探す。自分で状況を把握できているか確認する |
| 3 | **遊ぶ前に確認する操作を3つ書く** | Step 10（自分）・Step 13（相手） | あらかじめ観点を決めてから操作し、不具合を見つけやすくする |
| 4 | **テストの有効性を自分で確かめる** | Step 11 | 5分間、B とエディタだけを使う。**A には何も入力しない** |
| 5 | **レビュアーが提出内容を確認する** | Step 13 | 相手の PR の「レビューしてほしい点」が具体的かを確認し、テンプレートのままなら指摘する |
| 6 | **講師の口頭1問** | Step 9 | 「`logic.ts` の関数を3つ挙げて、それぞれ何を判断しているか言って」 |

**時間が足りなくなっても、この6項目は省略しません。** 必要に応じてゲームの実装範囲を調整してください。

## 1人で1ゲームを作るということ

今回はチームに分かれず、各自がすべての工程を担当します。
自分のペースで進められる反面、行き詰まっても周囲が気づきにくいため、次の3つの方法で進捗を共有します。

| 仕掛け | いつ | 中身 |
|---|---|---|
| **中間確認** | Step 9（70〜75分） | 講師が `npm run status` で進捗を確認し、必要に応じて個別に声をかけます |
| **`/stuck` を早めに使う** | 行き詰まったとき | 一人で抱え込まず、講師に相談するために使います |
| **Issue のチェックリスト** | 常時 | **これが唯一の進捗指標です。** チェック済みの項目数で、現在の進み具合を確認します |

**15分ルール**: 同じエラーで15分進まなかったら、その場で `/stuck` を入力するか、手を挙げてください。
一人で悩み続けて時間を費やさないようにしましょう。**相談も手順の一部です。**

**プロンプトで進むようになったぶん、「進んでいるように見えて何も分かっていない」状態が作りやすくなりました。**
上記の6つの仕組みは、作業内容を理解しないまま先へ進んでいないかを確かめるためのものです。
仕組み2（`/handoff` の誤り探し）や仕組み6（講師からの口頭質問）で答えに迷った場合は、一度手を止めて内容を確認してください。

## 事前課題（前日までに）

目的は、**当日に環境構築で時間を取られないようにすること**です。
P-6 まで終わって `npm run doctor` がすべて ✓ になっていれば準備完了です。
途中で行き詰まった場合は、その時点の画面を講師に送り、当日までに解決してください。

作業フォルダはどこでも構いませんが、**日本語やスペースを含まないパス**にしてください（例: `C:/work`）。

**P-1 〜 P-3 は自分で操作して進めます。**
**P-4 からはプロンプトを使います。** 当日と同じ進め方を一度練習しておくことも、事前課題の目的です。

### P-1 必要なツールをインストールする（自分で操作）

Node.js 22 以上、Git、GitHub CLI の3つをインストールします。

| ツール | 入手先 | 備考 |
|---|---|---|
| Node.js 22.x | https://nodejs.org/ | LTS の 22 系。20 以下では動きません |
| Git for Windows | https://git-scm.com/download/win | |
| GitHub CLI (`gh`) | https://cli.github.com/ | |

インストール後、**PowerShell を開き直してから**確認します。

```powershell

```

**完了条件**

- `git --version` と `gh --version` がバージョンを返す（`コマンドが見つかりません` にならない）

### P-2 GitHub の招待を承諾し、gh にログインする（自分で操作）

講師から届く**招待メール**（リポジトリ `Daisuke0719/card_arcade` へのコラボレーター招待）を承諾します。
承諾していないと、当日の push が 403 で失敗します。

```powershell
gh auth login
```

画面の案内に従って、次の項目を選びます。

1. `GitHub.com`
2. `HTTPS`
3. `Login with a web browser`（ブラウザが開くのでコードを貼り付ける）

終わったら確認します。

```powershell
gh auth status
gh repo view Daisuke0719/card_arcade --json name
```

**完了条件**
- `gh auth status` に `Logged in to github.com` と出る
- `Token scopes` に `repo` が含まれている
- `gh repo view` がエラーにならずリポジトリ名を返す（403 が出たら招待が未承諾です）

> ラベル・マイルストーン・9件の Issue は、講師が `node scripts/setup-github.mjs all` で先に作ってあります。
> **参加者がセットアップのスクリプトを実行する必要はありません。**
> （Claude Code に頼んでも、講師専用のコマンドとして拒否されます）
> 自分の Issue 番号は担当表のとおりです。手元で一覧したいときは `gh issue list --label game` を使います。

```text
A: /implement Step3 を入力する
        ↓
B: テストの有効性を確かめる（この5分間、Aには何も入力しない）
        ↓
A: 変更が元に戻っているか、1回だけ確認する
```

**入力するプロンプト**

1つ目 — 残りの必須要件と異常系テストを実装させます。

```text
/implement Step3（残りの必須要件と異常系テスト。index.ts の status を "ready" にしてください）
```

**必ず入れる異常系テスト（例）**

- 判定中・CPU の手番中にクリックしても状態が変わらない（連打で先に進めない）
- 出せないカードを出そうとしたら弾かれる
- 最後の1枚 / 0枚のときの境界
- 同じ seed なら同じ展開になる（テストが不安定にならない）

**ここで、いったんターミナルAの操作を止めます。**
次の「ターミナルBでやること」を先に実施してください。**その5分間はAに何も入力しません。**

2つ目 — 確認作業が終わったあとに、**1回だけ**入力します。

```text
logic.test.ts を1行だけ変更したあと、元に戻しました。
git diff で本当に元に戻っているか確認してください。
差分が残っていたら、どの行かだけを教えてください。直さないでください。
```

> **このプロンプトは、直前の確認作業を実施してから入力してください。**
> 実施していなければ、「1行だけ書き換えて元に戻した」という前提が成り立ちません。
>
> `Ctrl + Z` を押しすぎて**戻しすぎている**ことがあります（テストが1件消えている、など）。
> このプロンプトは、それを見つけるためにもあります。差分が残っていたら、**自分のエディタで**直してください。

期待値を書き換えてもテストが失敗しなかった場合に限り、続けて次を入力します。

```text
logic.test.ts の「<テスト名>」は、期待値を逆に書き換えても落ちませんでした。
このテストが何を確認しているのかを説明したうえで、落ちるように書き直してください。
実装（logic.ts）は変えないでください。
```

**Claude Code がやること**

| 実行されること | 何のため |
|---|---|
| 残りの必須要件と異常系テストの実装 → `npm test` | Step3 の実装 |
| `index.ts` の `status` を `"ready"` に変更 | アーケードの一覧で遊べる状態にする |
| 確認作業の直後に `git diff` | 書き換えが元に戻っているか確認する。**Claude Code は修正しない** |

**この5分間は、Claude Code を使いません。** 自分でテストの有効性を確認します。

**ターミナルB でやること**

#### テストが正しく機能することを確かめる

**ここから5分間、ターミナルAには何も入力しません。**

**テストが本当に仕様を検証しているか、自分で確認します。**
意図的に誤った期待値を設定し、テストが失敗することを確かめます。

Claude Code に正しさを尋ねるだけでは、この確認の代わりになりません。
必ず自分でテストを変更し、実行結果を確認してください。

1. エディタで `src/games/<ゲームID>/logic.test.ts` を開く
2. 必須要件に対応するテストを**1つ**選ぶ
3. その `expect(...)` の**期待値をわざと間違った値に書き換える**
   （例: `expect(next.phase).toBe("finished")` を `toBe("playing")` にする）
4. テストを実行する

```powershell
npm test
```

5. **そのテストが失敗することを確認する**
6. **エディタの取り消し（`Ctrl + Z`）で、書き換えを元に戻す**
   （`git restore` は使わないでください。まだコミットしていないテストごと消えます）
7. もう一度実行し、成功することを確認する

```powershell
npm test
```

> **期待値を変えても失敗しない場合、そのテストは意図した内容を検証できていません。**
> （よくある原因: 実装の結果をそのまま `expect` に渡している / 条件が常に真になっている）
> 確認作業が終わったら、ターミナルAで「入力するプロンプト」の最後の文面を入力してください。

この確認は、Pull Request の本文にもチェック項目として記載されています。
**テストの有効性を自分で確認するための重要な工程です。** 省略しないでください。

**完了条件**

- [ ] Issue の必須要件チェックリストが**すべて**更新されている（満たせなかった項目は「未達」と記録する）
- [ ] 異常系・境界値のテストが入っている
- [ ] **テストの有効性を、ターミナルBとエディタだけで検証した（Aには何も入力していない）**
- [ ] **期待値を変更したときにテストが失敗することを確認した**
- [ ] 確認作業のあと `git diff` を実行し、書き換えが残っていないことを確かめた
- [ ] `src/games/<ゲームID>/index.ts` の `status` が `"ready"` になっている
- [ ] `npm test` が成功した

### Step 12｜`/verify` → `/pr` → `gh pr ready`（105〜115分）

> **ターミナルBで `npm run dev` は実行中ですか？** — スクリーンショットを撮影するため、起動したままにしてください。

提出前の総合チェックを行い、Pull Request の本文を仕上げて Draft 状態を解除します。
**`npm run verify` が成功してから、完了と判断してください。** このコマンドでは、CIと同じ検証が行われます。

**この Step の最初に、もう一度 `/handoff` を入力します。**
Step 9 と同様に、**出力された10行から、実際の状態と異なる行を1つ探してください。**
特に、未完了の作業が「できている」と記載されていないか確認します。
誤りを残したまま PR を提出しないよう、ここで修正してください。

**入力するプロンプト**

1つ目 — 現在の状態が正しく記載されているか、自分で照合します。

```text
/handoff
```

（出力された10行から実際の状態と異なる行を1つ探し、その行だけを修正させてください）

2つ目 — Issue と実装を照合します。

```text
/verify <Issue番号>
```

必須要件と実装・テストの対応表が表示されます。満たしていない要件は、**未達として記録してください。**

3つ目 — Pull Request の本文を下書きします。

```text
/pr
```

`.pr-body.md` ができます。**`gh pr create` は実行されません。**
`/pr` は「レビューしてほしい点」を**空欄のまま残します。** この欄は参加者自身が記入します。

4つ目 — 自分で「レビューしてほしい点」を書き終えてから入力します。

```text
.pr-body.md の「レビューしてほしい点」を記入しました。次を順に実行してください。

1. npm run verify
2. git add src/games/<ゲームID>
3. git commit -m "feat(<ゲームID>): ゲームを実装する"
4. git push
5. gh pr edit <自分のPR番号> --body-file .pr-body.md

.pr-body.md の中身は書き換えないでください。
gh pr ready は実行しないでください。私が自分で入力します。
```

**Claude Code がやること**

| 実行されるコマンド | 承認 |
|---|---|
| `npm run verify`（範囲チェック → lint → 型 → テスト → ビルド） | 確認なしで通る |
| `gh issue view <Issue番号>` | 確認なしで通る |
| `.pr-body.md` の作成（`gh pr create` は実行しない） | 確認なしで通る |
| `git add` / `git commit` | 確認なしで通る |
| `git push` | **実行前に承認が必要** |
| `gh pr edit <自分のPR番号> --body-file .pr-body.md` | **実行前に承認が必要** |

**ターミナルB でやること**

1. **`.pr-body.md` の「レビューしてほしい点」を自分の言葉で書く**（ここは AI に任せません）

```powershell
code .pr-body.md
```

「勝敗判定を見てください」のような広い依頼ではなく、
「同じ数字が出たときの引き分け処理に自信がないため、重点的に確認してください」のように具体的に書きます。

レビュアーにどこを重点的に見てもらいたいか、自分で決めて書いてください。
**テンプレートのまま提出すると、Step 13 でその点を指摘されます**（仕組み5）。
迷った場合は、Step 11 の確認作業で最も自信がなかったテストについて書いてください。

2. **ゲーム画面のスクリーンショットを撮る**（`Win + Shift + S`）

3. **Draft 状態を解除し、CI を確認する**

```powershell
gh pr ready <自分のPR番号>
gh pr checks <自分のPR番号> --watch
```

`gh pr ready` は**自分で入力します。** レビューを依頼できる状態かどうかを、自分で最終判断するためです。

4. GitHub の画面で Pull Request を開き、**スクリーンショットを本文にドラッグ&ドロップ**する
   （画像ファイルはリポジトリにコミットしないでください）

5. **自分をレビューする人**（担当表のいちばん右）に「PR 出しました」と直接伝え、**PR 番号を渡す**

**完了条件**

- [ ] `/handoff` を実行し、実際の状態と異なる行を1つ見つけて修正を依頼した
- [ ] `npm run verify` が成功した
- [ ] Pull Request の Draft が解除されている（**`gh pr ready` を自分で実行した**）
- [ ] CI の `verify` が成功した
- [ ] 本文の「レビューしてほしい点」が**自分の言葉**で書かれている（テンプレートのままでない）
- [ ] スクリーンショットが本文に貼られている
- [ ] 「採用したルール / 今回は実装しない」が書かれている
- [ ] 自分をレビューする人に PR 番号を伝えた

### Step 13｜相互レビュー（115〜140分）

> **ターミナルBで `npm run dev` は実行中ですか？** — 相手のゲームを操作するときに使うため、起動したままにしてください。

レビュー担当は、参加者全員が1件ずつ担当できるように割り当てています。各自が1件をレビューし、自分の PR も1人からレビューを受けます。作業時間は25分です。

| レビューする人 | レビューする Pull Request |
|---|---|
| 担当1（ババ抜き） | 担当2（大富豪 / `daifugo`） |
| 担当2（大富豪） | 担当3（神経衰弱 / `shinkeisuijaku`） |
| 担当3（神経衰弱） | 担当4（ポーカー / `poker`） |
| 担当4（ポーカー） | 担当5（ぶたのしっぽ / `butanoshippo`） |
| 担当5（ぶたのしっぽ） | 担当6（スピード / `speed`） |
| 担当6（スピード） | 担当7（七並べ / `shichinarabe`） |
| 担当7（七並べ） | 担当8（ダウト / `doubt`） |
| 担当8（ダウト） | 担当9（ページワン / `pageone`） |
| 担当9（ページワン） | 担当1（ババ抜き / `babanuki`） |

**この組み合わせは、作業量のバランスを考慮して決めています。**

- **上級を担当した人（担当2 大富豪 / 担当4 ポーカー）は、初級のゲームをレビューします。**
  実装量が多いことを考慮し、レビューの負担を軽くしています。
- **逆に、上級の PR をレビューするのは初級を作った人**（担当1 → 大富豪、担当3 → ポーカー）です。
  初級は比較的早く実装を終えやすいため、作業量の多いレビューを割り当てています。
- 「実装量が多い人には比較的軽いレビューを、実装量が少ない人には比較的重いレビューを割り当てる」という考え方です。

チーム開発とは異なり、今回はコードを継続的に確認するチームメンバーがいません。
割り当てられたレビュアーが、実装を確認する唯一の参加者です。
**差分を見るだけで終えず、必ず実際にゲームを操作して確認してください。**

**この Step は A と B を4回往復します。順番を守ってください。**

```text
① A  相手のゲームで確認する項目を原文のまま表示する
② B  gh pr checkout して、実際に遊ぶ（中心となる作業）
③ A  /review で差分を読む
④ A  投稿文の下書きを作成する（投稿はしない）
⑤ B  GitHub の画面から投稿し、相手の「レビューしてほしい点」を確認する
⑥ B  自分のブランチに戻る
```

**入力するプロンプト**

① — 相手のゲームで確認すべき箇所を、原文のまま表示させます（**遊ぶ前に入力します**）。

```text
docs/games/<相手のゲームID>.md を開いて、「レビュアー向けミッション」の見出しの中にある
ミッション1・ミッション2・ミッション3 の本文を、そのまま引用して表示してください。

解釈も補足も要約も足さないでください。原文のまま出してください。
```

引用した内容を、相手のゲームを試す際の3つの確認観点として使います。
相手のゲームに詳しくなくても確認できるよう、ルール文書に観点が示されています。

ルールに詳しくなくても、記載された手順に沿って操作すれば、期待どおりに動くか確認できます。
引用された3つを、**紙かメモ帳に書き写してから**②へ進んでください。その後の確認で使用します。

③ — **②で実際に遊んだあとに**、Claude Code を使って差分を確認します。

```text
/review <相手のPR番号>
```

> `/review` の手順書には `npm run dev` が入っていますが、**Claude Code は実行できません**（拒否されます）。
> ②ですでに操作を確認しているため、そのまま次へ進みます。
> `npm ci` を実行しようとしたら `Esc` で止めてください（理由は②に書いてあります）。

`/review` はコメントを投稿しません。**投稿するかどうかは参加者自身が決めます。**

④ — 投稿文の下書きを作成させます。**投稿は実行させません。**

```text
私が実機で確認できたのは次の3つです。

1. <自分が画面で見たこと>
2. <自分が画面で見たこと>
3. <自分が画面で見たこと>

これ以外の指摘には「未確認」と明記した形にして、投稿用の文章を出してください。
再現手順が書けない指摘は落としてください。

投稿はしないでください。私が GitHub の画面から自分で投稿します。
```

**指摘には、次の3つの観点を含めます**

1. **ルール検証の指摘（再現手順つき）**
   「〇〇を〇回すると〇〇になります。Issue では〇〇のはずです」のように書きます。
   **再現手順が書けない指摘は投稿しません。**
2. **テスト観点の提案（具体的なテスト名で）**
   「`it("同じ数字が続いたとき引き分けになる")` を追加するとよいです」のように書きます。
3. **質問または可読性の提案**（1つは GitHub の suggestion 形式で書けるもの）

**Claude Code がやること**

| 実行されること | 何のため |
|---|---|
| `docs/games/<相手のゲームID>.md` の読み取り | ミッションを原文のまま引用する |
| `gh pr view <相手のPR番号>` / `gh pr diff <相手のPR番号>` | 差分と本文を読む |
| `gh issue view` | 必須要件と突き合わせる |
| `gh pr checkout` | 実行できますが、**②で自分が済ませてあります** |
| `npm ci` | **打たせないでください**（`Esc` で止める。理由は②） |
| `gh pr review` / `gh pr comment` | **拒否されます。** 投稿は参加者自身が行います |

**相手のブランチにいる間に相手のコードを編集しようとしても、拒否されます。**
`npm run scaffold` が記録した `.claude/.state/owner.json` の担当と突き合わせているからです。

```text
src/games/<相手のゲームID>/logic.ts は 担当N（ゲーム名）の担当です。

あなたの担当は <ゲームID> です。
いま相手のブランチを取ってきている（レビュー中）だけなので、
相手のコードは変更できません。
```

**気づいたことは、直すのではなくコメントで伝えてください。**

**ターミナルB でやること**

#### ② 相手のブランチに切り替え、実際に遊ぶ

先に自分の変更をすべてpushし、作業ツリーに未反映の変更がない状態にします。

```powershell
git status --short
```

何か表示されたら、ターミナルA で `git add` → `git commit` → `git push` を済ませてから次へ進みます。

```powershell
gh pr checkout <相手のPR番号>
```

> **`npm ci` は実行しないでください。**
> 理由は2つあります。
>
> 1. **`package-lock.json` は全ブランチで同一**です。依存関係の追加は禁止されているため、インストールし直す必要はありません。
> 2. **ターミナルBで `npm run dev` が動いている状態で `npm ci` を実行すると、Windows では失敗します。**
>    開発サーバーが `node_modules` 内のファイルを使用しているため、ファイル使用中のエラーになります。
>
> ターミナルAの Claude Code が `npm ci` を実行しようとしたら、**`Esc` で停止してください。**

ブラウザを **F5 で再読み込み**すると、一覧が相手のゲームに切り替わっています。

（表示されない場合に限り、ターミナルBの `dev` を `Ctrl + C` で停止し、`npm run dev` をもう一度実行してください）

**ゲームを操作しながら確認すること**

1. 普通に**最後まで1回クリアする**
2. **① で写したミッション1・2・3 を、書いてあるとおりに3つとも実行する**
3. **無効であるべき操作を試す**（判定中に連打する / 出せないカードを出す / 0枚のときに引く）
4. リセット後に、2回目のゲームが正しい初期状態で始まるか確認する

各項目について、実機で確認できたかどうかをその場でメモしてください。④のプロンプトで使用します。

#### ⑤ GitHub の画面から投稿し、PR 本文を確認する

GitHub の「Files changed」で該当行にコメントを付け、Review としてまとめて送信します。
修正が必要なら「Request changes」、問題がなければ「Approve」を選びます。

投稿は GitHub の画面から行うか、ターミナルBで自分でコマンドを入力します。

> ### レビュアーは提出内容の確認役です
>
> コメントを書く前に、**相手の PR 本文の「レビューしてほしい点」を読んでください。**
>
> - **具体的に書いてあるか？**（「どこを重点的に見てほしいか」が分かるか）
> - **テンプレートのコメントが残ったままではないか？**
> - 「勝敗判定を見てください」のように、**対象が広すぎる依頼になっていないか？**
>
> テンプレートのまま、空欄、または具体性がない場合は、**その点も指摘してください。**
> レビュアーが重点的に見るべき箇所を明確にしてもらうための指摘です。
>
> ```text
> 本文の「レビューしてほしい点」がテンプレートのままなので、どこを重点的に見ればよいか分かりませんでした。
> 実装していて一番自信がなかった箇所を1つ挙げてもらえますか。そこを見て、もう一度コメントします。
> ```

### Step 14｜`/fix-review` → 修正 → Approve（140〜152分）

> **ターミナルBで `npm run dev` は実行中ですか？** — 修正内容の確認に使うため、起動したままにしてください。

**入力するプロンプト**

1つ目 — 指摘を集め、対応方針の表を作成させます。

```text

```

指摘の一覧と対応方針が表で表示されます。**この時点ではまだ修正しません。**

| # | 指摘の内容 | 分類 | 対応方針 |
|---|---|---|---|

- **直す**: 指摘が妥当である。修正方法を1行で書く
- **相談**: 修正すべきか判断が分かれる。理由を書いて関係者に相談する
- **直さない**: 仕様どおり、または Issue の範囲外。**理由を丁寧に書く**
  （「直さない」と判断する場合も、理由を明確に説明してください）

2つ目 — **少なくとも1件の分類を、自分で見直します。**

> ### 出力された表をそのまま採用せず、自分で確認してください
>
> **分類を最終的に決めるのは実装者です。** Claude Code の提案だけで決めず、
> Issue の範囲や残り時間も踏まえて判断してください。
>
> 表を上から読み、**少なくとも1件は分類を自分で見直してください。**
> 変える方向はどちらでも構いません（「直さない」→「直す」でも、その逆でも）。
> 変更すべき項目が見つからない場合も、それぞれの分類が妥当かを改めて確認してください。

```text

理由は <自分の言葉で書いた理由> です。

src/games/<ゲームID> の外は触らないでください。
```

3つ目 — 修正後に検証し、コミットします。

```text

1. git add src/games/<ゲームID>
2. git commit -m "fix(<ゲームID>): レビュー指摘に対応する"
3. git push
```

4つ目 — 返信文の下書きを作成します。

```text

ご指摘ありがとうございます。
<どう直したか / なぜ直さないか>

投稿はしないでください。私が GitHub の画面から自分で返信します。
```

| 実行されるコマンド | 承認 |
|---|---|
| `gh pr view <自分のPR番号> --comments` | 確認なしで通る |
| 「直す」に分類した箇所の修正 | 確認なしで通る（担当フォルダの中だけ） |

**ターミナルB でやること**

1. **ブラウザをF5で再読み込みし、修正した箇所を実際に操作する**（テストが成功していても、画面に問題が残っている可能性があります）

2. **各指摘に対して、GitHub 上で返信する。** 修正しただけで終わらせないでください。


返信を確認し、CI が成功していれば承認します。**このコマンドはターミナルBで自分で実行します**（Aでは拒否されます）。

## 困ったときの対処方法

| 困りごと | 実行すること | 使用するターミナル |
|---|---|---|
| 同じエラーで15分進まない | `/stuck <一言>` | ターミナルA |
| 何をやっていたか分からなくなった | `/handoff` | ターミナルA |
| 範囲外のファイルを変更してしまった | `npm run scope` を実行させ、表示された `git restore` をそのまま実行させる | ターミナルA |
| 画面が真っ白 / 変更が反映されない | ブラウザをF5で再読み込み → 改善しなければ `Ctrl + C` で停止し、`npm run dev` を再実行 | ターミナルB |
| `npm run dev` を止めてしまった | `npm run dev` をもう一度実行 | ターミナルB |
| ポート 5173 が使用中と出る | `docs/troubleshooting.md` の T-03 を見る | ターミナルB |
| Claude Code が拒否メッセージを出した | メッセージの「次にやること」に従い、迂回しない | — |
| 拒否の理由が分からない | `docs/harness.md` を読む | — |
| どうしても分からない | **手を挙げる**（15分ルール） | — |

拒否された操作を迂回しようとせず、分からない場合は手を挙げてください。
