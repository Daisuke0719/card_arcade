- **参加者9名が、1人1ゲームずつ担当します。** チームはありません。調査・実装・テスト・PR・レビューを全部自分でやります。

## 1人で1ゲームを作るということ

チーム開発ではないので、操作担当も進行役もいません。**全部自分でやります。**
そのぶん速く進める代わりに、**「詰まっていることに誰も気づけない」**という弱点があります。
今日はこの弱点を、次の3つで埋めます。

| 仕掛け | いつ | 中身 |
|---|---|---|
| **中間チェックポイント** | Step 9（70〜75分） | 講師が `npm run status` を見て、遅れている人に**個別に**声をかけます |
| **`/stuck` を早めに使う** | 詰まった瞬間 | 相談相手は講師だけです。抱え込むと誰も気づきません |
| **Issue のチェックリスト** | 常時 | **これが唯一の進捗指標です。** 埋まった数が、今どこにいるかを表します |

**15分ルール**: 同じエラーで15分進まなかったら、その場で `/stuck` を打つか手を挙げてください。
1人で粘って30分溶かすのが、今日いちばん多い失敗の形です。**相談は遅れではなく手順です。**

### Step 4｜講師デモ「ハーネス一周」（24〜32分）

**やること**

**見るだけです。手を動かさないでください。**
講師が、わざと反則をして5つの層それぞれに止められる様子を実演します。
「怒られたときに、どこで止められたのか」が分かるようになるのがこの8分の目的です。

| 層 | 何が止めるか | 止まり方 |
|---|---|---|
| Layer 1 予防 | `npm run scaffold` | そもそも間違った構造を作れない |
| Layer 2 伝える | `CLAUDE.md` / `src/games/CLAUDE.md` | Claude が最初から規約を知っている |
| Layer 3 その場で止める | `.claude/hooks/` | 範囲外を編集しようとした瞬間に拒否される |
| Layer 4 コミットさせない | ESLint / 契約テスト / pre-commit | **ここだけは迂回できません** |
| Layer 5 マージさせない | CI / CODEOWNERS / ブランチ保護 | Pull Request が赤くなってマージできない |

デモで見るもの:

1. `src/core/` を編集しようとする → Claude Code が拒否する（Layer 3）
2. `npm install some-package` を打つ → 拒否される（Layer 3）
3. 範囲外のファイルを変更してコミットする → pre-commit が止め、`git restore ...` を出す（Layer 4）
4. `git commit --no-verify` で回避しようとする → 拒否される（Layer 4 は迂回不能）
5. 範囲外の変更を含む PR → CI の `verify` が赤くなりマージできない（Layer 5）

### Step 14｜`/fix-review` → 修正 → Approve（140〜152分）

**Claude Code に打つ内容**

```text

```

指摘の一覧と対応方針の表が出ます。**この時点ではまだ直しません。**

| # | 指摘の内容 | 分類 | 対応方針 |
|---|---|---|---|

- **直す**: 指摘が正しい。どう直すかを1行で書く
- **相談**: 直すべきか判断が分かれる。理由を書いて人間に委ねる
- **直さない**: 仕様どおり、または Issue の範囲外。**理由を丁寧に書く**
  （「直さない」を選ぶこと自体は悪いことではありません。理由を説明できるかが大事です）

方針は自分で決めます。迷ったら**レビュアー本人に直接聞く**か、講師に相談してください。
決まったら、修正させます。

```text
方針を決めました。「直す」に分類した3件だけを修正してください。
```

**コマンド（PowerShell）**

修正のたびに回します。

```powershell
npm run verify
git add src/games/<ゲームID>
git commit -m "fix(<ゲームID>): レビュー指摘に対応する"
git push
git log -1 --format=%h
```

**返信する（これを飛ばさない）**

指摘1件ずつに GitHub 上で返信します。**直しただけで終わらせないでください。**
レビュアーは「自分の指摘がどうなったか」が分からないと承認できません。

```text
ご指摘ありがとうございます。
<どう直したか / なぜ直さないか>
コミット: <SHA>
```

**レビュアー側の作業**

返信を確認し、CI が緑なら承認します。

```powershell
gh pr checks <相手のPR番号>
gh pr review <相手のPR番号> --approve --body "実機で確認しました。対応ありがとうございます。"
```

**完了条件**

- [ ] すべての指摘に**分類と理由**を付けて返信した（「直さない」も理由つきで返した）
- [ ] 修正後に `npm run verify` が緑
- [ ] CI の `verify` が緑
- [ ] レビュアーから **Approve** をもらった
- [ ] 自分がレビューした相手にも、Approve か Request changes を返した
