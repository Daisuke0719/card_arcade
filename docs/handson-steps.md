# ハンズオン手順

「Claude Code × GitHub 共同開発ハンズオン — みんなでつくる CARD ARCADE」の当日手順書です。
**上から順になぞれば進みます。** 迷ったら戻らずに、今いる Step の「完了条件」を読んでください。

- **参加者9名が、1人1ゲームずつ担当します。** チームはありません。調査・実装・テスト・PR・レビューを全部自分でやります。
- 前半（事前課題 P-1 〜 P-6）は**前日までに**各自で終わらせます。
- 後半（Step 1 〜 Step 18）が当日の流れです。各 Step に時刻・打つプロンプト・完了条件が書いてあります。
- 今日の作業の大半は、**Claude Code にプロンプトを打って進めます。**
  手順書に載っているプロンプトは、**コピーしてそのまま貼り付けて動く形**で書いています。
- ただし、**プロンプトで進められない場所を意図的に残してあります。** それが次のページの「ターミナル2本体制」です。

## この手順書の読み方

プロンプトとコマンドの中の `< >` は、自分の値に置き換えてください。**置き換えるのはここだけです。**

| 書き方 | 意味 | 例 |
|---|---|---|
| `<ゲームID>` | 自分が担当するゲームのゲームID（ローマ字） | `babanuki` |
| `<Issue番号>` | 自分のゲームの Issue 番号 | `1` |
| `<自分のPR番号>` | 自分が作った Pull Request の番号 | `13` |
| `<相手のゲームID>` | 自分がレビューする相手のゲームID | `daifugo` |
| `<相手のPR番号>` | 自分がレビューする相手の Pull Request の番号 | `15` |

Step 1 〜 Step 18 は、**すべて同じ4区画**で書いてあります。

| 区画 | 中身 |
|---|---|
| **打つプロンプト** | ターミナルA（Claude Code）にコピペする文面。丸ごと貼ってください |
| **Claude Code がやること** | そのプロンプトで実行されるコマンドの一覧。**参加者は打ちません**（何が動くかを知っておくためのものです） |
| **ターミナルB でやること** | 自分の手だけで打つコマンドと、目と手でやること。無い Step にも見出しは置いてあります |
| **完了条件** | ここが埋まれば次へ進めます |

プロンプトを自分の言葉に書き換えても構いませんが、**次の3つは消さないでください。**

1. **範囲を切る言葉**（「`logic.ts` と `logic.test.ts` だけ」「他のファイルは触らないで」）
2. **止める言葉**（「まだ直さないで」「投稿はしないで」「要約しないで」）
3. **実行させない言葉**（「`npm run dev` は実行しないで」「`gh issue create` は実行しないで」）

この3つが、今日の手順書がプロンプト集であって「丸投げ集」ではない理由です。

## ターミナル2本体制（今日いちばん大事な1ページ）

**今日は PowerShell を2本開きます。** 片方には Claude Code を入れ、もう片方には**絶対に入れません。**

| | ターミナルA（Claude Code） | ターミナルB（自分の手だけ） |
|---|---|---|
| 常駐しているもの | Claude Code のセッション | **`npm run dev`（研修中つけっぱなし）** |
| ここでやること | 調査 / 計画 / 実装 / 差分を読む / 文章の下書き | 実機で遊ぶ / `npm test` の自分確認 / `gh pr ready` / Approve / `gh pr checkout` / テストを疑う儀式 |
| ここでやらないこと | `npm run dev`（**そもそも起動できません**）／PR・Issue への投稿 | Claude Code を起動すること |

### なぜ2本に分けるのか

今日の手順書は、去年までの版よりもプロンプトで進める範囲がずっと広くなっています。
つまり**丸投げしようと思えばできてしまう**形に近づいています。
それでもこの研修の目的（AI に丸投げしない）を守るために、**丸投げできない場所を物理的に切り出しました。**

- 「実際に遊んで、壊れているかどうかを判断する」のは**人間にしかできません。**
  Claude Code はブラウザを開けませんし、遊べません。
- 「投稿してよいのは、自分が実機で確認したことだけ」という約束は、
  **確認したかどうかを知っている人間**が投稿することでしか守れません。
- ルールを口で言うと必ず破られます。だから今日は、**ルールではなく「場所」で分けます。**
  ターミナルB でやることは、A では**やろうとしてもできません。**

**「AI に任せた/任せなかった」の境界は、あなたの頭の中ではなく、窓の境界にあります。**

### A と B の見分け方（窓が増えても迷わない）

ターミナルB は `npm run dev` で埋まります。テストを打ちたくなったら、**もう1枚 PowerShell を開いて構いません。**

> **増やした窓は、ぜんぶ「B」です。**
> A と B の違いは窓の枚数ではなく、**Claude Code が入っているかどうか**だけです。
> Claude Code が入っている窓は、今日は**1枚だけ**にしてください。

Windows Terminal を使っている人は、タブを増やすのがいちばん楽です（`Ctrl + Shift + T`）。

### ターミナルA では、これができません（ハーネスが止めます）

**この仕組みはすでに実装されています。** 試すと拒否メッセージが出ます。

| 打っても実行されないコマンド | 理由 |
|---|---|
| `npm run dev` / `npm run preview` | 起動したままになりセッションが返らない。あなたの 5173 とポートが衝突する |
| `npm run test:watch` / `npm test -- --watch` / `npx vitest`（`run` なし） | 終わらない |
| `gh pr review` / `gh pr comment` / `gh issue comment` | 他人の PR・Issue に文字を投稿する = 他の人に波及する側 |
| `gh api` | 上の判定を全部迂回できる裏口（作業ブランチのときだけ） |
| `node scripts/setup-github.mjs` / `node scripts/build-issue-bodies.mjs` | 講師専用。9人分を壊せる（作業ブランチのときだけ） |
| `npm run scaffold -- --all` / `--force` | 同上 |
| `gh issue edit` | Issue 本文は講師が管理（作業ブランチのときだけ） |

拒否されるとき、Claude Code の画面にはこう出ます（`npm run dev` の場合）。

```text
npm run dev は Claude Code からは実行できません。
起動したままになるので、このセッションが返ってこなくなります。

開発サーバーは「あなたが、別のターミナルで」動かします。研修中はつけっぱなしです。

  1. PowerShell をもう1つ開く（これを「ターミナルB」と呼びます）
  2. cd してリポジトリのフォルダへ移動する
  3. npm run dev
  4. ブラウザで http://localhost:5173/ を開く
```

**回り込む方法を探さないでください。** 探す時間より、B に切り替えて打つほうが速いです。

### `owner.json` — レビュー中も担当を見失わない仕組み

`npm run scaffold -- --game <ゲームID>` を実行すると、`.claude/.state/owner.json` に
**自分のゲームIDが記録されます。**

これがあるので、Step 13 で `gh pr checkout <相手のPR番号>` して**ブランチが相手のものになっている間も**、
Claude Code は「あなたの担当」を見失いません。
その状態で相手のコードを編集しようとすると、**拒否されます。**

```text
src/games/<相手のゲームID>/logic.ts は 担当N（ゲーム名）の担当です。

あなたの担当は <ゲームID> です。
いま相手のブランチを取ってきている（レビュー中）だけなので、
相手のコードは変更できません。
```

**レビューで気づいたことは、直すのではなくコメントで伝えます。**

## 人間の確認が消えないようにする6つの機構

プロンプトで進む範囲が広がったぶん、**人間が確かめる場所を6か所に固定してあります。**
どれも「飛ばしても怒られないが、飛ばすと後で自分が困る」形になっています。

| # | 機構 | 出てくる Step | 中身 |
|---|---|---|---|
| 1 | **ターミナル2本体制** | 全 Step | 人間の担当を「ルール」ではなく「場所」にする |
| 2 | **`/handoff` で嘘を1行探す** | Step 9・Step 12 の直前 | 出てきた10行のうち**事実と違う行を1つ**探す。状態を知らなければ判定できない |
| 3 | **遊ぶ前に壊し方を3つ手で書く** | Step 10（自分）・Step 13（相手） | 先に書いてから遊ぶ。書いてから遊ぶと、見つかる不具合の数が変わります |
| 4 | **テストを疑う儀式を A から隔離** | Step 11 | 儀式の5分は B とエディタだけ。**A に1文字も打ちません** |
| 5 | **レビュアーが検問になる** | Step 13 | 相手の PR の「レビューしてほしい点」が具体的かを確かめ、テンプレのままなら指摘する |
| 6 | **講師の口頭1問** | Step 9 | 「`logic.ts` の関数を3つ挙げて、それぞれ何を判断しているか言って」 |

**この6つは、時間が押しても削りません。** 削るのはゲームの中身のほうです。

## 1人で1ゲームを作るということ

チーム開発ではないので、操作担当も進行役もいません。**全部自分でやります。**
そのぶん速く進める代わりに、**「詰まっていることに誰も気づけない」**という弱点があります。
今日はこの弱点を、次の3つで埋めます。

| 仕掛け | いつ | 中身 |
|---|---|---|
| **中間チェックポイント** | Step 9（70〜75分） | 講師が `npm run status` を見て、遅れている人に**個別に**声をかけます |
| **`/stuck` を早めに使う** | 詰まった瞬間 | 相談相手は講師だけです。抱え込むと誰も気づきません |
| **Issue のチェックリスト** | 常時 | **これが唯一の進捗指標です。** 埋まった数が、今どこにいるかを表します |

**15分ルール**: 同じエラーで15分進まなかったら、その場で `/stuck` を打つか手を挙げてください。
1人で粘って30分溶かすのが、今日いちばん多い失敗の形です。**相談は遅れではなく手順です。**

**プロンプトで進むようになったぶん、「進んでいるように見えて何も分かっていない」状態が作りやすくなりました。**
その状態を検出するために置いてあるのが、上の6つの機構です。
機構2（`/handoff` の嘘探し）と機構6（講師の口頭1問）で引っかかったら、それは遅れではなく**発見**です。
そこで一度手を止めるほうが、最終的に速く終わります。

```text
B: テストを疑う儀式（この5分、A には1文字も打たない）
        ↓
A: 元に戻っているかの確認を1回だけ打つ
```

**打つプロンプト**

1本目 — 残りの必須要件と異常系テストを実装させます。

```text
/implement Step3（残りの必須要件と異常系テスト。index.ts の status を "ready" にしてください）
```

**必ず入れる異常系テスト（例）**

- 判定中・CPU の手番中にクリックしても状態が変わらない（連打で先に進めない）
- 出せないカードを出そうとしたら弾かれる
- 最後の1枚 / 0枚のときの境界
- 同じ seed なら同じ展開になる（テストが不安定にならない）

**ここで、いったんターミナルA から手を離します。**
次の「ターミナルB でやること」（テストを疑う儀式）を先に済ませてください。**その5分は A に1文字も打ちません。**

2本目 — 儀式が終わったあとに、**1回だけ**打ちます。

```text
今 logic.test.ts を1行だけ書き換えて、元に戻しました。
git diff で本当に元に戻っているか確認してください。
差分が残っていたら、どの行かだけを教えてください。直さないでください。
```

> **このプロンプトは、儀式をやった人にしか打てません。**
> やっていない人は、そもそも「1行だけ書き換えて元に戻した」という事実がありません。
> 打っても、返ってきた答えの意味が分かりません。
>
> `Ctrl + Z` を押しすぎて**戻しすぎている**ことがあります（テストが1件消えている、など）。
> このプロンプトは、それを見つけるためにもあります。差分が残っていたら、**自分のエディタで**直してください。

儀式で「赤くならなかった」場合だけ、続けてこれを打ちます。

```text
logic.test.ts の「<テスト名>」は、期待値を逆に書き換えても落ちませんでした。
このテストが何を確認しているのかを説明したうえで、落ちるように書き直してください。
実装（logic.ts）は変えないでください。
```

**Claude Code がやること**

| 実行されること | 何のため |
|---|---|
| 残りの必須要件と異常系テストの実装 → `npm test` | Step3 の実装 |
| `index.ts` の `status` を `"ready"` に変更 | アーケードの一覧で遊べる状態にする |
| （儀式の直後）`git diff` | 書き換えが元に戻っているかを確認する。**直しません** |

**儀式の5分の間、Claude Code は何もしません。** それがこの Step の設計です。

**ターミナルB でやること**

#### テストを疑う儀式（この Step の主役）

**ここから5分間、ターミナルA には1文字も打ちません。**

**テストが本当に仕様を確認しているかを、人間の目で1回だけ確かめます。**
テストは「書いてあること」ではなく「落ちること」で価値が決まります。
そして**落ちるかどうかは、実際に落としてみないと分かりません。**

Claude に「このテストは正しいですか」と聞くのは、この儀式の代わりになりません。
**聞いた時点で、確かめたのはあなたではなくなります。**

1. エディタで `src/games/<ゲームID>/logic.test.ts` を開く
2. 必須要件に対応するテストを**1つ**選ぶ
3. その `expect(...)` の**期待値をわざと間違った値に書き換える**
   （例: `expect(next.phase).toBe("finished")` を `toBe("playing")` にする）
4. テストを実行する

```powershell
npm test
```

5. **そのテストが赤くなることを、目で確認する**
6. **エディタの取り消し（`Ctrl + Z`）で、書き換えを元に戻す**
   （`git restore` は使わないでください。まだコミットしていないテストごと消えます）
7. もう一度実行して、緑に戻ることを確認する

```powershell
npm test
```

> **赤くならなかったら、そのテストは何も確認していません。**
> （よくある原因: 実装の結果をそのまま `expect` に渡している / 条件が常に真になっている）
> 儀式が終わってから、ターミナルA で「打つプロンプト」の最後のものを伝えてください。

この儀式は Pull Request の本文にもチェック項目として載っています。
**あなたのテストを疑う人は、今日はあなた1人だけです。** ここを飛ばすと、誰も見ないまま通ります。

**完了条件**

- [ ] Issue の必須要件チェックリストが**全部**埋まっている（埋まらないものは「未達」と正直に記録する）
- [ ] 異常系・境界値のテストが入っている
- [ ] **テストを疑う儀式を、ターミナルB とエディタだけで実施した（A に1文字も打っていない）**
- [ ] **テストが赤くなることを目で見た**
- [ ] 儀式のあと `git diff` で確認し、書き換えが残っていないことを確かめた
- [ ] `src/games/<ゲームID>/index.ts` の `status` が `"ready"` になっている
- [ ] `npm test` が緑

### Step 12｜`/verify` → `/pr` → `gh pr ready`（105〜115分）

> **ターミナルB の `dev` は動いていますか？** — スクリーンショットを撮るので、動いている必要があります。

提出前の全部入りチェックを通し、Pull Request の本文を仕上げて Draft を外します。
**`npm run verify` が緑になるまで「できました」と言わないでください。** これが CI とまったく同じ内容です。

**この Step の直前に、もう一度 `/handoff` を打ちます。**
Step 9 と同じ課題です。**出てきた10行のうち、事実と違う行を1つ探してください。**
ここで見つかるずれは、たいてい「できていない」ものが「できている」に混ざっているものです。
**それを混ざったまま PR に出すと、レビュアーが最初に見つけます。**

**打つプロンプト**

1本目 — 状態の申告が正しいかを、自分で検算します。

```text
/handoff
```

（出てきた10行のうち、事実と違う行を1つ探して、その行だけを直させてください）

2本目 — Issue と実装の突き合わせ。

```text
/verify <Issue番号>
```

必須要件と実装・テストの対応表が出ます。**未達があれば正直に未達として扱ってください**（隠しても相互レビューで必ず見つかります）。

3本目 — Pull Request の本文の下書き。

```text
/pr
```

`.pr-body.md` ができます。**`gh pr create` は実行されません。**
`/pr` は「レビューしてほしい点」を**空欄のまま残します。** そこは人間が書く場所だからです。

4本目 — 自分で「レビューしてほしい点」を書き終えてから打ちます。

```text
.pr-body.md の「レビューしてほしい点」は私が自分で書きました。次を順に実行してください。

1. npm run verify
2. git add src/games/<ゲームID>
3. git commit -m "feat(<ゲームID>): ゲームを実装する"
4. git push
5. gh pr edit <自分のPR番号> --body-file .pr-body.md

.pr-body.md の中身は書き換えないでください。
gh pr ready は実行しないでください。私が自分で打ちます。
```

**Claude Code がやること**

| 実行されるコマンド | 承認 |
|---|---|
| `npm run verify`（範囲チェック → lint → 型 → テスト → ビルド） | 確認なしで通る |
| `gh issue view <Issue番号>` | 確認なしで通る |
| `.pr-body.md` の作成（`gh pr create` は実行しない） | 確認なしで通る |
| `git add` / `git commit` | 確認なしで通る |
| `git push` | **あなたの承認が要ります** |
| `gh pr edit <自分のPR番号> --body-file .pr-body.md` | **あなたの承認が要ります** |

**ターミナルB でやること**

1. **`.pr-body.md` の「レビューしてほしい点」を自分の言葉で書く**（ここは AI に任せません）

```powershell
code .pr-body.md
```

「勝敗判定を見てください」ではなく
「同じ数字が出たときの引き分け処理が怪しいので、そこを重点的に」のように具体的に書きます。

**あなたの PR を見るのは1人だけです。** その1人の目をどこに向けたいかを、自分で決めて書いてください。
**ここがテンプレートのままだと、Step 13 でレビュアーから「それ自体」を指摘されます**（機構5）。
書けないときは、Step 11 の儀式でいちばん自信がなかったテストの名前を書いてください。

2. **ゲーム画面のスクリーンショットを撮る**（`Win + Shift + S`）

3. **Draft を外して、CI を見る**

```powershell
gh pr ready <自分のPR番号>
gh pr checks <自分のPR番号> --watch
```

`gh pr ready` は**あなたが自分の手で打ちます。**「もう他人に見せてよい」と決めるのは人間だからです。

4. GitHub の画面で Pull Request を開き、**スクリーンショットを本文にドラッグ&ドロップ**する
   （画像ファイルはリポジトリにコミットしないでください）

5. **自分をレビューする人**（担当表のいちばん右）に「PR 出しました」と直接伝え、**PR 番号を渡す**

**完了条件**

- [ ] `/handoff` を打ち、事実と違う行を1つ見つけて直させた
- [ ] `npm run verify` が緑
- [ ] Pull Request の Draft が外れている（**`gh pr ready` を自分の手で打った**）
- [ ] CI の `verify` が緑
- [ ] 本文の「レビューしてほしい点」が**自分の言葉**で書かれている（テンプレートのままでない）
- [ ] スクリーンショットが本文に貼られている
- [ ] 「採用したルール / 今回は実装しない」が書かれている
- [ ] 自分をレビューする人に PR 番号を伝えた

- つまり「重い実装の人は軽いレビュー、軽い実装の人は重いレビュー」で釣り合わせています。

**そして、いちばん大事なこと。**

チーム開発なら、あなたのコードは同じチームの誰かが自然に目にします。
今日は違います。**あなたが書いたコードを見る他人は、リングの1人だけです。** 逃げ場も代わりもありません。
**差分を眺めるだけのレビューは、この研修では成果として認めません。**

**この Step は A と B を4回往復します。順番を守ってください。**

```text
① A  相手のゲームの「壊れやすい所」を原文のまま出す
② B  gh pr checkout して、実際に遊ぶ（ここが本体）
③ A  /review で差分を読む
④ A  投稿用の文章を作らせる（投稿はしない）
⑤ B  GitHub の画面から投稿する ＋ 相手の「レビューしてほしい点」を検問する
⑥ B  自分のブランチに戻る
```

**打つプロンプト**

① — 相手のゲームの「壊れやすい所」を、原文のまま出させます（**遊ぶ前に打ちます**）。

```text
docs/games/<相手のゲームID>.md を開いて、「レビュアー向けミッション」の見出しの中にある
ミッション1・ミッション2・ミッション3 の本文を、そのまま引用して表示してください。

```

**これが、相手のゲームで「遊ぶ前に書く壊し方3つ」の材料です**（Step 10 では自分で考えましたが、
相手のゲームはルールを知らないので、正典が用意してくれています）。

**相手のゲームのルールを知らなくても、書いてあるとおりに動かせば正しいかどうか判定できます。**
引用された3つを、**紙かメモ帳に写してから**②へ進んでください。写す1分が、あとの20分を決めます。

③ — **②で実際に遊んだあとに**、差分の読み込みを手伝わせます。

```text

```

> `/review` の手順書には `npm run dev` が入っていますが、**Claude Code は実行できません**（拒否されます）。
> 遊ぶのは②で済ませてあるので、そのまま進んで構いません。
> `npm ci` を実行しようとしたら `Esc` で止めてください（理由は②に書いてあります）。

`/review` はコメントを投稿しません。**投稿するかどうかは人間が決めます。**

④ — 投稿する文章を作らせます。**投稿はさせません。**

```text
私が実機で確認できたのは次の3つです。

1. <自分が画面で見たこと>
2. <自分が画面で見たこと>
3. <自分が画面で見たこと>

これ以外の指摘には「未確認」と明記した形にして、投稿用の文章を出してください。

```

**指摘は必ず3点セットで出します**

1. **ルール検証の指摘（再現手順つき）**
   「〇〇を〇回すると〇〇になります。Issue では〇〇のはずです」の形。
   **再現手順が書けない指摘は投稿しません。**
2. **テスト観点の提案（具体的なテスト名で）**
   「`it("同じ数字が続いたとき引き分けになる")` を足すとよいです」の形。
3. **質問または可読性の提案**（1つは GitHub の suggestion 形式で書けるもの）

**Claude Code がやること**

| 実行されること | 何のため |
|---|---|
| `docs/games/<相手のゲームID>.md` の読み取り | ミッションを原文のまま引用する |
| `gh pr view <相手のPR番号>` / `gh pr diff <相手のPR番号>` | 差分と本文を読む |

| `npm ci` | **打たせないでください**（`Esc` で止める。理由は②） |
| `gh pr review` / `gh pr comment` | **拒否されます。** 投稿は人間の仕事です |

```text

あなたの担当は <ゲームID> です。
いま相手のブランチを取ってきている（レビュー中）だけなので、
```

**気づいたことは、直すのではなくコメントで伝えてください。**

**ターミナルB でやること**
