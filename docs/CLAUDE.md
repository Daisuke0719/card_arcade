# `docs/` 文書作成ルール

このファイルは、`docs/` 以下の Markdown を作成・編集するときに適用します。
リポジトリ直下の `CLAUDE.md` にあるルールも引き続き守ってください。

## 文書を書く前に確認すること

書き始める前に、文書の読者と目的を確認します。

- 参加者向けの手順書: 初めてこのリポジトリを触る人が、迷わず操作できることを優先する。
- 講師向けの進行資料: 時刻、声をかける条件、トラブル時の対応をすぐ確認できるようにする。
- 技術解説: 仕組み、制約、採用理由を、コードや設定と対応させて説明する。
- ゲーム別の仕様書: 採用するルール、実装しないルール、必須要件、テスト条件を明確に分ける。
- トラブルシューティング: 症状、確認方法、原因、対処、解決の確認という順序で書く。

既存文書を編集するときは、対象の文書だけで判断せず、関連するファイルも確認します。
担当、ゲーム ID、Issue 番号は `harness/config.json` の内容を優先します。ゲームの仕様を変更するときは、対応する `docs/games/<ゲームID>.md`、Issue の本文、テストの間に矛盾が生じないか確認してください。

## 基本方針

- 読者が次に何をすればよいか分かる文章にする。
- 結論または操作を先に書き、理由や補足をあとに続ける。
- 一つの段落では一つの話題だけを扱う。
- 前提知識を要求する場合は、その前提を先に示す。
- 同じ内容を言い換えて繰り返さない。
- 読者を急かしたり責めたりせず、問題が起きたときの対処を具体的に示す。

## AI が作ったような文章を避ける

### 直訳調を避ける

英語の構文をそのまま日本語に移さず、文の役割を理解してから書き直します。

| 避ける表現                     | 推奨する表現                         |
| ------------------------------ | ------------------------------------ |
| 計画を出させます               | 実装計画の作成を依頼します           |
| 状態を画面に出します           | ゲームの状態を画面に反映します       |
| CI を見ます                    | CI の結果を確認します                |
| Draft を外します               | Draft 状態を解除します               |
| ブランチを切ります             | ブランチを作成します                 |
| 次の一手を出します             | 次に試すことを提案します             |
| 問題を潰します                 | 問題を一つずつ解決します             |
| 変更を入れます                 | 変更します / 変更を反映します        |
| ファイルを取ってきます         | ファイルを取得します                 |
| 最後までパイプラインを通します | 一連の検証が成功することを確認します |

「〜させます」を一律に禁止する必要はありませんが、AI や参加者に作業を依頼する場面で繰り返すと不自然になります。「依頼します」「確認します」「作成します」など、実際の行為に合う動詞を選んでください。

### 大げさな表現を避ける

説明の代わりになるようなキャッチコピーや比喩は使いません。

- `丸投げ集ではありません`
- `時間を溶かします`
- `レビュアーは検問です`
- `テストを疑う儀式です`
- `9人のリングです`
- `困ったときの逃げ道です`
- `今日いちばん持ち帰る価値があります`
- `ここが唯一の分かれ目です`

このような表現が必要に見えた場合は、伝えたい内容を具体的な行動に置き換えます。

```text
悪い例:
レビュアーは検問です。ここで黙ると、そのまま公開されます。

良い例:
レビュアーは、再現手順とテスト結果を確認します。懸念が残っている場合は、マージ前にコメントしてください。
```

### 読者の心理を決めつけない

次のような表現は避けます。

- `指摘がないのは、まだ読んでいないからです。`
- `分からないのは、自分の状態を把握していないからです。`
- `この手順を飛ばすと、必ず失敗します。`
- `誰も気づきません。`

読者の態度を推測するのではなく、確認する項目と、確認しなかった場合に起こり得る問題を書いてください。

```text
悪い例:
1件も問題を見つけられない計画は、まだ読んでいない計画です。

良い例:
問題が見つからない場合は、Issue の必須要件と計画を上から1件ずつ照合してください。
```

### 主語と強調を増やしすぎない

- 文脈から明らかな場合は、主語を省く。
- 「あなた」「人間」「参加者自身」「自分の手で」「自分の目で」を繰り返さない。
- AI と参加者を区別する必要がある場合だけ、主語を明記する。
- 太字は、禁止事項、必須条件、操作対象など、読み飛ばすと作業に影響する箇所に限る。
- 一つの段落で複数の文を太字にしない。
- 感嘆符は原則として使わない。

## 文体と用語

### 文体

- 本文と手順は「です・ます」調に統一する。
- 箇条書きの説明は、文書内で「〜する」または「〜します」のどちらかにそろえる。
- 手順の番号付きリストでは、一つの番号に一つの操作を書く。
- 操作結果は過去形で書かず、確認できる状態を書く。
  - 避ける: `画面が表示された。`
  - 推奨: `画面が表示されることを確認する。`
- 理由を補足するときは、括弧を重ねず、必要に応じて次の文に分ける。

### 用語

同じ操作を複数の言葉で呼ばないでください。

| 対象                         | 使用する表現                                   |
| ---------------------------- | ---------------------------------------------- |
| Claude の製品名              | `Claude Code`                                  |
| Claude Code へ文章を渡す操作 | プロンプトを入力する                           |
| シェルでコマンドを動かす操作 | コマンドを実行する                             |
| テストや CI の結果           | 成功する / 失敗する                            |
| ブラウザでゲームを試す操作   | ゲームを操作する / 実際に遊ぶ                  |
| Git の作業単位               | ブランチを作成する / ブランチを切り替える      |
| Pull Request の状態変更      | Draft 状態を解除する / Ready for review にする |
| 要件との比較                 | 照合する                                       |
| 内容を読む操作               | 確認する / 読む                                |

`見る`、`出す`、`入れる`、`やる` は意味が広いため、より具体的な動詞に置き換えられないか確認します。

## 見出し

- 見出しだけで、その節に何が書かれているか分かるようにする。
- `大切なこと`、`覚えておくこと`、`いちばん重要なページ` のような抽象的な見出しを避ける。
- 名詞だけを並べるより、必要に応じて操作を含める。
  - 避ける: `最終確認`
  - 推奨: `提出前にテストと差分を確認する`
- 同じ階層の見出しは、粒度と文型をそろえる。
- 見出しに絵文字や感嘆符を付けない。

## 手順書

手順を書くときは、次の順序を基本とします。

1. この手順で何を行うか。
2. 操作前に満たしておく条件。
3. 入力するプロンプトまたは実行するコマンド。
4. 実行後に確認する状態。
5. 失敗した場合の対処。

操作の前後関係が重要な場合は、「先に」「完了してから」「確認後に」を使って順序を明示します。「適宜」「必要なら」だけで済ませず、どの条件に該当したら実行するのかを書いてください。

完了条件は、読者が画面やコマンド結果で判定できる内容にします。

```text
避ける:
- 仕組みを理解した
- 正しく設定できた
- 問題なく動いた

推奨:
- `git branch --show-current` に `feature/<ゲームID>` と表示される
- `npm test` が終了コード 0 で完了する
- ブラウザに担当ゲームのタイルが表示される
```

## プロンプト例

文書内に Claude Code へ入力するプロンプトを載せる場合は、次の要素を必要な範囲で含めます。

1. 目的
2. 対象ファイルまたは対象範囲
3. 実行してよい操作
4. 実行してはいけない操作
5. 作業を止める条件
6. 報告してほしい形式

制約は、曖昧な注意ではなく具体的な命令として書きます。

```text
避ける:
いい感じに直してください。ほかはなるべく触らないでください。

推奨:
`src/games/<ゲームID>/logic.ts` だけを修正してください。
ほかのファイルは変更しないでください。
修正後に `npm test` を実行し、失敗した場合は追加の変更をせず、エラーをそのまま報告してください。
```

次の制約は意味を変えずに残します。

- 対象を限定する文: `logic.ts と logic.test.ts だけを変更してください。`
- 作業を止める文: `まだ修正しないでください。`
- 外部への操作を防ぐ文: `投稿はしないでください。`
- 長時間動作する処理を防ぐ文: `npm run dev は実行しないでください。`

プロンプトを自然な日本語に直す場合でも、制約を弱めたり削除したりしないでください。

## コマンド、コード、引用

- コマンド、オプション、パス、URL、コード、プレースホルダーは、文章を直す目的で変更しない。
- 実際の出力例やエラーメッセージは、原文のまま掲載する。文章上の都合で言い換えない。
- コードブロックの言語指定を維持する。PowerShell は `powershell`、通常の文面は `text` を使う。
- インラインのコマンド、ファイル名、型名、関数名はバッククォートで囲む。
- `<ゲームID>` や `<Issue番号>` などのプレースホルダーは、表記を文書内で統一する。
- コマンドの実行場所が重要な場合は、ターミナルAまたはターミナルBのどちらで実行するか明記する。

文書内のコマンドを変更する前に、`package.json`、スクリプト、CLI のヘルプなどで実際の構文を確認します。確認できないコマンドを推測で追加しないでください。

## 箇条書きと表

- 箇条書きは、三つ以上の並列項目がある場合や、順序のない条件を整理する場合に使う。
- 手順には番号付きリストを使う。順序に意味がない項目には番号を付けない。
- 一つまたは二つの短い内容を、無理に箇条書きにしない。
- 表は、複数の項目を同じ観点で比較するときに使う。文章で十分な内容を表にしない。
- 表の列名は具体的にする。`内容` や `備考` だけでは意味が分かりにくい場合は、何を示す列か明記する。
- セル内に長い説明を詰め込まない。説明が長くなる場合は、表の下に本文として書く。

## 注記と警告

引用ブロックは、前提条件、例外、危険な操作の警告に使います。本文と同じ内容を強調するためだけには使いません。

警告には、次の三つを含めます。

1. 何をしてはいけないか。
2. 実行すると何が起きるか。
3. 代わりに何をすればよいか。

```text
避ける:
絶対に実行しないでください。大変なことになります。

推奨:
`npm run dev` が動いている間は `npm ci` を実行しないでください。
Windows では使用中のファイルを置き換えられず、処理が失敗します。
依存関係を入れ直す場合は、先に開発サーバーを停止してください。
```

## 文書を修正するときの注意

- 文章だけを直す依頼では、技術的な意味、手順の順序、コマンド、時間、担当、完了条件を変更しない。
- 不整合や明らかな誤記を見つけた場合は、根拠を確認できる範囲で修正する。仕様変更につながる場合は、文章修正とは分けて報告する。
- 同じ表現が複数の文書にある場合でも、一括置換の前に文脈を確認する。
- 既存の用語を変更するときは、見出し、本文、表、完了条件、関連文書に古い表記が残っていないか検索する。
- 大幅に書き直したあとは、変更前後でコードフェンスとプレースホルダーの数を比較する。

## 完了前の確認

文書の作成または編集が終わったら、次を確認します。

### 内容

- 読者、目的、前提が明確か。
- 操作の順序と完了条件が一致しているか。
- 技術的な説明がコードや設定と一致しているか。
- 根拠のない断定や、読者の心理を決めつける表現がないか。
- 同じ説明を繰り返していないか。

### 日本語

- 英文を逐語訳したような語順が残っていないか。
- 「〜します」が三文以上続いていないか。
- `見る`、`出す`、`入れる`、`やる` を、より具体的な動詞に置き換えられないか。
- 不要な主語、太字、括弧、比喩を削れるか。
- 声に出して読んだときに、息継ぎしにくい長文や、不自然に短い文がないか。

### Markdown

- 見出しの階層が飛んでいないか。
- コードフェンスが閉じているか。
- 箇条書きと番号付きリストのインデントが正しいか。
- 表の列数が各行で一致しているか。
- リンク先、ファイルパス、見出し名が存在するか。
- コマンド、プレースホルダー、引用文を誤って変更していないか。

確認が終わるまでは、文書の修正を完了したと報告しないでください。
