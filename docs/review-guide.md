# レビューガイド — ほかの担当者の Pull Request を読む

## レビューの目的

レビューで見るのは「**動くか**」ではありません。動くかどうかは CI が見ています。

人間のレビューで見るのは、**他の人が読めて、直せるか**です。

- ルールの解釈が正典（`docs/games/<ゲームID>.md`）と合っているか
- 半年後に別の人が開いて、変数名と関数名だけで意味が分かるか
- テストが「壊れたら気づける」ものになっているか
- 直すときに、どこを直せばよいかが分かる形になっているか

**あなたはそのゲームのルールを知らなくてかまいません。**
このガイドの「ゲーム別ミッションカード」に書いてあるとおりに操作すれば、意味のある検証ができます。
むしろ**知らない人が触って壊れるところ**こそ、いちばん見つけたいバグです。

---

## 個人開発では、レビューの重みが変わります

今回は9人が**1人1ゲーム**を担当します。調査も実装もテストも Pull Request も、全部1人でやります。
そのぶん、レビューの意味がチーム開発のときとは変わります。

**あなたのコードを最後まで読む他人は、レビュアー1人だけです。**

チームで作っていれば、書いている途中に隣の人が「そのルールおかしくない？」と気づけます。
ペアで画面を見ていれば、連打で壊れる瞬間をその場で目撃できます。
今回はそれがありません。**あなたが見落としたバグは、そのまま統合デモに出ます。**

だから、この2つは形式ではなく実質です。

| 守ること | 個人開発だと何が起きるか |
|---|---|
| **必ず `gh pr checkout` して動かす** | 差分を読むだけだと、誰1人としてその実装を遊んでいない状態でマージされます |
| **3点セット（ルール検証・テスト観点・可読性）を必ず出す** | 「LGTM」だけで通すと、そのゲームは作った本人以外の目が一度も入らないまま公開されます |

作る側にも同じことが言えます。1人で書いていると、**自分の思い込みに気づける機会が1回しかありません。**
それがレビューです。指摘は「ダメ出し」ではなく、**あなたが1人では手に入れられない2つ目の目**です。

もう1つの目は講師です。詰まって10分たったら `/stuck` を実行するか、講師を呼んでください。
1人だと「詰まっていること自体」に気づくのが遅れます。中間チェックポイントで講師が `npm run status` を見ますが、
それを待たずに声を上げてかまいません。

輪になっています（担当1 → 担当2 → … → 担当9 → 担当1）。自分の PR は自分ではレビューしません。

### この組み合わせの意図

でたらめに並べた輪ではありません。**難易度を見て、負担が偏らないように組んであります。**

- **上級を担当する人（担当2 = 大富豪 / 担当4 = ポーカー）がレビューするのは、初級のゲーム**です。
  上級ゲームは実装そのものに時間がかかるので、レビュー先を軽くしてあります。
  担当2 のレビュー先は神経衰弱、担当4 のレビュー先はぶたのしっぽです。
- **逆に、上級のゲームをレビューするのは、早く終わる初級担当の人**です。
  大富豪をレビューするのは担当1（ババ抜き）、ポーカーをレビューするのは担当3（神経衰弱）。
  先に自分の実装が終わるので、重い Pull Request に時間を使えます。

つまり「**重いものを作る人には軽いものを、軽いものを作る人には重いものを**」という組み方です。
自分のレビュー先が重いと感じたら、それは**あなたの実装が先に終わる前提**で組まれているからです。
早く終わらせて、レビューに時間を回してください。

> 組み合わせの正は `harness/config.json` の `participants[].reviews` です。
> ゲームのページ（`docs/games/<ゲームID>.md`）の文中の記述と食い違って見えたら、**この表に従ってください。**
> 当日 `harness/config.json` の `participant` を GitHub のアカウント名に差し替えると、
> Issue・ラベル・雛形・画面の表示が一斉に揃います。

## 手順

レビューは20分です。**そのうち最初の10分は「動かす」に使ってください。**

### 1. 自分の変更を退避する

`gh pr checkout` は未コミットの変更があると失敗します。先に片付けます。

```powershell
git status
git add .
git commit -m "wip: レビュー前の一時保存"
```

### 2. 相手のブランチを取ってきて、動かす（**ここを飛ばさない**）

```powershell
gh pr list
gh pr checkout <PR番号>
npm ci
npm run dev
```

ブラウザで開いて、**実際に最後まで1回遊んでください。**

- 普通に1回クリアする
- **やってはいけない操作**をわざとやる（判定中に連打する、出せないカードを出す、0枚のときに引く）
- リセットして2回目が正しく始まるか見る
- 下の「ゲーム別ミッションカード」の3つを順にやる

**差分を眺めるだけのレビューは、この研修では無効です。**
GitHub の画面で赤と緑を見ているだけでは、ルールの誤りは1件も見つかりません。
逆に、5分遊べば必ず何か見つかります。

`/review <PR番号>` を使うと、この手順を Claude Code が案内し、指摘の下書きまで作ります。
ただし**コメントの投稿はしません。** 投稿するかどうかは人間が決めます。

### 3. Issue（正典）と突き合わせる

```powershell
gh pr view <PR番号>
gh issue view <その PR が閉じる Issue 番号>
```

必須要件を1つずつ読み、実装とテストが対応しているか確認します。
Issue のチェックリストは、**その人の進み具合を外から見られる唯一の指標**でもあります。
未チェックの項目が残ったまま Ready になっていたら、それ自体が確認すべき点です。

### 4. 差分を読む

```powershell
gh pr diff <PR番号>
```

### 5. 終わったら自分のブランチに戻る（忘れやすい）

```powershell
git switch feature/<自分のゲームID>
```

## 観点チェックリスト

| 観点 | 具体的に見ること |
|---|---|
| **Issue の必須要件** | 正典の必須要件が全部あるか。**書かれていないローカルルールが足されていないか**（多すぎるのも指摘対象） |
| **ルールの境界** | 同じ数字 / 最後の1枚 / 0枚 / 全員パス / K の次 / 誰かが上がった直後 — ここが正典と一致しているか |
| **テストの偏り** | `logic.test.ts` の `it("...")` を上から読む。正常系だけになっていないか。異常系・境界値があるか。怪しければアサーションを1つ逆にして、本当に赤くなるか手元で試す |
| **担当範囲** | `gh pr diff` のファイル一覧が `src/games/<その人のゲームID>/` の中だけか。外があれば**必ず指摘**（CI も落ちます） |
| **命名** | 変数名・関数名だけで意味が分かるか。`flag` `data` `tmp` `check2` のような名前が残っていないか |
| **役割の分離** | 勝敗やルールの判定が `<Xxx>Game.tsx` に漏れていないか。`logic.ts` に `Math.random()` `Date.now()` `setTimeout` `react` が入っていないか |
| **他への影響** | アーケード一覧（トップ画面）が壊れていないか。他のゲームが開けるか。`index.ts` の `status` が実態と合っているか |

## ゲーム別ミッションカード

自分がレビューする1枚だけ読めば十分です。ルールを知らなくても、書いてあるとおりに操作すれば判定できます。
より詳しい説明は `docs/games/<ゲームID>.md` の「レビュアー向けミッション」にあります。

### 担当1（ババ抜き担当） → 大富豪（`daifugo`）

1. **枚数のごまかしが通らないか。** CPU が2枚出しをした直後に、手札から**1枚だけ**選んで「出す」を押す
   → 出せないこと。3枚選んでも出せないこと。**場と同じランクのペア**も出せないこと（「より強い」でなければ出せないのが正しい）。
2. **8切りの後、手番が移っていないか。** `8` を含む組を出す
   → その瞬間に場札が消え、**もう一度あなたの番**になること。CPU に手番が移ったら不具合。
   場が空なので、次は好きなランク・好きな枚数で出せることも確認する。
3. **革命が起きて、元に戻るか。** 同じランクを**4枚**まとめて出す
   → 「革命」のログが出て、それ以降は `3` がいちばん強く `2` がいちばん弱くなること。
   **もう一度4枚出して**、強さが元（`2` が最強）に戻ること。**革命が戻らないのがいちばん多いバグです。**

### 担当2（大富豪担当） → 神経衰弱（`shinkeisuijaku`）

1. **判定中に連打する。** 違う数字の2枚をめくった直後（裏に戻るまでの0.8秒の間）に、別のカードを何度もクリックする。
   → 3枚目は**表にならず**、手数も**1しか増えない**のが正しい動きです。
2. **ペアが成立したカードをもう一度クリックする。**
   → **何も起きない**のが正しい動きです。裏に戻る / 手数が増える / 次の1枚目として数えられる、はいずれも不具合です。
3. **クリアしてから「もう一度」を押す。**
   → 結果に**手数が出て**、16枚が全部裏に戻り、**手数が0**になり、**前回とは違う配置**になるのが正しい動きです。

### 担当3（神経衰弱担当） → ポーカー（`poker`）

役の強さは**弱い順に**次のとおりです。この1行だけ手元に置けば、役を知らなくても判定できます。

> ハイカード < ワンペア < ツーペア < スリーカード < ストレート < フラッシュ < フルハウス < フォーカード < ストレートフラッシュ

1. **交換が本当に一度だけか。** 何も選ばずに「交換する」を押す → 手札が1枚も変わらず、そのまま判定へ進むこと。
   5枚すべてを選んで押す → 5枚とも入れ替わり、**山札の残りが5枚減る**こと。
   2枚選んで「交換する」を**素早く3回**押す → **交換は1回だけ**行われること
   （押したあとボタンが押せなくなっていれば正しい挙動です）。手札が2回入れ替わる・山札が想定より多く減る、が典型的なバグです。
2. **A の2つのストレートが両方通るか（ここがいちばん壊れやすい）。** 画面では狙って出せないので、テストで確認します。
   `src/games/poker/logic.test.ts` の `"A-2-3-4-5 をストレートと判定できる"` を探し、手札を **10-J-Q-K-A**
   （`hand("spades-10","hearts-J","clubs-Q","diamonds-K","spades-A")`）に書き換えて `npm test`
   → **これも `straight` になること。** 次に **A-2-3-4-6**（連番でない）に書き換えて
   → **`straight` にならず `high-card` になること。** 終わったら `git restore src/games/poker/logic.test.ts` で戻します。
   前者が落ちるなら A を 14 でしか見ておらず、後者が落ちるなら A を無条件に 1 として通しています。
3. **弱い役が勝っていないか / 手札が漏れていないか。** **10回**リセットして最後まで遊び、結果画面を毎回確認する。
   → 表示された**両者の役名**を上の一行と見比べ、**弱いほうが勝っていない**こと。
   同じ役名どうしになった回は、勝ちか引き分けが必ず表示され、画面が固まらないこと。
   交換する前に、CPU の手札の中身が**画面にも F12 の Elements にも出ていない**こと。

### 担当4（ポーカー担当） → ぶたのしっぽ（`butanoshippo`）

1. **引き取りが起きる瞬間を3回見る。** 同じ数字が2回続くまで進め、その瞬間を**3回**確認する。
   → 一致した瞬間に、**場に積まれていたカードが全部**その人の枚数に足されること。
   引き取りの直後、場の中央が**空**になっていること。
   空になった直後の1枚目のめくりで**引き取りが起きない**こと（起きたら、消したはずの古い1枚と比べています）。
2. **引き取った直後の手番を見る。** → **引き取った人の次の人**がめくること。引き取った人が続けてめくったら誤りです。
   1人飛ばして2人先に回っていないこと（`ScoreBoard` の手番表示で分かります）。
   CPU の手番中や引き取りの演出中に輪を**連打**しても、自分の番より先にめくれてしまわないこと。
3. **最後まで遊び切って枚数を確認する。** → 順位が**引き取り枚数の少ない順**に1位から4位まで並ぶこと（多い人が1位なら逆です）。
   4人の引き取り枚数の合計と、場に残ったカードの枚数を足すと **52枚**になること
   （合わなければ最後の引き取りが飛ばされたか、二重に数えています）。輪が0枚になったあとにクリックしても固まらないこと。

### 担当5（ぶたのしっぽ担当） → スピード（`speed`）

1. **同じ数字と連打。** 台札と**同じ数字**のカードをクリックする → 何も起きず、緑のハイライトも付かないこと。
   ハイライトが付いたカードを**素早く2回クリック**する → **2枚出ていない**こと。
   左右どちらにも出せるカードは**必ず左の台札**が変わること（これは仕様）。
2. **A と K の折り返し。** 台札が `K` のときに手札の `A` が出せること、台札が `A` のときに `K` が出せること。
   ついでに、台札が `K` のときに `2` が**出せない**ことも確認する。
3. **詰みからの自動復帰と決着。** 何も操作せずに待ち、双方が出せない状態になったら**1秒以内に台札が2枚とも自動で入れ替わる**こと。
   固まったら「二度と進まない」重大バグです。山札が0枚になっても固まらないこと、
   結果表示が残り枚数と矛盾していないこと（残り枚数が多いほうが「勝ち」なら不具合）。

### 担当6（スピード担当） → 七並べ（`shichinarabe`）

1. **CPU の手番中に自分の手札を連打する。**
   → 何も起きず、自分の手番が来たときに押した分がまとめて出たり2枚同時に出たりしないこと。
   手番のチェックが画面側の `disabled` だけだと、ここをすり抜けます。
2. **パスできる条件を確かめる。** 押せる（明るい）カードが1枚でもあるとき → **パスボタンが押せない**。
   1枚も無いとき → **パスボタンが押せる**。「出せるのにパスできる」はゲームが終わらなくなる不具合です。
3. **誰かを脱落させる。** 同じ人が**4回目のパス**をするまで進める。
   → 脱落した瞬間にその人の手札が**全部**場に出ること（7から離れた飛び地も出る）、以降その人に手番が回らないこと、
   順位表で**脱落した人が、手札を出し切った人より上に来ていない**こと。

### 担当7（七並べ担当） → ダウト（`doubt`）

1. **うそが暴かれたときの罰の向き。** 宣言ランクと**違うカード**をわざと2枚出し、CPU にダウトされる。
   → 公開されたカードが自分の選んだ2枚と同じで、**自分の手札が増える**（場札を全部引き取る）こと。
   4人の手札と場札を足して**52枚**になっているかも数える（増減していたらカードの複製か消失）。
2. **誰もダウトしないときの進み方とリセット。** 宣言が `A` → `2` → `3` … と1つずつ進み、**`K` の次が `A` に戻る**こと。
   その間、場札が減らずに積み上がること。1回ダウトを起こしたら、**場札が0枚に戻り、宣言が `A` に戻り、引き取った人の次の人から手番が始まる**こと。
3. **情報が漏れていないか。** F12 の Elements で CPU の手札の表示部分を調べ、
   ランクやスート（`spades`、`A` など）が**どこにも出ていない**こと（出ているのは枚数だけ）。場札の山も同様。

### 担当8（ダウト担当） → ページワン（`pageone`）

1. **8 と A を出したあとの手番を見る。** 自分の手札に `8` か `A` が来るまで遊び、出したあとの手番を追う
   （CPU が出した場合も手番の表示で追ってください）。
   → **`8` を出したら次の人が1回飛ばされる**こと（あなたが出したなら CPU 1 が飛ばされ、CPU 2 の手番になる）。
   **`A` を出したら同じ人の手番が続く**こと。`A` のあとに出せるカードが1枚も無いときは、**山札を引くだけ**で次の人へ移ること。
   `A` で手番が進む / `8` で誰も飛ばされない / `A` のあとに手番が固まる、のどれかが起きたら不合格です。
2. **山札を最後まで引き切る。** 残り枚数を見ながら遊び続け、山札が0枚になった瞬間を見る
   （1回で起きなければリセットして2〜3回試す）。
   → **ゲームが止まらず**、場札が混ぜられて山札に戻り、また引ける状態になること。
   混ぜ直したあとも、**場札の一番上は直前と同じカードのまま**であること（急に別のカードへ変わらない）。
   その場札に対して、出せる・出せないの判定が正しく効いていること。
3. **出せるのに引く / 出せないのに出す、を試す。** 押せる（明るい）カードがある状態で**山札をクリック**する
   → 何も起きないこと。押せない（暗い）カードを何度もクリックする → 何も起きないこと。
   CPU の手番中に自分の手札と山札を**連打**する → 何も起きず、自分の番でまとめて反映されたり2枚同時に出たりしないこと。

### 担当9（ページワン担当） → ババ抜き（`babanuki`）

1. **配札直後のペア掃除を5回試す。** リセットを5回繰り返し、毎回**自分の手札**に**同じ数字が2枚以上並んでいない**こと。
   （同じ数字が1枚だけ残っているのは**正しい状態**です。3枚あったうちの1枚）
2. **誰かが上がった直後の手番を見る。** CPU が1人上がるまで進め、
   → 上がった人の手札欄が**空**になって引けないこと、引く向きが**上がった人を飛ばして次の生存者**を指すこと、
   CPU の手番中に相手の手札を**連打**しても自分の番の前に引けてしまわないこと。
3. **最後まで遊び切って順位を確認する。** 順位が**上がった順**に並び、
   **最後に残った1人が4位**で、その人の手札が**ジョーカー1枚**であること。4人全員が「上がった」表示なら誤りです。

## 必ず出す3点セット

レビューコメントは**この3つを必ず**出してください。3つ揃って初めて「レビューした」と言えます。
繰り返しますが、そのコードを読む他人はあなた1人です。**出さなかった分は、誰も埋めません。**

### 1. ルール検証の指摘（**再現手順つき**）

```text
〇〇を〇回すると〇〇になります。
docs/games/<ゲームID>.md では〇〇のはずです。

再現手順:
1. ...
2. ...
3. ...
```

**再現手順が書けない指摘は投稿しないでください。** 直す側が確認できないからです。
「たぶんバグだと思う」は、指摘ではなく質問として書きます。

### 2. テスト観点の提案（**具体的なテスト名で**）

```text
logic.test.ts に次のテストを足すとよいと思います。

it("同じ数字が続いたときに引き分けになる")
it("最後の1枚を出したあとに手番が回らない")
```

「テストが足りません」ではなく、**そのまま貼れるテスト名**を書きます。
相手はそれを `logic.test.ts` にコピーするだけで着手できます。

### 3. 質問、または可読性の提案（1件は `suggestion` 形式で）

GitHub の差分の行番号をクリックして、コード提案として書けます。相手はボタン1つで取り込めます。

````markdown
```suggestion
const isDrawablePlayer = (id: PlayerId) => !isFinished(state.turn, id);
```
変数名が `f` だと役割が読み取れませんでした。この名前はいかがでしょうか。
````

## 指摘の書き方

### 悪い例と良い例

| | 書き方 |
|---|---|
| 悪い | 「動きません」 |
| 良い | 「CPU が1人上がったあと、自分の手番でカードをクリックしても何も起きなくなりました。手順: ①CPU が1人上がるまで待つ ②自分の番で左隣の手札をクリック → 反応なし。ブラウザのコンソールにエラーは出ていません」 |

| | 書き方 |
|---|---|
| 悪い | 「テストが足りないです」 |
| 良い | 「`it("判定中にもう一度クリックしても手数が増えない")` があると、実機で見つけた連打の問題を防げると思います」 |

| | 書き方 |
|---|---|
| 悪い | 「この書き方は良くないです」「普通はこう書きます」 |
| 良い | 「`reduce` の中で `hands` を直接書き換えているように見えました。意図的でしょうか？ もし違うなら、新しい配列を返す形にすると再現テストが書きやすくなりそうです」 |

| | 書き方 |
|---|---|
| 悪い | 「LGTM」だけ（動かしていない） |
| 良い | 「ミッション1〜3を実機で試して、いずれも期待どおりでした。特に革命が2回目で戻るところが正しく動いていました。以下は軽い提案です（マージを止めるものではありません）」 |

### 書くときの3つのルール

1. **人ではなくコードに向ける。** 「あなたのミス」ではなく「この関数はこう動いているように見えます」。
   1人で作っている相手には、これがとくに大事です。1人分の仕事にそのまま向く指摘は、人格への評価に聞こえやすいからです。
2. **確認できたことと推測を分ける。** 実機で確認していないものは「**未確認ですが**」と明記します。
   （`/review` にも「確認できたか / 未確認か」を明記させています）
3. **止めるものと、そうでないものを分ける。** マージを止める指摘なのか、単なる提案なのかを最初の1行で書きます。

## Approve していい基準・してはいけない基準

### Approve していい

- [ ] `gh pr checkout` して**実際に遊んだ**
- [ ] ミッションカードの3つを試して、期待どおりだった
- [ ] Issue の必須要件が満たされている（正典と突き合わせた）
- [ ] CI が緑
- [ ] 残っている指摘は「提案」だけで、マージを止めるものが無い

### Approve してはいけない

- **動かしていない。** 差分を読んだだけ、CI が緑なだけ、では Approve できません。
- **不具合を見つけた。** 小さくても Approve せず、`Request changes` かコメントで返します。
  「小さいから」で通すと、統合デモで全員の前で落ちます。
- **「相手に悪いから」。** これがいちばん危険です。
  Approve は「良い人ですね」という意思表示ではなく、「**この状態で `main` に入れてよい**」という技術的な判断です。
  相手は1人でそのゲームを書いています。**あなたが黙ると、教えてくれる人が誰もいなくなります。**
- **時間が無いから。** 遊ぶ時間が取れなかったときは、Approve せずに
  「時間内に実機確認ができませんでした。差分だけ読んだ範囲では〇〇が気になります」と正直に書きます。

## 指摘を受けた側の作法

**指摘には必ず何かを返します。** 直しただけで黙っているのが、レビュアーをいちばん困らせます。
「自分の指摘がどうなったか」が分からないと、レビュアーは承認できません。

```
/fix-review <PR番号>
```

`/fix-review` がコメントを集め、対応方針の表を作ります。分類は次の3つだけです。

| 分類 | どんなとき | 返し方 |
|---|---|---|
| **直す** | 指摘が正しい | どう直したかを1行 + コミット SHA |
| **相談** | 直すべきか判断が分かれる | 理由を書いて、レビュアーと講師に判断を委ねる |
| **直さない** | 仕様どおり、または Issue の範囲外 | **理由を丁寧に書く**。「直さない」を選ぶこと自体は悪いことではありません |

**「直さない」は正当な選択肢です。** 大事なのは、理由を説明できるかどうかです。
正典（`docs/games/<ゲームID>.md`）に無いルールを足す提案なら、
「今回は正典どおりに実装しているので、このルールは入れていません」と返すのが正解です。

返信の型:

```text
ご指摘ありがとうございます。
<どう直したか / なぜ直さないか>
コミット: <SHA>
```

直したら、必ず回し直してください。

```powershell
npm run verify
```

**投稿は人間が行います。** AI が作った返信文をそのまま貼らず、一度自分で読んでください。

## 時間が足りないとき

優先順位はこの順です。上から順に、できるところまでやってください。

1. **実機で1回遊ぶ**（これだけは絶対に落とさない）
2. ミッションカードの3つを試す
3. `logic.test.ts` の `it("...")` を上から読む
4. 変更ファイルの一覧が担当フォルダの中だけか確認する
5. 差分を全部読む

1と2をやれば、3点セットのうち最低2つは必ず書けます。

レビューが間に合いそうにないと分かった時点で、**相手と講師にそう伝えてください。**
今回はレビュアーが1人しかいないので、あなたが止まると相手の Pull Request もそこで止まります。
黙って遅れるのが、いちばん困ります。
