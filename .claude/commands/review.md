割り当てられた相手の Pull Request #$0 をレビューします。**コメントの投稿はしません。**
出てきた指摘のうち、**自分が実機で確認できたものだけ**を、人間が GitHub の画面から投稿します。

## 0. このコマンドを打つ前に、人間が終わらせておくこと

**このコマンドは「もう遊び終わった人」が打つものです。**
ここから先の手順（checkout・ブラウザ・実機プレイ）は、Claude Code には実行できません。

### 0-1. ターミナルB で相手のブランチを取ってくる

ターミナルB（`npm run dev` を付けっぱなしにしているほう）で、自分の手で打ちます。

```
gh pr checkout <相手のPR番号>
```

**`npm ci` は打ちません。** 理由は次のとおりです。

- 参加者が編集できるのは `src/games/<自分のゲームID>/` の中だけで、
  `package.json` と `package-lock.json` は運営管理の保護領域です。
- つまり**誰の PR でも依存は同じまま**なので、`node_modules` を入れ直す必要がありません。
- `npm ci` は `node_modules` を作り直すため、その間ターミナルB の開発サーバーが不安定になります。
- もし相手の PR で依存が変わっていたら、入れ直すのではなく**それ自体が指摘対象**です。

### 0-2. ブラウザを再読み込みして、相手のゲームを実際に遊ぶ

ターミナルB の開発サーバーは付けっぱなしなので、
ブラウザ（http://localhost:5173/）を**再読み込みするだけ**で相手のコードに切り替わります。

遊ぶ前に、`docs/games/<相手のゲームID>.md` の
**「レビュアー向けミッション（このゲームの壊れやすい所）」** を開いてください。
そこに書かれたミッション1〜3を、**自分の手でエディタか紙に書き写します。**
Claude に要約させないでください。書き写す3行が、今日あなたが相手のコードを疑う唯一の足場です。

そのうえで、次を実際に操作します。

- 書き写したミッション1〜3を、そのとおりに実行する
- 普通に1回クリアする
- **やってはいけない操作**をわざとやる（判定中に連打する、出せないカードを出す、0枚のときに引く）
- リセットして2回目が正しく始まるか見る

差分を眺めるだけのレビューは、この研修では意味がありません。
**このコードを他人の目で見るのは、あなた1人だけです。**

### 0-3. 遊び終わってから `/review` を打つ

Claude Code は代わりに遊べません。順番が逆になっていたら、0-1 に戻ってください。

## 1. 人間が何を見たかを先に受け取る

このコマンドの最初に、人間へ次の3つを聞いてください。**答えが返るまで差分を読み始めないでください。**

1. ミッション1〜3をやってみて、**画面で実際に起きたこと**（「たぶん動く」は答えになりません）
2. わざとやった「やってはいけない操作」と、そのときの画面の反応
3. リセット後の2回目が正しく始まったかどうか

答えが「まだ遊んでいない」だった場合は、ここで止めて
**「先にターミナルB で `gh pr checkout <相手のPR番号>` して遊んでください」**と伝えてください。

なお、レビュー中は相手のブランチにいますが、`.claude/.state/owner.json` に自分の担当が記録されているので、
**相手のコードを編集しようとするとハーネスが止めます。** 気づいたことは直すのではなく指摘にします。

## 2. Issue と突き合わせる

```
gh pr view $0
gh issue view <その PR が閉じる Issue番号>
```

必須要件が満たされているかを1つずつ確認します。

## 3. 差分を読む

```
gh pr diff $0
```

観点:

- **ルールの誤り**: 境界（同じ数字、最後の1枚、全員パス）の扱いが Issue と一致しているか
- **テスト**: 正常系だけになっていないか。異常系・境界値を見ているか。
  テストのアサーションを1つ逆にしたら本当に落ちるか（怪しければ人間に手元で試してもらう）
- **担当範囲**: `src/games/<相手のゲームID>/` の外を触っていないか
- **読みやすさ**: 変数名・関数名だけで意味が分かるか。ルール判定が `.tsx` に漏れていないか
- **他への影響**: 共通基盤や他のゲームに影響していないか

## 4. 「レビューしてほしい点」を検問する

相手の PR 本文の **「レビューしてほしい点」** を読み、**具体的かどうかを判定してください。**

- 具体的な例: 「同じ数字が続いたときの引き分け処理が怪しいので、そこを重点的に」
- 具体的でない例: 「勝敗判定を見てください」「全体的にお願いします」
- **最悪の例**: テンプレートのコメント（`<!-- ここは AI に書かせず ... -->`）が消えていない、または空欄のまま

テンプレのまま・空欄・抽象的だった場合は、**それ自体を1件目の指摘として出してください。**
「どこを不安に思っているか教えてください」と聞くのがレビュアーの仕事です。
ここを素通りすると、相手は「自分が何を怖いと思っているか」を言葉にしないまま今日を終えます。

## 5. 指摘をまとめる（必ず3点セット）

次の3つを**必ず**出してください。

1. **ルール検証の指摘**（再現手順つき）
   「〇〇を〇回すると〇〇になります。Issue では〇〇のはずです」という形。
   再現手順が書けない指摘は投稿しないでください。
2. **テスト観点の提案**（具体的なテスト名で）
   「〇〇のテストを足すとよいです」ではなく
   「`it("同じ数字が続いたとき引き分けになる")` を足すとよいです」の形。
3. **質問または可読性の提案**（1つは `suggestion` 形式で書けるもの）

第4項目として、4 で判定した「レビューしてほしい点」への指摘があれば足します。

## 6. 人間に渡す（投稿は人間が GitHub の画面から行う）

指摘の一覧と、それぞれについて「人間が実機で確認できたか」を明記して報告してください。
**確認できていない推測は「未確認」と明示してください。** 投稿するかどうかは人間が決めます。

**コメントの投稿は Claude Code からはできません。** `gh pr review` と `gh pr comment` はハーネスが止めます。
（レビューに書いてよいのは「自分が実機で確認したこと」だけ、という約束を守るためです）

投稿は次の手順で、人間が自分で行います。

1. GitHub で相手の Pull Request を開く
2. **Files changed** タブを開く
3. 指摘したい行の左の `+` を押して、コメントを書く
4. 右上の **Review changes** を押し、**Comment**（または修正が必要なら **Request changes**）で送る
5. Approve するのは、指摘が解消されて自分が納得したときだけ

## 7. レビューの完了条件

次を全部言えたら、このレビューは終わりです。

- [ ] ターミナルB で `gh pr checkout <相手のPR番号>` して、**実際に遊んだ**
- [ ] `docs/games/<相手のゲームID>.md` のミッション1〜3を手で書き写し、そのとおりに操作した
- [ ] 再現手順つきの指摘を1つ以上出した
- [ ] 具体的なテスト名でテスト観点を1つ以上出した
- [ ] **相手の PR の「レビューしてほしい点」が具体的か確かめた。
      テンプレのままなら、それ自体を指摘した**

## 8. 自分のブランチに戻る

投稿後は、自分のブランチに戻るのを忘れないでください（ターミナルB で打ちます）。

```
git switch feature/<自分のゲームID>
```

戻ったらブラウザを再読み込みして、自分のゲームが表示されることを確認してください。
