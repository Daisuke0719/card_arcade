他のチームの Pull Request #$0 をレビューします。**コメントの投稿はしません。**
出てきた指摘のうち、**自分が実機で確認できたものだけ**を人間が投稿します。

## 1. まず動かす（これを飛ばさない）

```
gh pr checkout $0
npm ci
npm run dev
```

画面を開いて**実際に最後まで1回遊んでください**。
差分を眺めるだけのレビューは、この研修では意味がありません。

遊びながら次を試してください。

- 普通に1回クリアする
- **やってはいけない操作**をわざとやる（判定中に連打する、出せないカードを出す、0枚のときに引く）
- リセットして2回目が正しく始まるか見る

## 2. Issue と突き合わせる

```
gh pr view $0
gh issue view <その PR が閉じる Issue 番号>
```

必須要件が満たされているかを1つずつ確認します。

## 3. 差分を読む

```
gh pr diff $0
```

観点:

- **ルールの誤り**: 境界（同じ数字、最後の1枚、全員パス）の扱いが Issue と一致しているか
- **テスト**: 正常系だけになっていないか。異常系・境界値を見ているか。
  テストのアサーションを1つ逆にしたら本当に落ちるか（怪しければ手元で試す）
- **担当範囲**: `src/games/<そのチームのID>/` の外を触っていないか
- **読みやすさ**: 変数名・関数名だけで意味が分かるか。ルール判定が `.tsx` に漏れていないか
- **他への影響**: 共通基盤や他のゲームに影響していないか

## 4. 指摘をまとめる（必ず3点セット）

次の3つを**必ず**出してください。

1. **ルール検証の指摘**（再現手順つき）
   「〇〇を〇回すると〇〇になります。Issue では〇〇のはずです」という形。
   再現手順が書けない指摘は投稿しないでください。
2. **テスト観点の提案**（具体的なテスト名で）
   「〇〇のテストを足すとよいです」ではなく
   「`it("同じ数字が続いたとき引き分けになる")` を足すとよいです」の形。
3. **質問または可読性の提案**（1つは `suggestion` 形式で書けるもの）

## 5. 人間に渡す

指摘の一覧と、それぞれについて「自分が実機で確認できたか」を明記して報告してください。
**確認できていない推測は「未確認」と明示してください。** 投稿するかどうかは人間が決めます。

投稿後は、自分のブランチに戻るのを忘れないでください。

```
git switch feature/<自分のゲームID>
```
