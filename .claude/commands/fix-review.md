自分の Pull Request #$0 に付いた指摘へ対応します。

## 1. コメントを読む

```
gh pr view $0 --comments
```

指摘を1件ずつ、**原文のまま**引用して並べてください。要約しないでください。
（要約すると「相手が何を心配しているか」が落ちます）

## 2. 対応方針を表にする

**まだ直さないでください。** 先に方針を出して、人間と合意します。

| # | 指摘の内容 | 分類 | 対応方針 |
|---|---|---|---|

分類は次の3つです。

- **直す**: 指摘が正しい。どう直すかを1行で書く
- **相談**: 直すべきか判断が分かれる。理由を書いて人間に委ねる
- **直さない**: 仕様どおり、または Issue の範囲外。**理由を丁寧に書く**
  （「直さない」を選ぶこと自体は悪いことではありません。理由を説明できるかが大事です）

## 3. 合意後に直す

人間が方針に合意したら実装します。修正のたびに次を回してください。

```
npm run verify
```

直したあと、**人間がターミナルB のブラウザを再読み込みして、指摘された操作をもう一度やります。**
「テストが通ったから直った」は、この研修では直ったことになりません。

## 4. 返信文を作る

指摘1つずつに対して、次の形の返信案を作ってください。

```
ご指摘ありがとうございます。
<どう直したか / なぜ直さないか>
コミット: <SHA>
```

## 5. 投稿は人間が GitHub の画面から行う

**返信の投稿は GitHub の画面から行います。`gh pr comment` はハーネスが止めます。**
（`gh pr review` と `gh issue comment` も同じく止まります。
他の人の画面に文字が出る操作は、確認した本人が自分の手で行う決まりです）

人間の手順:

1. GitHub で自分の Pull Request を開く
2. 該当のコメントの **Reply** に返信文を貼る
3. 直したものは **Resolve conversation** を押す
4. 全部返し終わったら、レビュアーに「直しました」と一言伝える

**返信せずに直しただけ、で終わらせないでください。**
レビュアーは「自分の指摘がどうなったか」が分からないと承認できません。
