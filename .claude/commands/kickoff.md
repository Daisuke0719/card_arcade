担当ゲームの実装を始める前の調査と計画を行います。**このコマンドではコードを1行も変更しません。**
（Edit / Write ツールはこのコマンドの間だけ使えなくなっています）

## 1. 前提を確認する

次を順に読んでください。

1. `CLAUDE.md`（絶対に守る5条）
2. `src/games/CLAUDE.md`（ファイルの役割と @core / @ui の早見表）
3. `src/games/example-game/logic.ts` と `ExampleGame.tsx`（お手本の型）
4. `src/games/example-game/README.md`（なぜ logic を分けるのか）

現在のブランチを確認し、自分の担当ゲームを特定してください。

```
git branch --show-current
```

## 2. Issue を読む

```
gh issue view $0
```

Issue が無い場合は `docs/games/<ゲームID>.md` を正典として読んでください。

## 3. 自分の担当フォルダの現状を見る

`src/games/<ゲームID>/` の5ファイルを読み、雛形として何が用意されているかを把握します。

## 4. 計画を提示する

次の形で提示してください。**まだ実装しないでください。**

### 採用するルール
Issue に書かれたルールをそのまま列挙する。曖昧な点があれば「Issue にはこう書かれているので、こう解釈する」と明示する。
Issue に書かれていないローカルルールは実装しない。

### 状態の設計
`logic.ts` に置く State 型と Action 型。フェーズ（`Phase`）の遷移図。

### 純粋関数の一覧
関数名 / 引数 / 戻り値 / 何を判断するか。
**時間と乱数が入り込む箇所は `pendingDelayMs` と `Rng` に閉じ込める**方針であることを示す。

### テストの一覧
Issue の必須要件それぞれに、対応するテスト名を1つ以上。
境界値（同じ数字・最後の1枚・0枚）と、やってはいけない操作の拒否を必ず含める。

### 画面の構成
使う `@ui` のコンポーネントと、それぞれの役割。

### 実装の順番
Step1（logic + test）→ Step2（画面）→ Step3（必須要件の残り）に分ける。
各 Step の完了条件を「どのコマンドが通れば次へ行けるか」で書く。

### 分からないこと・確認したいこと
判断に迷った点を正直に挙げる。

## 5. 止まる

計画を提示したら、**必ずそこで止まってください。**
人間が計画を確認して合意してから `/implement` に進みます。

人間が確認するのは次の点です。
- Issue の必須要件と計画が1対1で対応しているか
- ルールの解釈が Issue と食い違っていないか
- テストが正常系だけに偏っていないか
- 担当フォルダの外を触る計画になっていないか
